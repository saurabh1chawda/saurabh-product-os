## Current Authentication Baseline

A16.3a established a provider-neutral authentication boundary under `apps/api`.
It introduced credential-free authenticated identity, safe authentication
errors, and trusted-principal mapping. A16.3b selected a generic OIDC/JWT
strategy for the first production-oriented provider contract, while explicitly
deferring concrete provider selection, public route binding, and live provider
integration.

A16.3d implements the generic OIDC/JWT adapter contract needed by that decision.
It remains API-local and does not change Domain, Application, Infrastructure,
runtime composition, repository contracts, persistence, authorization, or
idempotency behavior.

## Generic Adapter Boundary

The implemented boundary is:

```text
bearer credential
  -> generic OIDC/JWT authentication configuration
  -> injected verifier port
  -> verified credential-free claims
  -> PortfolioWorkspaceAuthenticatedIdentity
  -> PortfolioWorkspacePresentationPrincipal
```

The adapter depends on an injected verifier. It does not implement cryptographic
JWT verification, decode unsigned token payloads, fetch JWKS documents, or use a
provider SDK. A future concrete verifier/JWKS slice must satisfy the verifier
port.

## Configuration Contract

`PortfolioWorkspaceOidcJwtAuthenticationConfiguration` is immutable and
serializable. It contains only non-secret provider-neutral settings:

- issuer;
- accepted audiences;
- allowed algorithms;
- bounded clock tolerance;
- authentication provider identifier;
- user/service principal-type strategy;
- optional display-name claim mapping.

Validation fails closed:

- issuer is required and bounded;
- at least one audience is required;
- at least one allowed algorithm is required;
- `none` is rejected;
- clock tolerance is non-negative and capped;
- provider identifier is bounded;
- claim names are bounded and control-character safe.

Configuration loading remains host-owned. The authentication module does not
read `process.env`.

## Bearer Credential Contract

`PortfolioWorkspaceBearerTokenCredential` represents bearer-token material at
the authentication boundary only.

The token is available only for verifier invocation. Public serialization and
inspection return a redacted shape:

```json
{
  "credentialType": "bearer-token",
  "redacted": true
}
```

Tokens do not enter trusted principals, presentation responses, authorization
resources, command contexts, idempotency scopes, or persistence.

## Verifier Port

`PortfolioWorkspaceJwtVerifier` is a provider-neutral async port:

```text
verify(token, verificationRequirements)
  -> Result<PortfolioWorkspaceVerifiedJwtClaims, PortfolioWorkspaceAuthenticationError>
```

The verifier receives the token and requirements for issuer, audience, and
algorithm. It returns credential-free verified claims. A future implementation
may use OIDC discovery, JWKS, and a JWT library, but those concerns remain
outside this slice.

## Claim Validation

The adapter validates verifier output even though the verifier is expected to
perform cryptographic verification.

Required rules:

- issuer must exactly match configuration;
- at least one token audience must match a configured audience;
- algorithm must be in the configured allowlist;
- subject is required, normalized, bounded, and control-character safe;
- expired credentials are rejected;
- not-yet-valid credentials are rejected;
- bounded clock tolerance is applied deterministically;
- display name is optional but must be safe if present;
- principal type is fixed or explicitly claim-driven.

The adapter does not allow issuer fallback, audience fallback, missing-subject
fallback, expired-token fallback, `alg=none`, or arbitrary service-principal
inference.

## User and Service Principal Mapping

Principal type defaults to a fixed `user` strategy. Service principals are
supported only through an explicit fixed strategy or an explicit verified claim
strategy. The adapter does not infer service identity from email addresses,
domains, or display names.

Authentication proves identity only. Service principals receive no roles,
permissions, policy bypass, or authorization privileges from authentication.

## Safe Errors and Retryability

A16.3d extends the authentication failure taxonomy with provider-neutral
reasons for malformed credentials, verification failure, issuer mismatch,
audience mismatch, algorithm rejection, invalid subject, expired credential,
not-yet-valid credential, invalid configuration, and verifier unavailability.

Retryability is conservative:

- missing, malformed, invalid, expired, mismatched, and rejected credentials are
  not retryable by replaying the same credential;
- invalid configuration is not client-retryable;
- verifier unavailability is retryable;
- unexpected verifier throws are mapped to safe verifier-unavailable failures.

Errors do not expose raw tokens, claim payloads, signing keys, JWKS responses,
provider stacks, SQL, secrets, or raw cryptographic failure details.

## Host Ordering

Future public host integration must preserve this order:

```text
transport credential extraction
  -> authentication
  -> trusted principal
  -> authorization
  -> durable idempotency for public mutations
  -> Application Service invocation
```

A16.3d does not bind authentication into public routes or internal handlers.
Existing internal handlers may continue receiving trusted principals from the
host boundary.

## JWKS and Key Rotation Boundary

This slice defines only the verifier port required by future JWKS work. Future
provider/JWKS implementation must address:

- key ID selection;
- JWKS discovery or configured JWKS URI;
- cache and refresh policy;
- key rotation;
- unknown `kid` behavior;
- issuer and audience enforcement;
- network timeout/failure behavior;
- no silent trust on unknown keys.

No network JWKS retrieval is implemented here.

## Dependency Decision

A16.3d adds no runtime dependency. The generic adapter uses an injected verifier
port. A concrete verifier library belongs in a future provider/JWKS slice.
