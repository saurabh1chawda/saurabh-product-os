# A16.4b - Portfolio Workspace Production Authorization Policy and Resource Resolver

## Executive Summary

A16.4b implements the first production authorization decision layer for Portfolio Workspace internal API flows.

The policy is provider-agnostic and deny-by-default. It derives initialization ownership only from the trusted `PortfolioWorkspacePresentationPrincipal`, stores that ownership as the Domain-approved `PortfolioWorkspaceAuthorizationResourceReference`, and authorizes existing execution access by resolving the durable stored resource before allowing the query.

Provider authentication, role systems, durable idempotency, public mutation routes, list/search, observability, and policy administration remain outside this slice.

## Current Boundary

The API host remains the presentation host boundary. It does not authenticate tokens, parse sessions, inspect repositories, open database connections, construct aggregates, or publish facts.

The Application package owns the repository port. A narrow `ResolvePortfolioExecutionAuthorizationResourceApplicationService` now loads a `PortfolioExecution` through that port and returns only the execution identity plus durable authorization resource. It does not expose aggregate state, repository revision, facts, projections, or persistence records.

The Infrastructure runtime composes this resolver with the same `PortfolioExecutionRepository` instance used by the other Portfolio Workspace Application Services.

## Authorization Policy

Initialization authorization creates an ownership resource from the trusted principal:

```text
trusted principal
  -> principal type
  -> authentication provider
  -> principal id
  -> stable SHA-256 identity hash
  -> PortfolioWorkspaceAuthorizationResourceReference
```

The request body, actor reference, command context, and transport headers cannot assert or override ownership.

Existing execution authorization resolves the stored authorization resource and compares it to the trusted principal-derived resource. A mismatch returns a safe forbidden presentation error.

Service principals receive no implicit global bypass. A service principal may access only resources initialized for that exact service principal identity.

## Resource Resolver

`PortfolioWorkspaceRuntimeAuthorizationResourceResolver` uses the runtime-exposed application resolver. It maps application not-found and persistence failures through existing presentation error mapping.

This keeps API handlers away from:

- repositories;
- Drizzle or PostgreSQL;
- loaded aggregate envelopes;
- revision metadata;
- persistence records;
- aggregate internals.

The get handler may perform one authorization-resource resolution before its normal get query. That duplicate read is accepted for this slice because it preserves the existing summary-only query result and avoids leaking authorization state into presentation responses.

## Host Composition

The API host composes `PortfolioWorkspaceProductionAuthorization` by default once the runtime is ready. Tests may still inject explicit authorization fakes.

This is not an allow-all fallback. The default policy denies mismatched durable ownership and returns only safe presentation errors.

## Not-Found and Forbidden Semantics

The current internal handler preserves not-found for missing executions during resource resolution. Existing but unauthorized executions return forbidden. This behavior is internal-host safe and does not expose persistence details, repository revision, SQL, or credentials.

Public endpoint exposure may revisit not-found versus forbidden equivalence as part of the public API threat model.

## Validation

Database-free validation covers:

- durable resource resolution through the application repository port;
- host default production authorization composition;
- initialization ownership derived from trusted principal only;
- get authorization allowed for matching durable ownership;
- mismatched users denied;
- service principals denied unless exact owner;
- safe forbidden/not-found/persistence error mapping;
- no repository, database, provider-auth, framework, retry, idempotency, or aggregate construction leakage into handlers.

Live PostgreSQL validation is deferred because this slice does not change schema, mapper, repository SQL, migration behavior, or runtime database lifecycle. The runtime object graph does add one application resolver, so A16 release validation should include the existing live runtime/API host suites before production release.

## Remaining Production Readiness Conditions

- Provider authentication integration.
- Production authorization administration/owner-source integration if ownership must come from organization or plan ownership instead of principal identity.
- Durable idempotency before public mutation exposure.
- Public route threat-model review, including not-found versus forbidden semantics.
- Branch protection and hosted CI proof remain governed by A16 release gates.
