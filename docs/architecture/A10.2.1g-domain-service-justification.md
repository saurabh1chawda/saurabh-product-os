# A10.2.1g - Domain Service Justification

## 1. Purpose

This document evaluates whether Portfolio Workspace currently justifies Supporting Domain Services.

It applies after completion of:

- Canonical vocabulary.
- Value objects and planning references.
- Supporting entities.
- `PortfolioExecution` behavioral aggregate.
- Immutable domain facts.
- Pure domain policies.
- Pure domain projections.

This document does not assume that domain services exist. It determines whether they should exist.

This document does not define TypeScript interfaces, implementations, registries, service locators, dependency injection, repositories, handlers, or application services.

## 2. Definition

A Domain Service is pure domain logic that does not naturally belong to a single Aggregate, Entity, or Value Object, yet remains entirely within the Domain Model.

A Domain Service may be justified when domain behavior spans multiple domain concepts and cannot be assigned cleanly to an existing model object.

A Domain Service is not:

- Orchestration.
- Workflow.
- Application service.
- Repository.
- Infrastructure.
- Policy engine.
- Projection builder.
- Integration adapter.
- Persistence adapter.
- UI coordinator.
- AI provider boundary.

Domain services MUST remain bounded-context-specific unless future architecture review authorizes shared abstractions.

## 3. Decision Criteria

A Domain Service is justified only if all of the following are true:

- The logic is domain logic.
- The logic spans multiple domain concepts.
- The logic belongs to no existing aggregate, entity, value object, policy, or projection.
- The logic has no infrastructure dependencies.
- The logic has no application coordination responsibilities.
- The logic has deterministic behavior.
- The logic has no side effects.

If logic can naturally live inside `PortfolioExecution`, a supporting entity, a value object, a domain policy, or a domain projection, a Domain Service MUST NOT be introduced.

## 4. Evaluation of Portfolio Workspace

| Capability | Current owner | Evaluation | Domain service justified |
| --- | --- | --- | --- |
| Execution identity and source references | `PortfolioExecution`; value objects | The aggregate owns one operational run and holds immutable plan, snapshot, approval, and command references. | No |
| Work-item ownership and duplicate detection | `PortfolioExecution` | Collection ownership and duplicate checks are aggregate-local invariants. | No |
| Candidate and accepted-artifact ownership | `PortfolioExecution`; supporting entities | The aggregate owns collections; entities own local identity and lifecycle representation. | No |
| Lifecycle changes | `PortfolioExecution` | Behavioral operations own lifecycle evolution. Generic transition services are prohibited. | No |
| Artifact acceptance and rejection | `PortfolioExecution` | Acceptance and rejection are aggregate decisions with explicit human context already represented by command context and facts. | No |
| Execution completion and cancellation | `PortfolioExecution` | Completion and cancellation are aggregate-level business operations. | No |
| Domain facts | Immutable fact classes | Facts represent completed business outcomes and have no behavior. | No |
| Completion, acceptance, and consistency reasoning | Domain policies | Reusable deterministic business reasoning is already modeled as pure policies. | No |
| Execution, work-item, candidate, and artifact read views | Domain projections | Read-oriented summaries are already modeled as projections. | No |
| Application orchestration | Application layer | Command sequencing, authorization, retries, idempotency delivery, and persistence coordination are outside the domain. | No |
| Infrastructure integration | Infrastructure layer | Storage, external APIs, browser automation, messaging, and AI providers remain outside domain packages. | No |

The current Portfolio Workspace model has one aggregate root. All implemented business behavior either belongs to `PortfolioExecution`, supporting entities, value objects, policies, facts, or projections.

No remaining implemented behavior requires a separate Domain Service.

## 5. Candidate Services

| Candidate service | Decision | Reason |
| --- | --- | --- |
| `PortfolioExecutionInitializationService` | Not justified | Initialization identity, idempotency delivery, and creation coordination are application concerns until a future initialization slice proves otherwise. Creation invariants should remain aggregate-owned. |
| `PortfolioWorkItemCoordinationService` | Not justified | Work-item coordination is aggregate-local. Introducing a service would weaken aggregate ownership. |
| `ArtifactAcceptanceService` | Not justified | Candidate acceptance is an explicit aggregate operation. Human approval provenance is supplied by command context; workflow and authorization remain application concerns. |
| `ExecutionCompletionService` | Not justified | Completion mutation belongs to `PortfolioExecution`; completion reasoning already belongs to `ExecutionCompletionPolicy`. |
| `ExecutionConsistencyService` | Not justified | Consistency reasoning already belongs to `ExecutionConsistencyPolicy`; duplicate detection belongs to the aggregate. |
| `ProjectionBuilderService` | Rejected | Projection construction belongs to projection factories. A builder service would blur projection and application responsibilities. |
| `PolicyExecutionService` | Rejected | Policy engines and registries are explicitly deferred by A10.2.1e. |
| `PortfolioWorkspaceService` | Rejected for domain model | This name implies application orchestration. It may only be considered outside the domain package in a future application-layer slice. |
| Cross-aggregate domain service | Deferred | No second aggregate exists. Re-evaluate only if cross-aggregate invariants appear. |

No candidate service currently satisfies all Domain Service decision criteria.

## 6. Architectural Recommendation

Conclusion A: No Supporting Domain Services are currently justified.

The completed architecture is clearer without them:

- `PortfolioExecution` owns mutable domain behavior and aggregate invariants.
- Entities own local identity and immutable state representation.
- Value objects own scalar identity and reference validation.
- Facts record immutable completed outcomes.
- Policies own reusable deterministic business reasoning.
- Projections own read-oriented derivation.
- Application services, repositories, integrations, and workflow remain outside the domain.

Introducing a Domain Service now would duplicate existing ownership or pull application coordination into the domain model.

A10.2.2 should skip a Supporting Domain Services implementation slice unless new implementation evidence appears.

## 7. Future Re-evaluation

This decision should be revisited only when at least one of the following occurs:

- A second Portfolio Workspace aggregate is introduced.
- Cross-aggregate invariants appear.
- Domain behavior spans multiple aggregates and cannot belong to either aggregate.
- Domain logic cannot naturally be represented as aggregate behavior, entity behavior, value-object validation, policy reasoning, or projection derivation.
- The bounded context expands beyond the current pilot scope.
- Architecture review identifies duplicated pure domain logic that is not policy or projection logic.

Re-evaluation must not be triggered merely by a desire to reduce small amounts of duplication or to create a generic service layer.

## 8. Deferred Topics

The following remain explicitly deferred:

- Application Services.
- Infrastructure Services.
- Repositories.
- Persistence adapters.
- CQRS infrastructure.
- Workflow.
- Integration.
- Service registries.
- Dependency injection.
- Shared execution services.
- Shared approval services.
- Shared artifact services.
- Shared projection services.

These are not gaps in Portfolio Workspace domain modeling. They require future implementation evidence and architecture review.

## 9. Final Decision

Portfolio Workspace currently does not require Supporting Domain Services.

Domain behavior remains assigned to the existing aggregate, entities, value objects, facts, policies, and projections.

No domain service implementation should begin until future architecture evidence satisfies all decision criteria in this document.

NO DOMAIN SERVICES CURRENTLY JUSTIFIED
