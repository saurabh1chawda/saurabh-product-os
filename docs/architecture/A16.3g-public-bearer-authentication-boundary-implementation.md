## Executive Summary

A16.3g implements the first public Portfolio Workspace authentication boundary under `apps/api/src/portfolio-workspace/public/`. It extracts bearer credentials strictly from the `Authorization` header, normalizes or generates correlation before authentication, invokes the existing A16.3d/e authentication abstraction, and returns either a trusted `PortfolioWorkspacePresentationPrincipal` or a safe public authentication failure.

It does not implement a public get route, public initialize route, HTTP framework adapter, authorization behavior, idempotency behavior, Application Service invocation, runtime access, repository access, persistence behavior, observability, rate limiting, retries, or provider discovery.

## Public Header Contract

`PortfolioWorkspacePublicAuthenticationRequest` contains only:

- optional framework-neutral headers;
- optional incoming correlation hint.

Headers may represent a single string value or an explicit readonly string array so duplicate `Authorization` values can be rejected deterministically.

The contract does not contain framework request objects, cookies, query parameters, body credentials, sessions, provider claims, JWT objects, repositories, runtimes, or database references.

## Bearer Extraction Rules

Extraction reads only the `Authorization` header using case-insensitive header-name matching.

Accepted form:

```text
Bearer <credential>
```

Rules:

- the scheme is case-insensitive;
- exactly one space separates scheme and credential;
- credential must be non-empty;
- credential must not contain whitespace;
- leading/trailing header whitespace is rejected;
- comma-joined multiple credentials are rejected;
- control characters and line breaks are rejected;
- unsupported schemes are rejected;
- credentials from query, body, cookies, and custom token headers are ignored.

## Duplicate Header Decision

More than one `Authorization` header representation is rejected as malformed. The boundary never chooses the first value silently.

Duplicate forms rejected include:

- multiple case variants such as `Authorization` and `authorization`;
- array values containing more than one element.

## Header Size Limit

The raw `Authorization` header limit is:

```text
8192 bytes/characters at the string boundary
```

The extracted bearer token is also bounded to the existing bearer credential limit of 4096 characters. Oversized values fail before authentication or verifier invocation.

The 8192-character limit is intentionally conservative: large enough for normal JWT bearer usage, but small enough to avoid unbounded parsing or accidental log/diagnostic exposure pressure.

## Credential Privacy

Raw credential lifetime is limited to:

```text
extraction -> PortfolioWorkspaceBearerTokenCredential -> authentication adapter invocation
```

Successful and failed public authentication result serialization contains no raw token. The redacted bearer credential contract is reused. Public failure JSON, messages, response metadata, and inspection output do not include token material, raw claims, JOSE details, JWKS data, provider errors, or verifier causes.

## Correlation Flow

Correlation is established before authentication:

```text
incoming untrusted hint
  -> normalizePortfolioWorkspaceCorrelationId(...)
  -> safe correlation for success or failure
```

Unsafe incoming correlation values are replaced by trusted generated values and are not echoed. If generation itself fails, the boundary uses a fixed safe fallback correlation ID.

## Authentication Boundary

`PortfolioWorkspacePublicAuthenticationBoundary` receives dependencies explicitly:

- `PortfolioWorkspaceAuthenticationAdapter`;
- `PortfolioWorkspaceCorrelationIdGenerator`.

It does not read `process.env`, instantiate JOSE/JWKS configuration, fetch provider metadata, construct a runtime, or invoke authorization.

## Authentication Success Contract

Success returns `PortfolioWorkspacePublicAuthenticationSuccess`:

- trusted `PortfolioWorkspacePresentationPrincipal`;
- safe correlation ID;
- response metadata containing `x-correlation-id`.

Success does not contain token, raw claims, JWT header, issuer configuration, JWKS data, verifier details, session, access token, ID token, refresh token, repository, runtime, or Application Service.

## Authentication Failure Mapping

Typed authentication failures map as follows:

| Existing reason | Public status | Challenge |
| --- | ---: | --- |
| missing, malformed, invalid, verification, issuer, audience, algorithm, subject, expiry, not-before, invalid identity, trusted-principal mapping | 401 | yes |
| authentication unavailable | 503 | no |
| verifier unavailable | 503 | no |
| invalid authentication configuration | 500 | no |

The boundary preserves existing typed authentication semantics. It does not inspect or match error message strings.

## WWW-Authenticate

Only `401` authentication failures include:

```text
WWW-Authenticate: Bearer
```

The challenge is intentionally minimal. It does not include provider reason, token detail, issuer, audience, realm, `error`, or `error_description`.

## Authorization Boundary

A16.3g performs no authorization. Authentication success means identity is trusted, not that any Portfolio execution is accessible.

Authorization remains the responsibility of the existing API host/internal handler flow and future public route wrappers.

## Route and Service Boundary

A16.3g stops after:

```text
public credential extraction
  -> authentication
  -> trusted principal or safe authentication failure
```

It does not call `getPortfolioExecution`, `initializePortfolioExecution`, runtime services, repositories, PostgreSQL, Domain aggregates, or Domain facts.
