# A16.4b - Durable Idempotency Boundary and Atomicity Architecture

## Document Control

- Slice: A16.4b
- Scope: Boundary reconciliation and atomicity architecture for durable Portfolio Workspace idempotency
- Repository: saurabh-product-os
- Status: IMPLEMENTED BY A16.4c

## Executive Summary

A16.4b reconciles stale future idempotency tests with the A16.4a decision that Application owns semantic idempotency contracts. The old assertion that Application must contain no idempotency vocabulary is obsolete.

The approved boundary is now:

```text
Domain
  no idempotency

Application
  semantic idempotency contracts and port

Infrastructure
  durable PostgreSQL persistence and future transaction mechanics

Presentation / Host
  raw external key handling, hashing, canonical request fingerprinting, and transport replay mapping
```

A16.4c adds the atomic orchestration boundary that coordinates idempotency reservation, aggregate mutation/save, and idempotency completion in one PostgreSQL transaction. Public mutation exposure remains deferred until Presentation/Host integration enforces raw-key handling and durable idempotency for requests.

## A16.4a Contract Baseline

A16.4a added Application-owned contracts under:

`packages/portfolio-workspace-application/src/idempotency`

Those contracts include:

- exactly nine mutation operations;
- `PortfolioWorkspaceIdempotencyIdentity`;
- SHA-256 `PortfolioWorkspaceIdempotencyKeyHash`;
- SHA-256 `PortfolioWorkspaceIdempotencyRequestFingerprint`;
- durable states `reserved` and `completed`;
- `PortfolioWorkspaceIdempotencyReplayPayload`;
- reservation observations for acquired, replay available, in progress, and fingerprint mismatch;
- `PortfolioWorkspaceIdempotencyPort`;
- safe idempotency errors;
- original command/correlation binding;
- expiry metadata.

The contracts deliberately do not add PostgreSQL schema, migrations, adapters, runtime composition, public handlers, retries, cleanup, or observability.

- `packages/infrastructure/tests/portfolio-workspace-idempotency.test.ts`

Those assertions were updated to enforce the new boundary:

- Application may contain semantic idempotency contracts and the port.
- Application must not contain raw `Idempotency-Key`, HTTP request concepts, status-code mapping, Drizzle, PostgreSQL, Pool, schema, transaction manager, or unit-of-work concepts.
- Infrastructure may depend inward on Application idempotency contracts.
- API contracts and Infrastructure idempotency code must remain free of framework and generic orchestration leakage.

## Infrastructure Ownership

Infrastructure will own the durable implementation of the Application port and the PostgreSQL transaction mechanics needed by A16.4c.

Infrastructure-owned concepts:

- durable idempotency record;
- persistence record version;
- PostgreSQL table and indexes;
- mapper between Application contracts and database rows;
- durable reservation uniqueness;
- completed replay persistence;
- corrupt/unsupported record detection;
- storage unavailable mapping;
- transaction-scoped execution against the same database connection/session used for aggregate persistence.

Infrastructure must not own:

- semantic operation definitions;
- raw external idempotency key parsing;
- canonical request fingerprint construction;
- presentation error/status mapping;
- Domain business rules.

## Durable Record Requirements

The future PostgreSQL record must store:

- deterministic scope identity or scope hash;
- record version;
- operation;
- pseudonymous authorization resource reference;
- operation resource identity;
- hashed external idempotency key;
- request fingerprint algorithm and value;
- durable state;
- original command ID;
- original correlation ID;
- versioned replay payload;
- createdAt;
- expiresAt;
- completedAt when completed.

Raw external keys, provider tokens, sessions, raw authorization claims, Domain aggregates, raw Domain facts, command context objects, SQL details, and database connection metadata must not be stored.

## Atomicity Requirement

Independent calls are not production-safe:

```text
reserve idempotency
save PortfolioExecution
complete idempotency
```

If the process dies after aggregate save but before idempotency completion, retry behavior becomes ambiguous and may either duplicate mutation or leave a stuck reservation.

A16.4c must provide this invariant:

```text
BEGIN TRANSACTION
  observe or reserve idempotency identity
  if replay/fingerprint mismatch/in-progress, do not mutate
  if acquired:
    load PortfolioExecution if needed
    invoke the existing mutation behavior
    save PortfolioExecution with expected revision
    persist replay completion
COMMIT

ROLLBACK on failure
```

Reservation, aggregate save, and replay completion must commit or roll back together.

## Transaction Ownership Decision

Chosen ownership for A16.4c:

Infrastructure transaction-bound mutation orchestrator implementing an Application-facing, Portfolio Workspace-specific atomic capability.

Rationale:

- Domain must not know transactions.
- Presentation must not coordinate SQL.
- Existing Application mutation services should not receive Drizzle, Pool, or transaction handles.
- The current `PortfolioExecutionRepository` is revision-aware but not transaction-scoped.
- PostgreSQL aggregate persistence and idempotency persistence must share one transaction.
- A generic UnitOfWork or TransactionManager is not justified.

The coordinator may be composed by Infrastructure/runtime later, but it must expose only technology-neutral outcomes across the Application/Presentation boundary.

## Reservation Concurrency Semantics

Same key, same fingerprint, completed:

- return replay available;
- do not mutate.

Same key, same fingerprint, in progress:

- return deterministic in-progress outcome;
- do not mutate.

Same key, different fingerprint:

- return fingerprint mismatch;
- do not mutate.

Two concurrent first requests:

- PostgreSQL uniqueness ensures only one acquires the durable reservation.

Transaction rollback after attempted reservation:

- no durable reservation should remain committed.

Aggregate optimistic concurrency conflict:

- rollback the idempotency reservation and aggregate write together;
- do not mark success;
- preserve only `reserved` and `completed` states unless a future recovery slice proves another state is required.

## Replay Contract Assessment

The A16.4a `PortfolioWorkspaceIdempotencyReplayPayload` is sufficient as the Application semantic boundary:

- versioned;
- opaque to Infrastructure;
- deterministic JSON-compatible payload;
- free of Domain aggregates, raw facts, command context, repository revision, and database internals.

Infrastructure should store the replay payload as a versioned JSON payload unless a future migration requirement proves specific indexed columns are needed. It should not reinterpret replay semantics.

## Expiry Semantics

Retention duration remains configuration/product policy.

Required future behavior:

- unexpired `reserved` records block duplicate execution;
- unexpired `completed` records replay matching requests;
- expired records may be treated as absent only if the same transaction safely replaces or removes the expired record;
- expiration must not allow two active owners of one unexpired idempotency identity.

No cleanup worker, scheduler, polling loop, or TTL service is implemented in A16.4b.

## Raw Key Privacy

Presentation receives the raw external key and must hash it before constructing Application contracts.

Application and Infrastructure receive only the hash.

The canonical identity tuple provides namespace separation, so no secret-key hashing is required by this architecture. If a future threat model requires keyed hashing, it must be introduced as a separate security decision.

Raw keys must not be:

- persisted;
- logged;
- returned;
- serialized in errors;
- placed in replay payloads.

## Request Fingerprint Ownership

Presentation/Host owns canonical request fingerprint construction because it has access to parsed transport inputs and presentation contract versions.

Fingerprint inputs should include:

- operation;
- presentation contract version;
- authorization resource reference;
- execution/resource identity;
- semantic mutation payload.

Fingerprint inputs must exclude:

- command ID;
- generated correlation ID;
- occurredAt;
- raw principal claims;
- provider tokens;
- session data;
- transient headers.

A16.4d must implement canonicalization in a stable, key-ordered way and pass only the opaque fingerprint to Application.
