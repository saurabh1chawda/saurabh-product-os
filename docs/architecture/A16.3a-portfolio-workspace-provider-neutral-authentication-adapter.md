# A16.3a - Portfolio Workspace Provider-Neutral Authentication Adapter

- Status: Implemented

## Purpose

A16.3a establishes the provider-neutral authentication trust boundary required before a public Portfolio Workspace host can accept authenticated requests. It does not select or implement an authentication provider. It defines how an externally authenticated identity becomes the existing trusted `PortfolioWorkspacePresentationPrincipal`.

## Baseline

The existing Portfolio Workspace API presentation layer already defines:

- `PortfolioWorkspacePresentationPrincipal`
- `PortfolioWorkspacePresentationPrincipalType.User`
- `PortfolioWorkspacePresentationPrincipalType.Service`
- safe presentation errors for unauthenticated and unavailable outcomes
- command-context creation from trusted principals
- production authorization based on trusted principal identity

No existing repository-wide authentication abstraction was found that should be reused for this bounded context.

## Authentication Boundary

Authentication remains API/host-owned. The new boundary distinguishes:

1. external authentication context, which may contain untrusted credential material;
2. a provider-neutral authentication adapter that verifies or resolves identity;
3. `PortfolioWorkspaceAuthenticatedIdentity`, a credential-free identity result;
4. `PortfolioWorkspacePresentationPrincipal`, the existing trusted presentation principal.

The boundary is implemented under `apps/api/src/portfolio-workspace/authentication/`.

## Adapter Contract

`PortfolioWorkspaceAuthenticationAdapter` accepts `PortfolioWorkspaceExternalAuthenticationContext` and returns:

- success: `PortfolioWorkspaceAuthenticatedIdentity`
- failure: `PortfolioWorkspaceAuthenticationError`

The adapter contract is asynchronous so a future host can call an external provider, but this slice does not implement provider calls, token verification, JWT parsing, OAuth, OIDC, or SDK integration.

## Authenticated Identity Contract

`PortfolioWorkspaceAuthenticatedIdentity` contains only:

- `provider`
- `subject`
- `principalType`
- optional `displayName`

It is immutable, deterministic, serializable, and value-comparable. It does not contain raw claims, tokens, cookies, sessions, credentials, provider SDK objects, authorization decisions, roles, permissions, or resource references.

## Trusted Principal Mapping

`mapAuthenticatedIdentityToPresentationPrincipal(...)` maps:

- `subject` to `principalId`
- `provider` to `authenticationProvider`
- `principalType` to the existing presentation principal type
- optional `displayName` unchanged after validation

This preserves the existing authorization ownership identity semantics. Existing persisted authorization references hash `authenticationProvider` and `principalId`; A16.3a does not change that format.

## Human and Service Principals

Human and service principals are both supported through the same contract. Service principals do not receive implicit privilege, bypass, roles, permissions, or different authorization behavior. Authorization remains an explicit separate decision.

## Error Contract

`PortfolioWorkspaceAuthenticationError` exposes safe categories only:

- `authentication-required`
- `authentication-invalid`
- `authentication-unavailable`
- `invalid-authenticated-identity`
- `trusted-principal-mapping-failed`

Provider failures are reduced to safe metadata: error name and code only. Messages, stack traces, claims, tokens, credentials, SQL, and provider details are not serialized.

Presentation mapping uses the existing safe presentation vocabulary:

- required/invalid/mapping failures map to unauthenticated;
- unavailable failures map to Portfolio Workspace unavailable.

## Credential Privacy

Credential material remains outside:

- Domain
- Application
- Portfolio Workspace aggregate state
- command contexts
- authorization resource references
- idempotency records
- normal presentation error output

Tests verify raw token and claim fixtures do not appear in trusted principals or serialized authentication errors.

## Authentication and Authorization Separation

Authentication answers who the principal is. Authorization answers whether that principal can perform an operation on a resource. A16.3a does not modify production authorization policy and does not infer authorization from authentication.

## Host Integration

The API host and internal handlers continue to receive `PortfolioWorkspacePresentationPrincipal`. This slice adds the safe upstream mapping boundary that future host routes can call before invoking handlers. No public route, framework adapter, header parser, provider SDK, or token verifier was introduced.
