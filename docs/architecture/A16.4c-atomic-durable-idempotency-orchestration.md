## Executive Summary

A16.4c implements the Infrastructure-owned transaction boundary required before public mutation idempotency can be wired into host handlers.

The new `PostgresPortfolioWorkspaceIdempotentMutationOrchestrator` coordinates:

1. durable idempotency reservation;
2. transaction-scoped `PortfolioExecutionRepository` use;
3. aggregate mutation/save through existing Application use cases;
4. A16.4a replay payload completion;
5. PostgreSQL commit or rollback.

Domain remains idempotency-free. Application owns semantic contracts only. Infrastructure owns PostgreSQL transactions and durable idempotency records. Presentation/Host remains responsible for raw external key receipt, hashing, request fingerprinting, authorization, and replay response mapping.

## Transaction Boundary

The transaction boundary is Infrastructure-owned and Portfolio Workspace-specific. The orchestrator uses Drizzle's PostgreSQL transaction callback and constructs both:

- `PostgresPortfolioWorkspaceIdempotencyStore`;
- `PostgresPortfolioExecutionRepository`;

against the same transaction-bound database object.

No Pool, PoolClient, Drizzle transaction, schema, repository internals, or SQL handles cross into Domain or Application.

## Transaction-Scoped Repository Strategy

The existing PostgreSQL repository and idempotency store now accept either the normal Drizzle database or the transaction-bound Drizzle database. This is an Infrastructure-local constructor compatibility change only.

Application Services continue to receive only the Application-owned `PortfolioExecutionRepository` port. They do not inspect, increment, or persist idempotency state.

## Durable Record

The durable idempotency record stores:

- scope hash;
- record version;
- operation;
- authorization resource reference;
- resource identity;
- idempotency key hash;
- request fingerprint algorithm/value;
- status;
- original command ID;
- original correlation ID;
- replay contract version;
- replay response payload;
- created, updated, completed, and expiry timestamps.

Raw idempotency keys are not accepted by the Infrastructure persistence contract and are not stored.

## State Semantics

Durable states remain minimal:

- `reserved`;
- `succeeded`.

Reservation outcomes:

- new identity: first execution is reserved;
- completed same fingerprint: replay is available;
- reserved same fingerprint: in-progress;
- same identity with different fingerprint: fingerprint mismatch.

No retry loop, cleanup worker, expiry sweeper, or additional terminal failure state was introduced.

## Replay Persistence

The replay payload now matches the A16.4a semantic contract:

- `replayContractVersion`;
- `responsePayload`.

Infrastructure stores the payload opaquely and does not reinterpret presentation semantics, HTTP status, facts, aggregate state, repository revisions, or framework responses.

## Representative Mutation Proof

Initialize Portfolio Execution is the representative mutation because it exercises aggregate creation, duplicate identity conflict, durable save, replay persistence, and rollback.

The live integration suite now covers:

- first initialization commits reservation, aggregate, and replay;
- duplicate same key/fingerprint replays without a second mutation;
- different fingerprint returns mismatch without mutation;
- mutation failure rolls back reservation;
- replay-completion failure rolls back aggregate save;
- duplicate aggregate creation rolls back reservation;
- concurrent same-key requests produce one aggregate mutation at most.

## All-Nine Mutation Expansion

The orchestrator is operation-agnostic but typed by Portfolio Workspace idempotency identity. The current slice proves the pattern with initialization. Wiring all nine mutation handlers through the orchestrator remains a host/presentation integration task.

Get Portfolio Execution remains outside idempotency management.

## Optimistic Concurrency

Repository optimistic concurrency remains unchanged. If the transaction-scoped repository returns a save failure such as duplicate identity or stale revision, the orchestrator rolls back the idempotency reservation and returns the original typed failure. It does not reload, replay, retry, or translate the failure into a Domain error.

## Reservation Races

Correctness is provided by PostgreSQL uniqueness plus transaction semantics, not process-local locks. The live suite exercises concurrent same-scope reservations and verifies only one first execution wins.

## Rollback Guarantees

Rollback is forced through an internal sentinel only after a first reservation has been acquired and the aggregate mutation or replay completion fails. The sentinel is caught at the orchestrator boundary and converted back into the original safe `Result`.

Expected outcomes:

- reservation without aggregate mutation: rolled back;
- aggregate save without replay completion: rolled back;
- completion persistence failure: rolled back;
- optimistic create conflict: reservation rolled back;
- unexpected storage failure: safe persistence error returned.

## Error Contract

The orchestrator returns typed mutation failures unchanged or `PortfolioWorkspaceIdempotencyPersistenceError` for infrastructure persistence failures. It does not expose SQLSTATE, table names, SQL, Pool, Drizzle, credentials, stack traces, HTTP status codes, or presentation framework objects.

## Privacy

The durable idempotency implementation persists only hashed idempotency key identity and pseudonymous authorization/resource identifiers. It does not persist raw idempotency keys, tokens, sessions, cookies, raw request objects, actor provider claims, Domain facts, aggregate payloads, or command contexts in the idempotency record.

The aggregate payload continues to persist command context actor reference as intentional audit provenance; that is distinct from idempotency identity.

## Runtime Impact

Runtime composition is unchanged. The orchestrator is exported from Infrastructure for future host composition, but the current `PortfolioWorkspaceRuntime` does not expose transaction handles, repository internals, Drizzle, Pool, or idempotency store internals.

## Presentation Impact

A16.4c does not implement public mutation endpoints or raw-key handling. Public mutation exposure remains blocked until public routes use the A15/A16 contracts to hash the raw idempotency key, create the canonical request fingerprint, authorize the principal, and execute the mutation through this atomic orchestrator.

## CI Impact

## Remaining Public-Exposure Blockers
