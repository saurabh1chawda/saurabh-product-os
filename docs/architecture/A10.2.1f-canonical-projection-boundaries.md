# A10.2.1f - Canonical Projection Boundaries

## 1. Purpose

This document defines the canonical Portfolio Workspace domain projection boundary before projection implementation begins.

It applies to the Portfolio Workspace bounded context after completion of:

- Canonical domain vocabulary.
- Supporting entities.
- `PortfolioExecution` behavioral aggregate.
- Immutable Portfolio Workspace domain facts.
- Pure Portfolio Workspace domain policies.

This document does not define TypeScript interfaces, classes, storage, serialization formats, CQRS infrastructure, repositories, UI models, or implementation code.

## 2. Definition

A Domain Projection is a derived read model representing domain information from an alternative read-oriented perspective.

A Portfolio Workspace projection may answer questions such as:

- What is the current execution summary?
- What work remains visible from aggregate state?
- Which artifact candidates exist for review?
- Which accepted artifacts exist under work items?
- What completion view can be derived without mutating the aggregate?

A Domain Projection is not:

- A source of truth.
- An aggregate.
- A policy.
- A workflow.
- Persistence.
- A UI model.
- An integration model.
- An application service.

Projections MUST remain bounded-context-specific unless future architecture review authorizes shared projection abstractions.

## 3. Responsibilities

Projections may:

- Derive information from aggregate read-only state.
- Summarize aggregate state.
- Present read-oriented domain views.
- Compose immutable values.
- Recompute deterministic views from the same inputs.
- Expose query-friendly domain information without exposing mutable aggregate internals.

Projections MUST NOT:

- Own invariants.
- Make business decisions.
- Mutate aggregates.
- Mutate entities.
- Evaluate policies.
- Publish facts.
- Publish events.
- Coordinate workflows.
- Perform retries.
- Schedule work.
- Call repositories.
- Call APIs.
- Own application authorization.
- Own UI behavior.
- Invoke AI providers.

Projection creation is read-oriented derivation. Domain state changes remain owned by `PortfolioExecution` operations.

## 4. Dependencies

Allowed dependencies:

- `PortfolioExecution` read-only state.
- Supporting entity read-only state.
- Immutable Portfolio Workspace domain facts.
- Portfolio Workspace value objects.
- Immutable policy decisions only when supplied as prior read inputs by the application layer.

Forbidden dependencies:

- Repositories.
- Ports.
- Persistence.
- Messaging.
- HTTP.
- UI.
- AI.
- External services.
- Browser automation.
- Workflow engines.
- Application services.
- Infrastructure adapters.
- Policy execution.

Projections must not introduce reverse dependencies into Planning packages.

## 5. Projection Lifetime

Domain projections are:

- Immutable.
- Deterministically recomputable.
- Stateless after creation.
- Dependency-free except for approved domain model imports.

Identical projection inputs MUST produce identical projection outputs.

Projections must not retain mutable caches, store refresh state, track subscribers, persist themselves, or become the authoritative execution record.

## 6. Projection Taxonomy

Portfolio Workspace may define the following projection categories when implementation evidence justifies them.

| Category | Purpose | Inputs | Must not own |
| --- | --- | --- | --- |
| Execution summary | Summarize execution identity, source plan reference, lifecycle, and aggregate-owned counts. | Aggregate read-only state; value objects. | Execution lifecycle policy, terminal outcome derivation, persistence. |
| Work-item summary | Present work-item identity and lifecycle from a read-oriented perspective. | Aggregate read-only state; `PortfolioWorkItem` state. | Work-item mutation, completion eligibility, dependency enforcement. |
| Candidate summary | Present artifact candidates requiring or reflecting human review. | Candidate state; relevant facts. | Acceptance workflow, AI validation, artifact creation. |
| Artifact summary | Present accepted artifacts owned by work items. | Accepted-artifact state; relevant facts. | Artifact storage, rendering, publishing, supersession behavior. |
| Completion view | Derive completion-oriented read information from aggregate state and facts. | Aggregate read-only state; work-item state; relevant facts. | Completion decisions, policy evaluation, execution completion mutation. |

Projection categories for feedback, terminal outcome, application orchestration, persistence-backed queries, or cross-workspace views remain deferred until the corresponding behavior is implemented or canonicalized.

## 7. Relationship Matrix

The dependency direction is strictly one-way:

```text
Aggregate
    ↓
Facts
    ↓
Policies
    ↓
Projections
    ↓
Application Layer
```

This ordering does not mean projections execute policies. It means each lower layer may consume stable outputs from layers above it only through explicit inputs.

| Component | Relationship to projections | Boundary |
| --- | --- | --- |
| `PortfolioExecution` aggregate | Owns mutable execution state and domain operations. Projections may read aggregate snapshots or read-only accessors. | Projections must not mutate or replace aggregate state. |
| Supporting entities | Provide read-only entity state through aggregate ownership. | Projections must not coordinate entities independently. |
| Domain facts | Provide immutable evidence of completed domain decisions. | Projections may summarize facts but must not publish, retain queues, or define integration events. |
| Domain policies | Produce immutable decisions when explicitly invoked elsewhere. | Projections must not execute policies or make policy decisions. |
| Application layer | May request projections and pass them to presentation or orchestration code. | Application services own orchestration; projections remain domain read models. |
| Future persistence | May store or rebuild projections through infrastructure if later authorized. | Persistence must not become the source of domain truth. |
| Future UI | May render projection data. | UI mapping and presentation metadata are outside domain projections. |

## 8. Examples

Conceptual examples only:

- An execution summary projection derives counts of work items by lifecycle from `PortfolioExecution`.
- A candidate summary projection lists registered, accepted, and rejected candidates without performing acceptance.
- An artifact summary projection lists accepted artifact references without loading artifact content.
- A completion view derives whether all work items are resolved without completing the execution.

These examples do not authorize query services, read repositories, UI view models, projection persistence, handlers, or CQRS infrastructure.

## 9. Deferred Work

The following remain explicitly deferred:

- Projection persistence.
- Query services.
- Read repositories.
- CQRS infrastructure.
- Projection caching.
- UI mapping.
- Cross-workspace projections.
- Search indexing.
- Projection refresh orchestration.
- Repository-backed projection rebuild.
- Application-level projection services.
- Shared projection abstractions.

These are not gaps in A10.2.2 projection implementation. They require future implementation evidence and architecture review.

## 10. Final Decision

Portfolio Workspace domain projections may be implemented as deterministic, immutable, package-local read models.

They may derive read-oriented views from aggregate read-only state, supporting entities, immutable domain facts, and explicitly supplied immutable policy decisions.

They must not own invariants, decisions, mutation, orchestration, persistence, messaging, UI, AI, or external side effects.
