## Executive Summary

The current dirty worktree contains a coherent A16.4 authorization implementation for the currently exposed Portfolio Workspace API host flows: Initialize Portfolio Execution and Get Portfolio Execution by ID.

The implementation introduces a durable `PortfolioWorkspaceAuthorizationResourceReference`, stores it with `PortfolioExecution`, derives initialization ownership from the trusted presentation principal, and resolves the stored resource before allowing get-by-ID access.

The design is broadly aligned with the approved A15/A16 architecture: authentication remains outside Portfolio Workspace, authorization remains host/presentation-owned, Domain stores only a provider-neutral resource reference, and Application exposes a narrow resolver through the existing repository port.

The implementation is not yet a complete production authorization closure for every runtime-exposed operation. The API host exposes only initialize and get handlers. Direct runtime access to begin, activate, complete, cancel, accept, reject, complete execution, and cancel execution remains unwrapped by authorization. That is acceptable for the current internal host surface, but it is a blocker before those operations are exposed through any production transport.

## Principal Model

The authenticated principal is represented by `PortfolioWorkspacePresentationPrincipal`.

Fields:

- `principalId`
- `principalType`
- `authenticationProvider`
- optional display name

The API host receives this as already-authenticated trusted input. Portfolio Workspace does not parse tokens, sessions, cookies, provider claims, or provider SDK objects.

## Ownership Model

Access-control ownership is represented by `PortfolioWorkspaceAuthorizationResourceReference`.

For production authorization, the default policy derives the reference from:

- principal type;
- authentication provider;
- principal ID;
- SHA-256 hash over provider plus principal ID.

The stored value has the shape:

```text
portfolio-workspace:principal:<principal-type>:<sha256>
```

The raw principal ID and provider are not stored in the authorization resource. The aggregate payload still persists initialization `commandContext.actorReference` for internal audit provenance under the existing command-context contract.

A16.2m reconciled this privacy boundary against live PostgreSQL evidence. Final manual validation reports repository 17/17, runtime 9/9, and API host 9/9 with no failed or skipped live tests after the host assertion was narrowed to `aggregate_payload.authorizationResourceReference`.

## Ownership Persistence Model

`PortfolioExecution` now carries `authorizationResourceReference` as immutable aggregate state.

The PostgreSQL physical table is unchanged. The authorization resource is stored inside the JSONB aggregate payload, and `PORTFOLIO_EXECUTION_RECORD_VERSION` is raised to `2`.

Version-1 records are intentionally rejected because they cannot prove trusted ownership. A future production migration/backfill would be required for any real existing durable data.

## Authorization Policy Boundary

Authorization remains in `apps/api`, outside Domain and Application.

The current concrete policy is `PortfolioWorkspaceProductionAuthorization`.

It:

- returns a trusted authorization resource for initialization;
- ignores ownership-shaped request input;
- resolves the durable resource for get-by-ID;
- compares the stored resource to the trusted principal-derived resource;
- denies mismatches with safe forbidden errors;
- gives service principals no implicit bypass.

## Runtime Composition Assessment

`PortfolioWorkspaceRuntime` now exposes `resolvePortfolioExecutionAuthorizationResource`, composed with the same shared `PortfolioExecutionRepository` as the other services.

This supports API host authorization without exposing repositories, Drizzle, Pool, revisions, persistence records, or aggregate internals to handlers.

Runtime still exposes all application services directly. Hosts that call those services directly must enforce authorization before invocation.

## API and Presentation Boundary Assessment

The API host composes production authorization by default when no explicit test authorization is injected. This replaces the previous fail-fast requirement for an explicit authorization dependency.

This is not an allow-all fallback because the default policy resolves durable ownership and denies mismatches.

Presentation mappers receive the trusted authorization resource from the authorization boundary, not from request JSON.

## Domain Boundary Assessment

The Domain now stores access-control resource identity as immutable aggregate scope.

This is an access-control ownership value, not provider authentication, roles, permissions, sessions, or policy logic. The Domain still does not decide whether a caller is authorized.

The choice is architecturally acceptable because the aggregate must carry durable execution ownership for future access decisions and persistence recreation.

## Application Boundary Assessment

Application remains repository-port owned and technology-neutral.

The new resolver service loads one aggregate and returns only:

- execution ID;
- authorization resource reference;
- optional correlation ID.

It does not return the aggregate, revision, facts, projections, repository, or infrastructure data.

## Security Findings

### Finding 1 - Runtime Direct-Service Bypass Risk

- Severity: Required before exposing more operations
- Issue: Runtime services remain directly callable without authorization guards.
- Assessment: Acceptable for internal composition only if hosts never expose runtime services directly.
- Required action: Every future handler/route/worker must authorize before invoking a runtime service, or use an authorized facade.

### Finding 2 - Public Forbidden-vs-Not-Found Policy Deferred

- Severity: Required before public endpoints
- Issue: Current internal get returns 403 for existing unauthorized and 404 for missing.
- Assessment: Safe for internal host; public API may require enumeration-resistant 404.
- Required action: Decide and test public route privacy semantics before public exposure.

### Finding 3 - Existing Durable Version-1 Data Unsupported

- Severity: Required before production deployment over existing data
- Issue: Version-1 records lack authorization resources.
- Assessment: Correctly fail-closed.
- Required action: Create a trusted backfill/migration plan if any real durable rows exist.

### Finding 4 - Provider Authentication Still Deferred

- Severity: Blocking public production
- Issue: No real provider authentication adapter exists.
- Assessment: A16.4 authorization assumes trusted principals.
- Required action: Implement provider authentication before public traffic.

## Migration Assessment

No physical SQL migration is required because the payload lives in JSONB.

The durable record version change from `1` to `2` is intentional. Version-1 records are unsupported unless a future trusted migration assigns authorization resources.

No migration metadata isolation changes are part of A16.4.

## Backward Compatibility

Intentional breaking changes:

- Domain constructor and initialization now require `authorizationResourceReference`.
- Durable record version changes to `2`.
- Version-1 durable records are rejected.

Non-breaking API behavior:

- Presentation responses and projections do not expose the authorization resource.
- Existing initialize/get response shapes remain safe.

Potential integration impact:

- Any host constructing `PortfolioWorkspaceApiHost` without authorization now receives the default production policy, not construction failure.
- Tests or internal hosts that require custom policy can still inject one.
