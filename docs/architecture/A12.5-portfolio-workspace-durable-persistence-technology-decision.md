## 2. Purpose

This document selects the durable persistence technology for the first Portfolio Workspace `PortfolioExecutionRepository` adapter.

It does not implement schemas, migrations, ORM models, repository adapters, mapper code, connection configuration, transaction code, concurrency code, deployment configuration, APIs, or UI.

The selected technology must conform to A12.1 through A12.4. The Portfolio Workspace architecture is not reshaped to match a storage tool.

## 3. Current Architecture and Workload

Current confirmed architecture:

- `PortfolioExecution` is the aggregate and persistence boundary.
- `PortfolioExecutionRepository` is owned by `@career-companion/portfolio-workspace-application`.
- A12.2 repository contract tests exist as reusable adapter tests.
- A12.3 in-memory adapter exists in `@career-companion/infrastructure-memory`.
- The in-memory adapter uses explicit mapping and safe rehydration through public domain constructors.
- A12.4 defines durable mapping requirements.
- No durable database, ORM, query builder, or document SDK is currently installed for Portfolio Workspace.

Workload shape:

- Access is primarily load-by-`ExecutionId` and save-one-aggregate.
- One repository load retrieves one `PortfolioExecution`.
- One repository save persists one aggregate consistency boundary.
- Work items, candidates, and accepted artifacts are owned collections.
- Current query needs do not justify a read-model store.
- Initial write concurrency is expected to be low or moderate, but lost updates are unacceptable.
- Aggregate size is bounded by portfolio execution scope, but may grow with candidate/artifact metadata.

## 4. Assumptions

Conservative assumptions:

- The first durable adapter optimizes for correctness, testability, and architectural clarity.
- The deployment target can provide a managed PostgreSQL-compatible database.
- Local development can use a containerized or otherwise disposable PostgreSQL instance.
- Analytical/reporting queries are future projection concerns, not first-adapter requirements.
- Artifact content storage is not part of this adapter unless already represented as canonical aggregate scalar data.

Unproven assumptions:

- Final production hosting provider.
- Expected number of concurrent users.
- Aggregate count and average aggregate payload size.
- Long-term reporting needs.
- Audit/fact persistence requirements.

## 5. Decision Criteria

Scoring uses qualitative ratings:

- High: strongly satisfies the criterion with low architectural friction.
- Medium: satisfies the criterion with trade-offs or additional discipline.
- Low: weak fit, significant risk, or requires extra architecture.
- Reject: conflicts with current architecture for the first durable adapter.

Criteria:

- Aggregate atomicity.

- Record versioning and migrations.
- Local development.
- Testability.

## 8. Relational Versus Document Analysis

One serialized aggregate document or JSON column:

- Best matches aggregate snapshot persistence.
- Simplifies atomic replacement.
- Keeps child collections inside the aggregate boundary.
- Reduces early schema churn.
- Limits direct queryability over child concepts.

Normalized relational tables:

- Improves future queryability.
- Increases mapper complexity.
- Requires multi-table transactions.
- Risks treating supporting entities as independent persistence roots.
- Premature for current load-by-ExecutionId repository contract.

Hybrid relational record plus JSON aggregate payload:

- Provides a relational identity, record version, revision, and operational columns.
- Stores canonical aggregate state as one JSONB payload.
- Supports one-row atomic replacement and compare-and-swap.
- Allows future selective indexes without making projections source of truth.
- Best satisfies A12.4 for the first durable adapter.

Native document database document:

- Fits object shape.
- Supports single-document atomicity.
- Adds a new operational database category not otherwise present.
- Has weaker repository fit than PostgreSQL for future relational/reporting needs.

Decision: use the hybrid relational record plus JSONB aggregate payload.

## 9. Storage Engine Decision

Selected storage engine: PostgreSQL.

Rationale:

- Mature transaction and concurrency model.
- Supports one-row aggregate persistence.
- Supports explicit optimistic concurrency through a revision column.
- Supports JSONB payloads with valid JSON storage and future indexing options.
- Strong managed-hosting availability.
- Strong backup, restore, monitoring, and migration ecosystem.
- Does not require domain classes to become persistence models.

SQLite is not selected for production because initial concurrency requirements include lost-update prevention in a multi-user durable environment.

MongoDB is not selected because current repository needs are satisfied by PostgreSQL while preserving future relational options and avoiding a second database category.

Filesystem/JSON is rejected for durable production use.

## 10. Access-Layer Decision

Selected access layer: Drizzle with `node-postgres`.

Rationale:

- Drizzle supports PostgreSQL while keeping mapping explicit and infrastructure-owned.
- Drizzle migrations can generate and apply SQL migration files under version control.
- It avoids requiring decorators or persistence annotations on domain classes.
- It is lighter than a full ORM for one aggregate repository.
- It allows direct SQL-level optimistic concurrency patterns where needed.

Native `pg` is deferred because it would require more custom migration and schema-management decisions.

Prisma is deferred because its generated model/client approach is more than the first aggregate adapter needs and may encourage persistence-shaped records to become application-facing models.

## 11. Aggregate Representation Decision

Initial durable record representation:

- One table for PortfolioExecution aggregate snapshots.
- `execution_id` as the durable primary lookup key.
- `record_version` as explicit persistence record version.
- `revision` as optimistic concurrency metadata.
- JSONB aggregate payload containing canonical aggregate state.
- Optional infrastructure timestamps if required by A12.6/A12.7.

The JSONB payload is not a public API and is not the domain `toJSON()` contract by itself. It is an adapter-owned persistence record whose mapper may use domain serialization as input.

No separate durable tables are selected for work items, candidates, or accepted artifacts in the first adapter.

## 12. Atomicity Decision

Atomic save strategy:

- Persist one aggregate snapshot with one row-level insert or update.
- Replace the aggregate payload atomically with revision advancement.
- On update, require the expected current revision to match.
- Treat failed compare-and-swap as an infrastructure concurrency conflict.

Partial writes are prevented by single-row replacement. If future schema changes normalize child records, multi-table transaction architecture must be revisited.

## 13. Optimistic Concurrency Decision

Selected mechanism: integer revision column.

Rules:

- Revision is infrastructure metadata.
- Revision is not a domain lifecycle value.
- Revision is not added to `PortfolioExecution`.
- Save must include expected revision semantics before the adapter is production-capable.
- Stale saves fail deterministically.
- Technical conflicts do not become Portfolio Workspace domain errors.
- Automatic retries must not blindly repeat domain operations.

A12.6 must define how expected revision is carried at the repository/infrastructure boundary because the current `PortfolioExecutionRepository.save(execution)` port has no revision parameter.

## 14. Record Versioning Decision

Selected strategy:

- Store explicit `record_version`.
- Start the first durable record shape at version `1` during the durable mapper/schema slice.
- Treat schema migration version, persistence record version, technical revision, and domain lifecycle as separate concepts.
- Reject unsupported future record versions during rehydration.
- Maintain deterministic fixtures for supported, corrupt, and unsupported record shapes.

Do not add record version to the domain aggregate.

## 15. Migration Decision

Selected migration approach: Drizzle migration files, reviewed and version-controlled.

Rules:

- Migrations are infrastructure artifacts.
- Migration files are not created in this task.
- Local and CI migration execution must be defined before durable adapter implementation.
- Production migrations must use an explicit deploy step, not implicit runtime schema drift.
- Migration failure and incompatible schema state must be visible as infrastructure failure.

## 16. Local Development and Test Decision

Local development:

- Use a local PostgreSQL instance, preferably containerized or otherwise disposable.
- Do not require managed cloud databases for ordinary development.

Automated tests:

- Mapper tests can run without a database.
- Repository contract tests for the durable adapter require isolated PostgreSQL state.
- Concurrency tests require at least two repository instances or two logical sessions.
- Migration tests require a disposable schema or database.

SQLite may be used only for unrelated local tooling if already justified elsewhere. It is not the durable PortfolioExecution adapter target.

## 17. Package Boundary Decision

Future durable adapter package placement:

- Preferred: a Portfolio Workspace-specific module under `@career-companion/infrastructure`.
- Acceptable if dependency isolation becomes clearer: a new bounded-context-specific infrastructure package.
- Not selected: `@career-companion/persistence`, because it owns technology-agnostic primitives.
- Not selected: `@career-companion/repositories`, because the PortfolioExecution port is Application-owned.
- Not selected: `@career-companion/portfolio-workspace` or `@career-companion/portfolio-workspace-application`, because concrete storage must remain outside Domain and Application.

Dependency direction remains:

Infrastructure -> Application port -> Domain.

## 18. Security and Operational Assessment

PostgreSQL satisfies the operational posture for the first durable adapter:

- mature backup and restore practices;
- managed-hosting availability;
- access-control support;
- encryption-at-rest support through managed providers;
- secret handling through deployment configuration;
- mature monitoring and failure diagnosis.

The first durable adapter must not store auth sessions, provider SDK objects, UI state, request bodies, prompts, or logs inside aggregate records.

Provider-specific security, retention, backup, and observability settings remain deployment decisions.

## 19. Selected Technology Trade-Offs

Benefits:

- Strong match for aggregate atomicity and optimistic concurrency.
- Explicit mapper remains infrastructure-owned.
- JSONB payload avoids premature normalization.
- Relational envelope supports revision, record version, and future operational columns.
- Drizzle keeps SQL and migrations visible without domain annotations.

Limitations:

- JSONB payload limits ad hoc querying over child collections.
- Future reporting may require projections or read models.
- Local development needs PostgreSQL setup.
- Drizzle and PostgreSQL become infrastructure dependencies.
- Record shape and migration discipline still require A12.6/A12.7 decisions.

Operational burden:

- Manage database connection strings and secrets.
- Run migrations in local, CI, and production.
- Monitor storage availability and concurrency conflicts.
- Maintain corrupt-record and migration fixtures.

## 20. Rejected and Deferred Alternatives

Rejected for first durable adapter:

- Filesystem/JSON persistence: insufficient concurrency, corruption, migration, and operational guarantees.
- SQLite production adapter: useful for embedded/local contexts but weaker fit for multi-user durable concurrency and managed production operations.
- Normalized relational child tables: premature and risks supporting-entity persistence roots.

Deferred:

- Native `pg`: viable but lacks repository-standard migration ergonomics by itself.
- Prisma: viable for broader relational models but heavier than current explicit aggregate mapping needs.
- MongoDB: viable document store but not better than PostgreSQL for current deployment and future relational/reporting flexibility.
- Projection store: deferred until query/read-model requirements justify it.
- Fact/audit store: deferred until audit architecture is approved.

## 21. Inputs Required for A12.6

A12.6 must define technology-independent infrastructure contracts for:

- record not found behavior at adapter boundary;
- mapping failure;
- unsupported record version;
- unavailable storage;
- concurrency conflict;
- transaction failure;
- constraint violation;
- migration incompatibility;
- expected revision handling;
- save result semantics.

A12.6 superseded the original synchronous save assumption. The current `PortfolioExecutionRepository` is asynchronous and revision-aware: loads return a `LoadedPortfolioExecution` envelope, saves accept an optional expected revision, and successful saves return `PortfolioExecutionSaveResult`.

## 25. Final Decision

GO - DURABLE TECHNOLOGY SELECTED.

Selected technology:

- Storage engine: PostgreSQL.
- Access layer: Drizzle with `node-postgres`.
- Representation: relational aggregate record with JSONB aggregate payload.
- Atomicity: one-row aggregate snapshot replacement.
- Optimistic concurrency: integer revision compare-and-swap.
- Record versioning: explicit persistence record version.
- Migrations: Drizzle-generated and reviewed SQL migration files.
- Local/test strategy: disposable PostgreSQL database plus pure mapper tests.
- Package boundary: Portfolio Workspace-specific durable infrastructure module under `@career-companion/infrastructure`, unless A12.6 identifies a stronger bounded-context package need.
