# A15.3 - Portfolio Execution Initialization Architecture

## Executive Summary

PortfolioExecution initialization is a Portfolio Workspace Application use case.

Presentation must not construct or seed `PortfolioExecution`. Infrastructure must not construct new business state except when rehydrating persisted records. Runtime composition must only assemble services and adapters.

The chosen architecture is:

```text
approved planning / approval source
  -> Portfolio Workspace initialization input
  -> InitializePortfolioExecutionApplicationService
  -> PortfolioExecution initialization behavior
  -> PortfolioExecutionRepository.save(new execution)
  -> PortfolioExecutionSummaryProjection + PortfolioExecutionInitializedFact
  -> presentation response mapping
```

Portfolio Workspace owns the aggregate, its lifecycle, and the persisted execution boundary. Planning and approval bounded contexts own the meaning and provenance of `PortfolioPlanReference`, `PlanSnapshotReference`, and `ApprovalReference`. A higher-level orchestration boundary is required when initialization must obtain or validate those upstream references from another context.

Implementation status: A15.3a has implemented the Application-owned initialization use case, domain initialization behavior, and `PortfolioExecutionInitializedFact`. A15.3b has exposed the initialization service through runtime composition. A15.3c has implemented transport-neutral Presentation initialization request, response, and request-to-Application input mapping contracts. HTTP handlers, authorization enforcement, and durable idempotency remain deferred.

Readiness decision: READY WITH CONDITIONS.

## Ownership Analysis

| Concept | Owner | Reason |
| --- | --- | --- |
| `PortfolioExecution` aggregate | Portfolio Workspace Domain | It is the consistency boundary for execution lifecycle, work items, candidates, and accepted artifacts. |
| Aggregate initialization use case | Portfolio Workspace Application | Application coordinates one use case: construct through domain behavior, save through repository port, return result. |
| `PortfolioPlanReference` | Portfolio planning/approval source owns meaning; Portfolio Workspace owns immutable reference copy | Workspace must not embed the full plan or derive planning meaning. |
| `PlanSnapshotReference` | Portfolio planning/source snapshot boundary owns generation and meaning; Workspace owns immutable reference copy | Snapshot creation and compatibility are upstream concerns. |
| `ApprovalReference` | Approval boundary owns approval decision/provenance; Workspace owns immutable reference copy | Workspace requires approval provenance but does not run approval workflow. |
| Initial work items | Source planning/orchestration owns derivation; Portfolio Workspace owns copied execution entities after initialization | Once initialized, work items are aggregate-owned supporting entities. |
| Initial candidates | Source planning/orchestration owns derivation; Portfolio Workspace owns copied execution candidates after initialization | Once initialized, candidate acceptance/rejection is aggregate behavior. |
| Transaction | Portfolio Workspace Application | It owns the conceptual create transaction around aggregate construction and repository save. |
| Persistence revision | Repository/infrastructure boundary | Revision is not Domain state. |
| Presentation mapping | `apps/api` presentation boundary | Presentation may parse external input and construct command context but must not construct aggregate state. |

## Cross-Context Analysis

Portfolio Workspace should not reach directly into Planning or Approval repositories during initialization unless a future architecture defines explicit Application ports for that purpose.

The clean boundary is a trusted initialization input containing already-approved references and initial owned item descriptions. The provenance of those values is outside Portfolio Workspace:

- a Portfolio Planner or approval context creates or selects the approved plan;
- a snapshot boundary freezes the approved plan meaning;
- an approval boundary supplies approval provenance;
- an orchestration boundary decides when those values are trusted enough to initialize an execution.

Portfolio Workspace then decides whether the aggregate can be initialized from those values and persists the new aggregate.

This means two layers may be required:

- `InitializePortfolioExecutionApplicationService` inside Portfolio Workspace Application;
- a future higher-level orchestration service if the host must coordinate Planning, Approval, and Portfolio Workspace in one external workflow.

The higher-level orchestration service must not replace the Portfolio Workspace initialization use case.

## Aggregate Construction Review

Current `PortfolioExecution` constructor accepts:

- `ExecutionId`;
- `PortfolioPlanReference`;
- `PlanSnapshotReference`;
- `ApprovalReference`;
- `PortfolioExecutionCommandContext`;
- `PortfolioExecutionLifecycle`;
- optional `PortfolioWorkItem[]`;
- optional `ArtifactCandidate[]`;
- optional `AcceptedArtifact[]`.

It validates reference/value-object instances, validates lifecycle vocabulary, and enforces duplicate detection by registering supplied owned collections. It can therefore support safe rehydration and current tests.

However, direct constructor use is not a complete initialization behavior because:

- it does not express the business decision `InitializePortfolioExecution`;
- it accepts arbitrary lifecycle values, including non-initial states;
- it can accept accepted artifacts at construction time, which is required for rehydration but not for new initialization;
- it does not produce `PortfolioExecutionInitializedFact`;
- it does not distinguish creation from persistence rehydration;
- it does not define initialization-specific invariants such as "new executions start Initialized" or "accepted artifacts are empty at initialization."

Implemented direction:

- retain the constructor for public-constructor rehydration and test fixtures unless a separate factory/rehydration architecture replaces it;
- add an intention-revealing domain initialization behavior;
- ensure initialization creates lifecycle `Initialized`;
- allow initial work items and candidates only if supplied by trusted Application/orchestration input;
- do not allow initial accepted artifacts for new initialization.

## Repository Review

The current `PortfolioExecutionRepository` port exposes:

```text
loadByExecutionId(executionId) -> LoadedPortfolioExecution | undefined
save(execution, expectedRevision?) -> Result<PortfolioExecutionSaveResult, save failure>
```

A12.6 established create semantics:

- absent aggregate creation uses `save(execution, undefined)`;
- duplicate identity creation must fail explicitly;
- successful creation returns initial persisted revision;
- revision remains outside the Domain aggregate.

No repository contract change is required for initialization.

The initialization Application Service must:

- not load first merely as a duplicate check unless needed for user-facing error clarity;
- save the new aggregate with creation semantics;
- allow `PortfolioExecutionAlreadyExistsError` to propagate through the existing repository failure boundary;
- not convert duplicate creation into a Domain lifecycle error;
- not expose the returned revision in the Application Result unless a future consumer need is approved.

## Fact Review

A10.2.1d already identifies:

- command: `InitializePortfolioExecution`;
- deferred fact: `PortfolioExecutionInitializedFact`.

Initialization is a meaningful business outcome that has already occurred. It should therefore produce one immutable Domain fact.

Recommended fact payload:

- `ExecutionId`;
- `PortfolioPlanReference`;
- `PlanSnapshotReference`;
- `ApprovalReference`;
- `PortfolioExecutionCommandContext`.

Evaluate whether initial work-item and candidate identifiers should be included. Default recommendation: omit full collections from the fact unless traceability requirements prove a concrete need. The aggregate/projection can expose initialized state, and facts should remain compact canonical outcomes rather than snapshots.

The fact must not contain:

- repository revision;
- persistence metadata;
- presentation principal;
- HTTP/auth/session metadata;
- full plan or snapshot payload;
- projections;
- transport DTOs.

The aggregate must not retain pending facts.

## Projection Review

Initialization should return a `PortfolioExecutionSummaryProjection` derived from the initialized aggregate after successful save.

The summary should reflect:

- lifecycle `Initialized`;
- initialized work-item summaries, if any;
- initialized candidate summaries, if any;
- zero accepted artifacts for new initialization;
- the initialization fact type if the existing projection fact list supports it.

The Application Result should include:

- summary projection;
- `PortfolioExecutionInitializedFact`;
- `correlationId` derived from the fact command context.

Returning only identifiers would under-serve the presentation boundary because the first endpoint needs enough state to render or confirm the initialized execution without violating repository access boundaries. Returning the aggregate remains forbidden.

## Application Service Review

`InitializePortfolioExecutionApplicationService` belongs in `packages/portfolio-workspace-application`.

It should be use-case-specific and should not introduce a generic Application framework.

Responsibilities:

- receive immutable `InitializePortfolioExecutionInput`;
- invoke domain initialization behavior;
- save through `PortfolioExecutionRepository` using creation semantics;
- derive `PortfolioExecutionSummaryProjection`;
- return immutable `InitializePortfolioExecutionResult`;
- propagate Domain and repository failures through existing `Result` conventions.

It must not:

- load Planning or Approval repositories directly unless future ports are explicitly approved;
- derive plan snapshots;
- approve plans;
- construct references from untrusted presentation payloads;
- duplicate aggregate duplicate checks;
- publish facts;
- expose repository revision;
- call Infrastructure directly.

Potential input fields:

- `ExecutionId`;
- `PortfolioPlanReference`;
- `PlanSnapshotReference`;
- `ApprovalReference`;
- `PortfolioExecutionCommandContext`;
- initial `PortfolioWorkItem` collection or a narrow immutable initialization item contract that the Application maps to domain entities;
- initial `ArtifactCandidate` collection or a narrow immutable initialization candidate contract that the Application maps to domain entities.

Preferred implementation detail for later review: avoid passing already-constructed aggregate instances into the input.

## Presentation Responsibilities

Presentation may:

- parse external request shape;
- authenticate actor through host/provider code;
- create trusted `PortfolioExecutionCommandContext` using A15.2;
- parse external identifier strings through Domain constructors where approved;
- map success and failures into presentation responses.

Presentation must not:

- construct `PortfolioExecution`;
- construct `PortfolioWorkItem` or `ArtifactCandidate` from arbitrary public request payload unless a future trusted initialization contract approves it;
- invent `PortfolioPlanReference`, `PlanSnapshotReference`, or `ApprovalReference`;
- validate plan approval;
- access repositories or runtime internals;
- call Infrastructure adapters;
- serialize Application Results directly as public responses.

Before a public initialization endpoint exists, the source of plan/snapshot/approval references and authorization must be defined.

## Runtime Responsibilities

The A14 runtime should eventually compose `InitializePortfolioExecutionApplicationService` alongside the existing services.

Runtime may:

- construct the service with the existing `PostgresPortfolioExecutionRepository`;
- expose the service as a named runtime property;
- preserve disposal and readiness behavior.

Runtime must not:

- read or derive initialization input;
- construct aggregates;
- call Planning/Approval services;
- run initialization on startup;
- add repository adapters;
- add service lookup or DI frameworks.

No runtime contract change is required until the initialization service exists.

## Alternative Designs Considered

### Alternative A: Presentation constructs `PortfolioExecution`

Rejected.

This violates A15: presentation is an outer adapter and must not seed aggregates or own business creation.

### Alternative B: Infrastructure repository creates missing aggregate on first command

Rejected.

This would hide a business decision inside persistence and would make load/save semantics ambiguous.

### Alternative C: Begin Execution creates the aggregate if missing

Rejected.

Beginning execution and initializing execution are separate business decisions. `beginExecution()` currently moves an initialized execution to active and returns `PortfolioExecutionStartedFact`.

### Alternative D: Higher-level orchestration creates the aggregate directly

Rejected as the only creation path.

Orchestration may gather trusted references, but Portfolio Workspace still needs its own initialization use case and domain initialization behavior.

### Alternative E: Application service uses current constructor directly

Conditionally acceptable only as a temporary implementation detail, but not the preferred architecture.

The constructor is too broad for new initialization because it supports rehydration and arbitrary lifecycle input. A future implementation should add intention-revealing domain initialization behavior.

## Chosen Architecture

Chosen architecture:

1. Portfolio Workspace owns `InitializePortfolioExecutionApplicationService`.
2. A future domain initialization behavior creates a new `PortfolioExecution` in lifecycle `Initialized`.
3. Initialization returns `PortfolioExecutionInitializedFact`.
4. Application saves the new aggregate with repository creation semantics.
5. Application returns an immutable result containing the initialized summary projection, the initialization fact, and fact-derived correlation ID.
6. Presentation only maps trusted request/principal/context into Application input and maps the result/error outward.
7. Cross-context orchestration is required only when the system must obtain or validate plan/snapshot/approval references from Planning/Approval contexts.

## Required Domain Changes

Implemented in A15.3a:

- add an intention-revealing initialization behavior for new aggregate creation;
- constrain new initialization lifecycle to `Initialized`;
- ensure initial accepted artifacts are not allowed during new initialization;
- produce `PortfolioExecutionInitializedFact`;
- update fact union and projection fact handling;

Still deferred:

- reconcile `ApprovalReference` documentation and implementation shape if the initialization contract requires structured approval fields.

No new aggregate root is required.

## Required Application Changes

Implemented in A15.3a:

- add initialization input/result/service/error alias;
- use existing `PortfolioExecutionRepository.save(execution, undefined)` creation semantics;
- return summary projection and initialization fact;
- propagate duplicate creation as `PortfolioExecutionAlreadyExistsError`;
- keep repository revision internal.

Still deferred:

- update runtime-facing composition.

No repository port change is required.

## Required Presentation Changes

Implemented in A15.3c:

- added presentation initialization request/response contracts;
- use A15.2 command-context factory output as the trusted operation context;
- map invalid identifiers/references safely;
- map `PortfolioExecutionAlreadyExistsError` to conflict;
- avoid constructing the aggregate or supporting entities from untrusted payload outside approved mapping.

Public endpoint exposure still requires authorization and idempotency decisions.

## Required Runtime Changes

Implemented in A15.3b:

- compose `InitializePortfolioExecutionApplicationService` in A14 runtime;
- expose it as a named service;
- share the same PostgreSQL-backed `PortfolioExecutionRepository` used by the behavioral services;
- preserve runtime disposal/readiness behavior;
- validate the live runtime workflow through initialization rather than direct repository seeding;
- do not add in-memory fallback, handlers, or DI.

## Recommended Implementation Sequence

1. Add domain initialization behavior and `PortfolioExecutionInitializedFact`.
2. Add focused domain tests for successful initialization, invalid references, duplicate initial work items/candidates, no accepted artifacts, deterministic serialization, fact immutability, and constructor-vs-initialization separation.
3. Add `InitializePortfolioExecutionInput`, result, error alias, and Application Service.
4. Add Application tests for creation semantics, duplicate identity conflict, result shape, fact-derived correlation, no repository revision exposure, and no aggregate leakage.
5. Update runtime composition to expose the initialization service. Complete in A15.3b.
6. Add presentation initialization contracts only after the Application use case and runtime exposure exist. Complete in A15.3c.
7. Define cross-context orchestration/source-reference contract before public endpoint exposure.
8. Define authorization and idempotency before public mutation endpoint exposure.
