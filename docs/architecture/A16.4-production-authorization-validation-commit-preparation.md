## Staged Authorization Scope

The staged index contains 64 files. The staged changes introduce a persisted Portfolio Workspace authorization resource reference, make initialization accept trusted ownership from the presentation authorization boundary, expose an Application resolver for persisted ownership, and compose production authorization in the API host.

The staged set includes Domain, Application, Infrastructure-memory, Infrastructure persistence/runtime, API/internal host, tests, and A16.4 authorization documentation. It does not stage idempotency, SQL migration files, dependency changes, lockfile changes, CI changes, telemetry, deployment, or auth-provider integration.

## Security Model

Initialization ownership is derived from an already trusted presentation principal. Request-body ownership-shaped fields are ignored by the production path and cannot override the trusted principal-derived resource reference.

Read authorization resolves the persisted PortfolioExecution authorization resource through the runtime-exposed Application resolver, compares it to the trusted principal-derived resource reference, and denies mismatches before execution data is returned.

The principal-derived resource reference uses SHA-256 pseudonymization over authentication provider and principal identifier. This is pseudonymization, not encryption. It avoids persisting raw principal IDs or provider-local subject values in the authorization resource reference.

## Record-Version Compatibility

`PORTFOLIO_EXECUTION_RECORD_VERSION` advances to `2` because the durable aggregate payload now requires `authorizationResourceReference`. Version 1 records do not prove trusted authorization ownership and are intentionally rejected as unsupported rather than being inferred or upgraded silently.

This is fail-closed for legacy/unowned persisted state. Existing version 1 data requires an explicit migration/backfill policy before production rollout if such records exist. No SQL schema migration is required for the aggregate payload shape because the durable representation uses a JSONB payload and explicit record-version validation.

## Fail-Closed Findings

- Missing execution returns the existing safe not-found presentation error.
- Resolver failures prevent authorization from allowing access.
- Mismatched users, different providers, and service principals without ownership are denied.
- Malformed stored authorization resources fail during mapping instead of allowing access.
- Version 1 records are unsupported and fail closed.
- Runtime-not-ready behavior remains unavailable rather than permissive.
- No production allow-all fallback is staged.

## Not-Found Versus Forbidden Policy

Current internal API behavior distinguishes missing executions from existing executions owned by another principal:

- missing execution returns not-found;
- existing execution with mismatched ownership returns forbidden.

This is acceptable for the current internal API handler scope. Before public exposure, the public endpoint threat model should decide whether unauthorized execution IDs must be masked as not-found to reduce enumeration risk.

## Privacy Findings

Safe responses do not expose raw principal IDs, authentication-provider subjects, SQL metadata, repository revision, Domain aggregate internals, runtime/database objects, or stored authorization references unnecessarily.

Persisted `commandContext.actorReference` remains audit provenance. Persisted `authorizationResourceReference` is the pseudonymous authorization resource used for ownership decisions.

The authorization resource derivation includes stable namespace, principal type, authentication provider, and principal identifier in the hashed input. The stored value is domain-shaped as `portfolio-workspace:principal:<principalType>:<sha256>`.

## Deployment Conditions

Version 1 PortfolioExecution records cannot prove trusted ownership and are intentionally unsupported by the version 2 mapper. Repository evidence does not prove whether any production Portfolio Workspace database contains version 1 rows. If such rows exist, deployment requires an explicit migration or backfill policy before rollout.
