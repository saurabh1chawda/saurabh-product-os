## Objective

A16.3e implements the smallest production-oriented concrete verification
boundary required to make the A16.3d generic OIDC/JWT adapter usable by a future
host. It verifies JWT signatures through a mature JOSE implementation, resolves
keys through a trusted JWKS URI, maps verified claims into the A16.3d verifier
port, and preserves the existing trusted-principal mapping.

It does not expose Portfolio Workspace publicly, add middleware, extract
Authorization headers, choose a commercial identity provider, change
authorization or idempotency, or modify Domain/Application/Infrastructure.

## Existing A16.3d Boundary

A16.3d owns Portfolio Workspace authentication policy:

- expected issuer;
- accepted audiences;
- allowed algorithms;
- subject requirements;
- expiry/not-before policy;
- clock tolerance;
- user/service principal mapping;
- display-name mapping;
- trusted principal construction.

A16.3e implements a concrete verifier for the existing
`PortfolioWorkspaceJwtVerifier` port. It returns credential-free verified claims
only after JOSE verifies the JWT signature.

## Dependency Decision

A16.3e adds `jose` to `@career-companion/api`.

Reason:

- JWT signature verification and JWK/JWKS handling are security-sensitive;
- custom RSA/ECDSA, ASN.1, JWK conversion, and signature-validation code would
  be inappropriate;
- `jose` is provider-neutral and does not couple the repository to Auth0,
  Okta, Clerk, Cognito, Firebase, Supabase, or another provider SDK.

No general authentication framework was added.

## Concrete Verifier Design

`PortfolioWorkspaceJoseJwtVerifier` implements `PortfolioWorkspaceJwtVerifier`.

Responsibilities:

- decode and validate the protected JWT header;
- require a non-empty `kid`;
- reject algorithms outside the caller's allowed list before verification;
- verify the JWT through `jose.jwtVerify`;
- resolve keys through a configured JWKS source or a test-only injected key
  resolver;
- map verified payload and protected header into
  `PortfolioWorkspaceVerifiedJwtClaims`;
- map JOSE/key/network failures into safe authentication errors.

The verifier does not construct trusted principals and does not perform
authorization.

## Cryptographic Trust Boundary

Cryptographic verification happens before claims can become
`PortfolioWorkspaceVerifiedJwtClaims`. The token is not decoded and trusted
without signature verification.

The verifier uses the mature JOSE implementation for parsing, signature
verification, and JWK/JWKS key material handling. The repository does not
implement custom crypto primitives.

## JWKS Ownership

JWKS configuration is explicit and trusted:

- JWKS URI is supplied by host-owned configuration;
- JWT claims never select the network destination;
- JWKS URI must be HTTPS;
- credentials in JWKS URLs are rejected;
- URL fragments are rejected;
- malformed URLs are rejected.

OIDC discovery is deferred. The verifier does not derive discovery or JWKS
endpoints from untrusted token content.

## Key Cache and Rotation Behavior

`PortfolioWorkspaceJoseJwtVerifierConfiguration` includes bounded cache and
cooldown settings used by JOSE remote JWKS resolution:

- request timeout;
- cache max age;
- unknown-key cooldown duration.

The cache is process-local and verifier-owned. Signing keys are never persisted
to Portfolio Workspace storage. Unknown keys fail safely and may become
available after JWKS refresh according to JOSE cache behavior.

No distributed key cache is introduced.

## SSRF and Network Safety

The verifier prevents token-controlled SSRF by requiring the JWKS endpoint to
come from trusted configuration. It rejects non-HTTPS JWKS URIs, credentialed
URLs, fragments, malformed URLs, empty values, and unsafe control characters.

Network response bodies and lower-level provider details are not exposed through
safe authentication errors.

## Configuration Ownership

Two immutable configuration contracts now exist:

- `PortfolioWorkspaceOidcJwtAuthenticationConfiguration` for Portfolio
  Workspace authentication policy;
- `PortfolioWorkspaceJoseJwtVerifierConfiguration` for concrete JOSE/JWKS
  verification mechanics.

Environment loading remains host-owned. Authentication code does not read
`process.env`.

## Host Composition Boundary

`createPortfolioWorkspaceOidcJwtAuthenticationAdapter` composes:

```text
generic authentication configuration
  + JOSE verifier configuration
  -> PortfolioWorkspaceJoseJwtVerifier
  -> PortfolioWorkspaceOidcJwtAuthenticationAdapter
```

This is a construction boundary only. It does not create HTTP routes, parse
headers, run middleware, or alter existing internal handler trust assumptions.

## Policy Versus Verification Ownership

The verifier performs cryptographic verification and header/key safety checks.
The A16.3d adapter remains the authoritative Portfolio Workspace policy layer.

There is limited intentional overlap for algorithm handling:

- the verifier rejects disallowed algorithms before verification to prevent
  algorithm-confusion risk;
- the A16.3d adapter also validates the verified algorithm as part of the
  provider-neutral policy contract.

Issuer, audience, subject, expiry, not-before, display-name, and principal-type
semantics remain owned by the A16.3d adapter.

## Error Mapping

Concrete verifier failures map to existing safe authentication reasons:

- malformed token/header -> `credential-malformed`;
- missing `kid`, invalid signature, claim-shape failure -> `verification-failed`;
- disallowed algorithm -> `algorithm-rejected`;
- JOSE/JWKS unavailable, timeout, invalid JWKS, no matching key, multiple keys,
  unexpected verifier failure -> `verifier-unavailable`;
- JOSE expiry detection -> `credential-expired`.

Safe errors do not include raw token, JWT payload, signing key material, JWKS
response body, URL credentials, stack traces, or sensitive provider details.

## Privacy Posture

Bearer credentials remain redacted in serialization. Verified claims are not
stored in trusted principals beyond approved identity fields. Raw JWTs, signing
keys, JWKS payloads, and claim sets are not persisted by Portfolio Workspace and
are not included in safe presentation errors.

## Tests

Database-free API tests cover:

- successful signed user JWT verification;
- successful signed service JWT verification through explicit claim strategy;
- correct key selection;
- malformed token;
- invalid signature;
- missing `kid`;
- unknown `kid`;
- disallowed algorithm;
- key-resolution failure;
- invalid configuration;
- HTTPS/JWKS URL safety;
- host adapter composition;
- token redaction and safe failure serialization;
- source-boundary purity.

Tests use locally generated key pairs and JOSE-signed JWTs. They do not depend
on a real identity provider or external network.

Production-facing public exposure remains blocked until a host route layer
extracts credentials, constructs the configured adapter, authenticates callers,
then invokes authorization and idempotency in the approved order.

strict bearer credential, authenticates through this adapter boundary, and hands
only a trusted `PortfolioWorkspacePresentationPrincipal` to the existing API
host/internal-handler flow.
