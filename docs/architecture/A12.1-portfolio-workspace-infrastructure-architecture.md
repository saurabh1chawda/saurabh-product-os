## 2. Purpose

Infrastructure provides technical capability behind Application Layer ports.

Infrastructure is replaceable. Domain and Application behavior MUST remain independent of database, storage, framework, vendor, transport, deployment, and operational technology choices.

This document defines how infrastructure may implement Portfolio Workspace application ports without allowing technical concerns to enter the Domain or Application layers.

This document does not define TypeScript interfaces, repository adapter code, persistence mappings, schemas, migrations, controllers, DTOs, messaging, background jobs, UI, or AI integration.

## 3. Architectural Position

Compile-time dependency direction:

```text
Presentation
    -> Application
        -> Domain

Infrastructure
    -> Application ports
        -> Domain types where required
```

These arrows represent compile-time knowledge, not runtime control flow.

Application services may receive infrastructure adapter instances through composition. They MUST depend only on Application-owned port contracts. Domain packages MUST NOT depend on Application or Infrastructure packages.

## 4. Infrastructure Responsibilities

Infrastructure may own:

- Repository adapter implementations.
- Aggregate persistence mapping.
- Serialization and deserialization mechanics.
- Database or storage access.
- Optimistic concurrency implementation.
- Technical transaction implementation.
- Connection management.
- Schema migrations.
- Operational logging and metrics.
- Technical retry behavior where explicitly safe and idempotent.
- Integration with external systems behind approved ports.

Infrastructure MUST NOT own:

- Business invariants.
- Lifecycle decisions.
- Acceptance rules.
- Completion rules.
- Candidate or work-item coordination.
- Domain fact creation.
- Policy decisions.
- Application-result construction.
- Application-use-case sequencing.
- Presentation formatting.

## 5. Port and Adapter Boundary

`PortfolioExecutionRepository` is owned by the Application Layer package.

Infrastructure implements the port. The existing port exposes:

- `loadByExecutionId`
- `save`

The port crosses these concepts:

- `ExecutionId`
- `PortfolioExecution`
- `PortfolioExecutionRevision`
- `LoadedPortfolioExecution`
- `PortfolioExecutionSaveResult`
- technology-neutral repository failure contracts

`PortfolioExecution` is the persistence and consistency boundary because it owns mutable execution state and aggregate-owned collections. Supporting entities MUST NOT receive independent repositories in the Portfolio Workspace pilot.

Adapters MUST be substitutable behind the same Application-owned port. An adapter MUST NOT widen the port contract unilaterally. If a future adapter needs additional semantics, the Application Layer port must be reviewed explicitly.

Domain packages MUST NOT import ports or adapters.

## 6. Repository Adapter Contract

Loading must:

- Locate one `PortfolioExecution` aggregate by `ExecutionId`.
- Return not-found distinctly from technical failure.
- Rehydrate a valid aggregate.
- Preserve identifiers, planning references, approval reference, command context, lifecycle, work items, candidates, accepted artifacts, and all persisted canonical state.
- Avoid invoking business operations during rehydration.
- Avoid emitting domain facts.
- Avoid re-running policies.
- Reject corrupt or unsupported persisted representations.

Saving must:

- Persist `PortfolioExecution` as one consistency boundary.
- Preserve atomic aggregate state.
- Preserve canonical identifiers and lifecycle strings exactly.
- Avoid persisting Application Results as sources of truth.
- Avoid deriving business facts.
- Avoid mutating the aggregate.
- Avoid saving projections as canonical domain state.

## 7. Persistence Mapping Boundary

The following concepts are distinct:

| Concept | Owner | Rule |
| --- | --- | --- |
| Domain Model | Domain package | Business truth and invariants. |
| Persistence Record | Infrastructure adapter | Storage-oriented representation. |
| Database Schema | Infrastructure adapter | Technology-specific storage shape. |
| Mapping Adapter | Infrastructure adapter | Deterministic translation between storage and domain. |

Domain entities are not ORM entities. Persistence records are infrastructure types. Database column names MUST NOT enter domain vocabulary. Mapping must be explicit and deterministic.

Transport DTOs and persistence records are distinct concepts.

## 8. Aggregate Rehydration

Rehydration must reconstruct an existing `PortfolioExecution` without replaying application use cases.

Rehydration MUST NOT call:

- `beginExecution`
- `activateWorkItem`
- `completeWorkItem`
- `cancelWorkItem`
- `acceptCandidate`
- `rejectCandidate`
- `completeExecution`
- `cancelExecution`

Rehydration MUST NOT emit facts, re-run policies, infer missing state silently, or mutate persisted meaning.

Current aggregate status: IMPLEMENTED.

The current constructor reconstructs aggregate state with supplied collections and lifecycle. Structural collection registration is constructor/internal behavior and is covered by adapter contract tests to ensure rehydration does not replay business operations or emit facts.

No aggregate change is authorized by this document.

## 9. Serialization Ownership

Domain `toJSON()` output, Application Result serialization, persistence serialization, and transport serialization are separate.

Domain `toJSON()` is a deterministic domain representation. It MUST NOT automatically become the database schema.

Infrastructure may use domain serialization as an input signal, but persistence mapping remains an explicit adapter responsibility. This architecture does not standardize one universal JSON representation.

## 10. Identity Mapping

Infrastructure MUST preserve canonical string values exactly for:

- `ExecutionId`
- `WorkItemId`
- `CandidateId`
- `AcceptedArtifactId`
- `PortfolioPlanReference`
- `PlanSnapshotReference`
- `ApprovalReference`
- `PortfolioExecutionCommandContext`

Rules:

- Do not regenerate identities on load.
- Do not derive accepted-artifact identity from candidate identity.
- Do not normalize identifiers beyond approved value-object behavior.
- Do not introduce database-generated domain IDs.
- Preserve aggregate initialization command context fields exactly when persisted.
- Preserve operation command context exactly when persisting domain facts or audit records in a future explicitly approved audit boundary.

Persistence-generated IDs are prohibited unless a future domain decision explicitly authorizes them.

## 11. Lifecycle Mapping

Infrastructure MUST store exact canonical serialized strings for:

- `PortfolioExecutionLifecycle`
- `PortfolioWorkItemLifecycle`
- `ArtifactCandidateLifecycle`

Rules:

- Reject unsupported values.
- Do not use database numeric enum ordering as canonical meaning.
- Do not add persistence-only lifecycle values.
- Do not map lifecycle values through UI labels.
- `AcceptedArtifact` remains lifecycle-free.

## 12. Domain Fact Boundary

Domain facts are produced by `PortfolioExecution` behavior and returned to the Application Layer.

Domain facts are not:

- Event streams.
- Integration events.
- Transport messages.
- Projection updates.
- Repository adapter outputs.

Repository adapters MUST NOT create, publish, replay, or require domain facts to rehydrate aggregates.

If operational audit persistence is later required, it must be designed separately and MUST NOT implicitly convert the Portfolio Workspace architecture into event sourcing.

## 13. Projection Boundary

Projections are derived read models. They are not canonical aggregate persistence state.

Infrastructure MUST NOT use projections to rehydrate `PortfolioExecution`.

Projection materialization, read repositories, CQRS infrastructure, caching, and search indexing remain deferred until a separate architecture decision authorizes them.

## 14. Transaction Boundary

Application Services own the conceptual use-case transaction:

```text
load aggregate
    -> invoke domain decision
    -> save aggregate
    -> derive projection
    -> return result
```

Infrastructure owns technical transaction implementation.

For current single-aggregate use cases, load and save should participate in one technical transaction where required by the selected technology. Application services MUST remain unaware of database transaction objects.

Transaction APIs MUST NOT enter Domain models, Application Results, or Presentation DTOs.

Transaction port decision: DEFERRED. No Unit of Work abstraction is justified until a concrete adapter demonstrates the need.

## 15. Concurrency Boundary

Concurrency classification: IMPLEMENTED FOR CURRENT REPOSITORY CONTRACT.

Current use cases mutate one `PortfolioExecution` aggregate. A durable adapter must protect against lost updates when two callers load and save the same execution concurrently.

Expected durable-adapter concerns:

- Concurrent modification of one `PortfolioExecution`.
- Stale write rejection.
- Revision or version tokens at the persistence layer.
- Conflict reporting as infrastructure/application failure.

Do not introduce a domain version field automatically. Technical concurrency failures are not domain lifecycle decisions.

The current in-memory and PostgreSQL adapters implement revision-aware repository semantics. Revision remains persistence metadata and does not enter domain state.

## 16. Error Boundary

Domain errors:

- Aggregate invariant failures.
- Business-decision rejections.
- Lifecycle and identity invariant failures.

Application errors:

- `PortfolioExecutionNotFoundError`.
- Use-case boundary failures.

Infrastructure errors:

- Connection failure.
- Timeout.
- Serialization failure.
- Corrupt persisted representation.
- Concurrency conflict.
- Storage unavailable.

Presentation errors:

- HTTP, GraphQL, CLI, or UI-specific mappings.

Repository adapters MUST NOT translate technical failures into domain errors. Infrastructure errors MUST NOT contain HTTP status codes. Presentation mapping remains deferred.

Exact infrastructure error contracts may be defined during adapter architecture.

## 17. Technology-Neutral Selection Criteria

No storage, ORM, database, filesystem, or cloud vendor is selected by this document.

Future durable technology selection must consider:

- Atomic aggregate persistence.
- Deterministic mapping.
- Concurrency support.
- Testability.
- Local development.
- Operational simplicity.
- Migration support.
- Expected data volume.
- Query patterns.
- Portability.
- Security and privacy requirements.

Technology follows architecture requirements, not the reverse.

## 18. Adapter Taxonomy

| Adapter category | Classification | Boundary |
| --- | --- | --- |
| In-memory repository adapter | IMPLEMENTED | Validates port contract without durable storage. |
| Durable repository adapter | IMPLEMENTED | PostgreSQL adapter exists under `@career-companion/infrastructure`; runtime composition remains deferred. |
| Transaction adapter | DEFERRED | Requires concrete adapter evidence. |
| Operational telemetry adapter | OPTIONAL | Technical telemetry only; no business conclusions. |
| Artifact storage adapter | DEFERRED | Only if artifact content storage becomes canonical. |
| Supporting-entity repository adapter | REJECTED | Violates aggregate persistence boundary. |
| Generic repository framework | REJECTED | Not justified by Portfolio Workspace evidence. |

## 19. In-Memory Adapter Boundary

The first repository adapter should normally be an in-memory `PortfolioExecutionRepository` adapter after Application Layer corrections are complete.

Architectural value:

- Validates the port contract.
- Supports deterministic adapter tests.
- Exercises rehydration and save/reload equivalence.
- Avoids premature durable technology selection.

Limitations:

- Non-durable.
- Not production persistence.
- Limited concurrency guarantees.
- Not a substitute for durable adapter architecture.

Existing test fakes inside application tests are not production Infrastructure adapters.

Recommended package boundary: `@career-companion/infrastructure-memory`, using a bounded-context-specific module or path for Portfolio Workspace. This uses the existing in-memory infrastructure package while avoiding a generic repository framework.

## 20. Package Boundary

Existing evidence:

- `@career-companion/infrastructure-memory` is the canonical package for deterministic in-memory implementations.
- `@career-companion/infrastructure` is currently reserved for infrastructure adapter boundaries.
- `@career-companion/persistence` owns generic persistence primitives.
- `@career-companion/repositories` owns earlier repository contracts for existing Foundation-era domains.
- Portfolio Workspace already owns its repository port inside `@career-companion/portfolio-workspace-application`.

Decision:

- In-memory adapter: implemented under `@career-companion/infrastructure-memory` in a Portfolio Workspace bounded-context-specific module.
- Durable adapter: implemented under `@career-companion/infrastructure` in a Portfolio Workspace bounded-context-specific module.

Rules:

- Infrastructure may depend on Application and Domain.
- Application and Domain MUST NOT depend on Infrastructure.
- Do not move `PortfolioExecutionRepository` into a shared repositories package without evidence.
- Do not introduce a generic repository framework.

## 21. Composition Root Boundary

Concrete adapters are connected to Application Services in a future composition root.

Possible composition roots:

- API application.
- Worker.
- CLI.
- Desktop host.
- Dedicated composition package.

The composition root MUST NOT live inside Domain or Application packages.

Dependency-injection frameworks remain deferred. Manual constructor composition is preferred initially.

## 22. Testing Strategy

Future repository adapter contract tests must cover:

- Load existing aggregate.
- Not-found behavior.
- Save and reload equivalence.
- Identity preservation.
- Planning reference preservation.
- Approval reference preservation.
- Command context preservation.
- Execution lifecycle preservation.
- Work-item collection preservation.
- Candidate collection preservation.
- Accepted-artifact preservation.
- Deterministic mapping.
- Rejected corrupt state.
- No domain facts emitted during load.
- No Application Result persistence.

Concurrency tests for durable adapters must cover:

- Stale write rejection.
- No lost update.

Boundary tests must verify:

- Infrastructure depends inward.
- Domain and Application do not depend outward.
- No UI, API, AI, messaging, workflow, or transport concern enters adapters.
- No domain-rule duplication appears in infrastructure.

## 23. Security and Privacy Boundary

Infrastructure owns technical security controls:

- Secure storage.
- Encryption at rest where required.
- Secret handling.
- Least-privilege access.
- Sensitive audit metadata handling.
- Data retention and deletion mechanics.

Security implementation MUST NOT alter domain semantics, lifecycle rules, candidate acceptance, completion eligibility, or fact meaning.

Provider-specific controls remain deferred.

## 24. Observability Boundary

Infrastructure may emit technical telemetry for:

- Load latency.
- Save latency.
- Failure rates.
- Serialization failures.
- Concurrency conflicts.
- Connection health.

Infrastructure MUST NOT reinterpret domain facts, create business conclusions, publish execution outcomes, or replace Application Results.

Domain facts and technical logs remain distinct.

Deferred:

- Event publication.
- Messaging.
- Background jobs.
- Artifact binary or content storage.
- Projection materialization.
- Caching.

Implemented since this decision:

## 26. Implementation Sequence

Historical recommended sequence has been completed through A12.10. The next implementation boundary is runtime composition, not another repository contract correction.

## 27. Final Decision

Portfolio Workspace infrastructure architecture is defined.

Infrastructure MUST implement inward-facing Application ports, keep Domain and Application independent from concrete technology, persist `PortfolioExecution` as the aggregate consistency boundary, map persistence explicitly, avoid fact/event sourcing assumptions, and keep projections and Application Results out of canonical persistence.

Readiness for runtime composition remains conditional on release hygiene, Node 22 validation, and CI/live PostgreSQL gate definition.
