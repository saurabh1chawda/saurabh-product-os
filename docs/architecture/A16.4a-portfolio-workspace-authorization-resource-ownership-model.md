# A16.4a - Portfolio Workspace Authorization Resource Ownership Model

## Executive Summary

A16.4 identified a production authorization blocker: `PortfolioExecution` carried business provenance references but no stable security resource or ownership reference.

A16.4a resolves that model gap with `PortfolioWorkspaceAuthorizationResourceReference`, an immutable provider-neutral Domain value object. Initialization now requires this trusted reference, `PortfolioExecution` persists it as immutable execution scope, and durable records carry it inside the aggregate JSONB payload.

The value does not contain roles, permissions, provider claims, tokens, sessions, HTTP data, tenant provider SDK objects, or policy decisions.

## Current Ownership Gap

Before A16.4a, `PortfolioExecution` stored execution identity, portfolio plan reference, plan snapshot reference, approval reference, initialization command context, lifecycle, and aggregate-owned children.

Those references are provenance and workflow references. None safely identify the security resource that owns an execution.

## Authorization Resource Concept

`PortfolioWorkspaceAuthorizationResourceReference` is the canonical execution ownership/security resource reference.

It is immutable, serializable, value-comparable, provider-neutral, technology-neutral, and bounded. It rejects blank, unsafe, control-character, and whitespace-containing values.

## Package Boundary Decision

The authorization resource reference belongs in `@career-companion/portfolio-workspace` because it is part of initialized aggregate scope that must remain durable and immutable for the lifetime of a `PortfolioExecution`.

Application accepts the value as initialization input. Infrastructure maps it as aggregate payload state. API handlers receive it only from the host-local trusted authorization boundary.

## Domain Model Decision

`PortfolioExecution` now requires `authorizationResourceReference` in both constructor rehydration and `PortfolioExecution.initialize(...)`.

The initialized execution and `PortfolioExecutionInitializedFact` carry the same reference. Later lifecycle operations do not mutate or replace it.

## Trusted Resource Source

The presentation request body does not contain a trusted ownership field.

For internal initialization, `PortfolioWorkspaceInternalAuthorization.authorizeInitialize(...)` returns the trusted `PortfolioWorkspaceAuthorizationResourceReference`. The handler passes that value to the presentation mapper, which creates `InitializePortfolioExecutionInput`.

Client-supplied ownership-shaped request fields are ignored by request construction and cannot become trusted input.

## Persistence Strategy

The PostgreSQL table remains unchanged: `execution_id`, `record_version`, `revision`, and `aggregate_payload`.

The authorization resource reference is stored inside `aggregate_payload`, alongside other aggregate-owned references. No separate column, child table, projection table, or fact table is introduced.

`PORTFOLIO_EXECUTION_RECORD_VERSION` is now `2` because record payload compatibility changed. Existing version-1 records lack the required security resource and must not be silently rehydrated as if ownership were known.

A16.4a.1 explicitly classifies version-1 records as intentionally unsupported unless a future approved migration/backfill can assign trusted authorization resources to known historical records.

## Projection and Presentation Decision

`PortfolioExecutionSummaryProjection` and API presentation responses do not expose the authorization resource reference.

Reason: the reference is security-sensitive authorization metadata, not read-side product state.

## Migration Impact

No SQL migration is required because the physical schema already stores aggregate snapshots in JSONB.

Before deploying over existing durable data, a backfill or migration policy must assign valid authorization resources to existing executions. The current release has no approved production durable data set, so this remains a release condition rather than an immediate migration file.

## Security Boundaries Preserved

A16.4a does not add JWT parsing, OAuth/session/cookie handling, provider authentication, RBAC, permission strings, production policy, public routes, idempotency, retries, telemetry, UI, or AI.

## Backward Compatibility

This is a durable record compatibility change. Version-1 records cannot be safely mapped because ownership would be unknown.

A16.4a.1 confirms version-1 records are intentionally unsupported and version-2 records are canonical. Manual PostgreSQL 17 live validation under Node `v22.23.2` and pnpm `11.9.0` passed after the record-version change:

- repository live suite: 17/17 tests passed;
- runtime live suite: 9/9 tests passed;
- API host live suite: 8/8 tests passed.

## Required Future Work

A16.4b should define production authorization policy, execution resource resolver, initialize resource resolution rules, read/mutation resource resolution, forbidden/not-found privacy behavior, and security tests for cross-resource access.

Provider authentication remains a separate future slice.

## Readiness Decision

COMPLETE WITH RELEASE CONDITIONS.

A16.4a.1 closes the persistence compatibility policy and accepts PostgreSQL 17 live validation. A16.4b may proceed. Broader production release conditions remain: provider authentication, production authorization policy/resource resolver, public route decisions, durable public mutation idempotency, observability, and production database operations.
