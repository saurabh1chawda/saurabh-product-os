# A11.2 - Application Result Boundaries

## 1. Purpose

This document defines the canonical Application Result boundary for Portfolio Workspace before application service implementation begins.

The Domain Model is complete. Application Services have been defined by A11.1. This document establishes the contract between the Application Layer and every future Presentation Layer.

Application Results are the only objects that cross the Application boundary.

This document does not define TypeScript interfaces, classes, JSON schemas, REST payloads, GraphQL types, dependency injection, frameworks, controllers, routes, or implementation code.

## 2. Definition

An Application Result is an immutable representation of the outcome of a single completed application use case.

Application Results are boundary contracts.

They are not:

- Domain objects.
- Aggregates.
- Entities.
- Value objects.
- Policies.
- Projections themselves.
- Transport DTOs.
- Persistence models.
- Repository records.
- Infrastructure adapters.
- Controllers.
- UI models.

An Application Result may contain domain-derived outputs, but it must not become part of the Domain Model.

## 3. Responsibilities

Application Results may contain:

- Domain projections.
- Immutable domain facts.
- Policy decisions, only when intentionally surfaced by the use case.
- Use-case metadata.
- Correlation identifiers.
- Domain errors or application-level rejection information.

Application Results MUST NOT contain:

- Aggregates.
- Mutable entities.
- Repository references.
- Transactions.
- Infrastructure objects.
- ORM models.
- Database connections.
- HTTP request or response objects.
- SDK objects.
- UI state.
- Rendering metadata.
- External service clients.

Application Results summarize completed use-case outcomes. They do not execute work, coordinate retries, invoke policies, mutate domain state, or persist themselves.

When an Application Result contains a domain fact, its `correlationId` MUST be derived from the returned fact's `PortfolioExecutionCommandContext`. Application Results MUST NOT combine a fact produced with one command context and a correlation identifier from another source.

## 4. Ownership

| Layer | Owns | Must not own |
| --- | --- | --- |
| Domain | Business truth, aggregate invariants, entity state, value objects, domain facts, policies, projections. | Use-case orchestration, presentation formatting, persistence implementation. |
| Application | Use-case completion, transaction coordination, result assembly, correlation, returned boundary contract. | Business rules, aggregate internals, transport formatting, infrastructure implementation. |
| Presentation | Formatting and transport-specific transformation. | Domain truth, aggregate reconstruction, lifecycle policy, approval policy. |
| Infrastructure | Persistence and external systems behind ports. | Domain policy, presentation shape, application result semantics. |

Application Results are owned by the Application Layer.

Presentation may consume Application Results. Presentation does not own them.

## 5. Dependency Rules

Allowed dependency direction:

```text
Application Result
    ↓
Domain Projection
    ↓
Immutable Facts
```

Forbidden dependency direction:

```text
Application Result
    ↓
Aggregate

Application Result
    ↓
Infrastructure

Application Result
    ↓
Presentation DTO
```

Rules:

- Aggregates never cross the Application boundary.
- Mutable entities never cross the Application boundary.
- Infrastructure objects never appear inside Application Results.
- Presentation DTOs are derived from Application Results, never the reverse.
- Application Results are never used as persistence records.

## 6. Immutability

Application Results are:

- Immutable.
- Serializable.
- Value-comparable.
- Free of behavior.
- Derived from one completed use case.

Application Results must not expose mutable arrays, mutable objects, callbacks, service references, repository references, transaction handles, or lazily loaded data.

Identical completed use-case outputs should produce identical Application Results.

## 7. Relationship to Presentation

Presentation layers may transform an Application Result into:

- REST DTO.
- GraphQL response.
- CLI output.
- Desktop UI model.
- Mobile UI model.

The transformation is one-way:

```text
Application Result
    ↓
Presentation DTO or View Model
```

Presentation MUST NOT:

- Reconstruct aggregates from Application Results.
- Mutate Application Results.
- Treat Application Results as domain truth.
- Call domain behavior directly through Application Results.
- Add lifecycle or approval policy during formatting.

Presentation may hide, rename, localize, paginate, or format result data for a specific interface. Those transformations do not change the Application Result contract.

## 8. Relationship to Domain

Application Results never become inputs back into the Domain Model.

Future use cases always begin by loading aggregates through Application Layer coordination, not by reusing Application Results.

Allowed:

- Domain operation produces facts.
- Application Service builds projection.
- Application Service assembles Application Result.
- Presentation transforms Application Result.

Forbidden:

- Presentation submits an Application Result back as aggregate state.
- Application Service reconstructs an aggregate from an Application Result.
- Domain behavior consumes an Application Result.
- Application Result becomes a source of lifecycle truth.

Domain facts and projections may appear inside Application Results only as immutable outputs of a completed use case.

## 9. Example Structure

Conceptual examples only:

| Result | Conceptual contents | Must not contain |
| --- | --- | --- |
| `BeginExecutionResult` | Execution summary projection, produced facts, use-case metadata, correlation identifier. | `PortfolioExecution` aggregate, repository, transaction, HTTP response. |
| `CompleteExecutionResult` | Completion fact, execution summary projection, intentionally surfaced policy decision where applicable. | Completion policy implementation, database record, UI status object. |
| `AcceptCandidateResult` | Candidate acceptance fact, candidate summary projection, accepted-artifact summary where applicable, correlation identifier. | Mutable candidate entity, approval workflow, external publishing state. |

These examples do not authorize implementation, TypeScript contracts, JSON schemas, DTO fields, controller payloads, or persistence models.

## 10. Deferred Topics

The following remain explicitly deferred:

- REST.
- GraphQL.
- OpenAPI.
- DTO mapping.
- Serialization format.
- Framework annotations.
- Versioning.
- Backward compatibility.
- CLI output contracts.
- UI view-model contracts.
- Mobile response models.
- Error transport mapping.
- Pagination conventions.
- API authentication and authorization mapping.

These are not Application Result boundary gaps. They require future implementation evidence and architecture review.

## 11. Final Decision

Application Results are immutable Application Layer boundary contracts for completed use cases.

They may contain domain projections, immutable domain facts, intentionally surfaced policy decisions, use-case metadata, and correlation identifiers.

They must never contain aggregates, mutable entities, repositories, transactions, infrastructure objects, presentation DTOs, transport objects, or SDK objects.

Presentation consumes Application Results. Presentation never consumes Aggregates.
