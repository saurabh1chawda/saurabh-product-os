## 2. Purpose

This document defines the canonical persistence mapping boundary for Portfolio Workspace before durable storage technology is selected.

It does not select a database, define a physical schema, introduce migrations, implement repositories, or change the domain model.

The persistence mapper MUST preserve the PortfolioExecution aggregate exactly enough to rehydrate domain behavior through the public domain constructors and value objects. It MUST NOT make persistence records a source of business truth independent of the aggregate.

## 3. Current State Model

PortfolioExecution is the aggregate root and persistence boundary.

The aggregate currently owns:

- ExecutionId
- PortfolioPlanReference
- PlanSnapshotReference
- ApprovalReference
- PortfolioExecutionCommandContext as execution initialization context
- PortfolioExecutionLifecycle
- PortfolioWorkItem collection
- ArtifactCandidate collection
- AcceptedArtifact collection

Supporting entities are aggregate-owned. They MUST NOT be persisted through independent entity repositories.

Behavioral operations receive operation-specific PortfolioExecutionCommandContext values and return immutable domain facts. Those operation contexts are fact payload, not mutable aggregate state.

## 4. Canonical Versus Derived State

| Concept | Classification | Persistence rule |
| --- | --- | --- |
| ExecutionId | Canonical aggregate state | MUST persist. |
| PortfolioPlanReference | Canonical aggregate state | MUST persist exactly as immutable reference data. |
| PlanSnapshotReference | Canonical aggregate state | MUST persist exactly as immutable reference data. |
| ApprovalReference | Canonical aggregate state | MUST persist exactly as immutable provenance data. |
| Aggregate commandContext | Canonical initialization context | MUST persist as execution initialization context. |
| Operation-specific commandContext | Domain fact payload | MUST NOT be persisted as aggregate state unless future audit architecture authorizes fact storage. |
| PortfolioExecutionLifecycle | Canonical aggregate state | MUST persist exact lifecycle string. |
| PortfolioWorkItem collection | Canonical aggregate-owned state | MUST persist inside the aggregate record. |
| ArtifactCandidate collection | Canonical aggregate-owned state | MUST persist inside the aggregate record. |
| AcceptedArtifact collection | Canonical aggregate-owned state | MUST persist inside the aggregate record. |
| Domain facts | Immutable business outcomes | MUST NOT be persisted as aggregate state. Audit persistence is deferred. |
| Domain policies | Pure business reasoning | MUST NOT persist. |
| Domain projections | Derived read models | MUST NOT be source of truth. Projection persistence is deferred. |
| Application results | Application boundary output | MUST NOT persist as aggregate state. |
| Repository implementation details | Infrastructure concern | MUST NOT enter domain records except explicit technical metadata. |
| Record version and revision token | Operational metadata | MAY persist with durable records; MUST remain outside domain behavior. |

## 5. Persistence Record Boundary

A PortfolioExecution persistence record is an infrastructure-owned representation of one aggregate snapshot.

It MAY contain:

- aggregate state required for rehydration;
- explicit record version;
- technical revision token for optimistic concurrency;
- adapter-owned timestamps if required by the selected durable store.

It MUST NOT contain:

- domain projections;
- policy decisions;
- application results;
- HTTP, UI, session, authentication, or provider objects;
- repository handles or transaction objects;
- event bus or messaging metadata;
- AI provider metadata;
- denormalized business rules that compete with the aggregate.

The record is not a public TypeScript domain contract and is not a transport DTO.

## 6. Mapping Direction

The canonical direction is:

PortfolioExecution aggregate -> persistence record -> PortfolioExecution aggregate.

Mapping MUST be explicit and deterministic. Durable adapters MAY use the aggregate's public serialization as mapper input, but MUST NOT treat serialized JSON shape as a substitute for adapter-owned record-versioning and corrupt-state handling.

Rehydration MUST recreate domain value objects and entities rather than bypassing constructors or mutating private state.

## 7. Identifier Mapping

Identifiers MUST be stored as their canonical stable string values:

| Identifier | Stored value | Rehydration |
| --- | --- | --- |
| ExecutionId | nonempty string | ExecutionId.create(...) or existing public constructor/factory convention |
| WorkItemId | nonempty string | WorkItemId.create(...) or existing public constructor/factory convention |
| CandidateId | nonempty string | CandidateId.create(...) or existing public constructor/factory convention |
| AcceptedArtifactId | nonempty string | AcceptedArtifactId.create(...) or existing public constructor/factory convention |

The persistence layer MUST NOT generate identifiers during rehydration.

The persistence layer MUST NOT derive AcceptedArtifactId from CandidateId.

Duplicate identity detection during rehydration MUST fail the record as corrupt or unsupported state. It is not a user-facing domain decision.

## 8. Reference Mapping

References MUST be stored as immutable scalar reference data:

- PortfolioPlanReference: planId, roadmapId, planArtifactReference
- PlanSnapshotReference: snapshotReference
- ApprovalReference: approved immutable provenance fields currently defined by the domain

The persistence layer MUST NOT embed PortfolioPlan, roadmap items, planning artifacts, approval workflows, approver behavior, or planning mutable state.

## 9. Command Context Mapping

PortfolioExecution currently stores one command context as execution initialization context. That context MUST be persisted as canonical aggregate state.

Behavioral facts carry operation-specific PortfolioExecutionCommandContext values supplied to each aggregate operation. Those operation contexts MUST NOT be folded into aggregate persistence unless a future audit-store architecture explicitly persists facts.

Application result correlationId is derived from the returned fact, not from persisted aggregate initialization context.

## 10. Lifecycle Mapping

Lifecycle values MUST be persisted as exact canonical serialized strings:

PortfolioExecutionLifecycle:

- Initialized
- Active
- Completed
- Cancelled

PortfolioWorkItemLifecycle:

- Pending
- Active
- Blocked
- ReadyForReview
- Completed
- Cancelled

ArtifactCandidateLifecycle:

- Registered
- Accepted
- Rejected

AcceptedArtifact has no lifecycle. A durable record MUST NOT introduce AcceptedArtifactLifecycle.

Unknown lifecycle values MUST be rejected during rehydration. The mapper MUST NOT trim, lowercase, alias, or infer lifecycle values.

## 11. Collection Mapping

Aggregate-owned collections MUST be persisted within the PortfolioExecution record:

- workItems
- candidates
- acceptedArtifacts

The persistence layer MUST preserve enough deterministic ordering to round-trip aggregate serialization and repository contract tests.

Collections MUST NOT be persisted through separate public repositories. Physical storage may use normalized tables or documents, but the repository contract remains one aggregate load and one aggregate save.

## 12. Aggregate Atomicity

PortfolioExecution persistence MUST be atomic at the aggregate boundary.

A successful save MUST persist the aggregate identity, references, initialization context, lifecycle, work items, candidates, and accepted artifacts as one consistent aggregate snapshot.

A failed save MUST NOT leave a partially persisted aggregate visible through the repository port.

## 13. Rehydration

Rehydration MUST:

- validate record version support;
- reconstruct identifiers through domain value-object construction;
- reconstruct references and contexts through domain constructors or factories;
- reconstruct lifecycle values through canonical runtime validation where available;
- reconstruct supporting entities;
- construct PortfolioExecution through its public aggregate constructor;
- fail on corrupt, missing, duplicated, or unsupported state.

Rehydration MUST NOT:

- replay facts;
- invoke business operations;
- publish facts;
- evaluate policies;
- calculate projections;
- bypass domain constructors;
- fill missing required state with defaults.

## 14. Record Versioning

Durable records MUST include an explicit record version before the first durable adapter is implemented.

The version identifies the infrastructure record shape, not the domain lifecycle.

Unsupported versions MUST fail rehydration through an infrastructure mapping failure. They MUST NOT be translated into domain errors.

The in-memory adapter may continue using the current public aggregate serialization as its in-process clone representation because it is not durable storage.

## 15. Schema Evolution

Schema evolution belongs to infrastructure architecture and selected durable technology.

Future migrations MUST preserve:

- aggregate identity;
- planning and approval references;
- initialization command context;
- lifecycle strings;
- collection ownership;
- accepted-artifact immutability;
- deterministic rehydration.

Migrations MUST NOT infer missing business state or create accepted artifacts, facts, policies, or projections as a side effect unless a future migration architecture explicitly authorizes the transformation.

## 16. Corrupt and Unsupported State

The mapper MUST treat the following as corrupt or unsupported state:

- missing aggregate identity;
- invalid identifier strings;
- missing required references;
- invalid command context;
- unknown lifecycle strings;
- duplicate work-item identifiers;
- duplicate candidate identifiers;
- duplicate accepted-artifact identifiers;
- accepted-artifact lifecycle fields;
- unsupported record version;
- child rows or documents that cannot be associated with exactly one aggregate snapshot.

Corrupt persisted state is an infrastructure mapping failure, not a domain command rejection.

## 17. Infrastructure Error Boundary

Durable adapter errors MUST remain outside the Portfolio Workspace domain error catalog.

Infrastructure mapping errors may include concepts such as:

- record not found;
- corrupt record;
- unsupported record version;
- concurrency conflict;
- storage unavailable.

These MUST NOT be represented as PortfolioWorkspaceDomainError subtypes.

Application services may surface repository-port failures only through future application/infrastructure error contracts. HTTP status codes and transport concerns remain outside this layer.

## 18. Transaction Mapping

The Application Layer owns the conceptual transaction boundary:

load aggregate -> invoke domain behavior -> save aggregate -> derive projection -> return result.

The durable adapter owns storage-specific transaction mechanics needed to make save atomic.

No domain object, application input, application result, projection, policy, or fact may contain transaction handles.

A shared transaction abstraction remains deferred until a durable adapter proves it is required.

## 19. Optimistic Concurrency

The durable adapter MUST define optimistic concurrency before production durable persistence.

The concurrency token is technical metadata and MUST NOT become domain state.

The repository save contract MUST prevent lost updates. A stale save MUST fail with an infrastructure/application boundary failure, not by silently overwriting another aggregate snapshot.

Blind retry is not authorized by this document.

## 20. Persistence Query Boundary

The current repository boundary is aggregate-oriented:

- load PortfolioExecution by ExecutionId;
- save PortfolioExecution.

Durable persistence MUST NOT introduce query methods for work items, candidates, accepted artifacts, policies, projections, or facts through the aggregate repository.

Read models and query services are deferred projection infrastructure.

## 21. Fact and Audit Boundary

Domain facts are immutable business outcomes returned by aggregate operations.

Aggregate persistence MUST NOT retain pending facts, event queues, or event-sourcing streams.

Audit persistence is a separate future architecture decision. If audit storage is introduced later, operation-specific command contexts belong with the persisted fact/audit record, not with mutable aggregate state.

## 22. Projection Boundary

PortfolioExecutionSummaryProjection and related projections are derived read models.

They MAY be recomputed from a rehydrated aggregate.

They MUST NOT be persisted as the source of truth for aggregate behavior.

Projection persistence, caching, query repositories, and UI mapping remain deferred.

## 23. Security and Privacy Mapping

Persistence records MUST store only canonical domain information and approved infrastructure metadata.

They MUST NOT store:

- authentication sessions;
- access tokens;
- AI prompts or provider outputs beyond approved artifact candidate data;
- UI state;
- request bodies;
- logs embedded in aggregate records;
- external provider objects.

Any future durable technology decision MUST specify encryption, access control, backup, retention, and data-classification requirements for persisted records.

## 24. Observability

Observability belongs outside the domain model.

Durable adapters MAY emit operational metrics or logs for load/save/mapping failures, but those signals MUST NOT alter aggregate state, facts, policies, projections, or application results.

Logs MUST NOT become the persistence record.

## 25. Mapping Test Strategy

Durable mapping tests MUST cover:

- exact aggregate round trip;
- identifier round trip;
- reference round trip;
- initialization command-context round trip;
- lifecycle exact-string round trip;
- collection ordering and encapsulation;
- duplicate identity rejection;
- unknown lifecycle rejection;
- unsupported record-version rejection;
- corrupt missing-field rejection;
- no fact replay;
- no projection persistence;
- no policy evaluation;
- no infrastructure object leakage;
- optimistic concurrency behavior once a durable adapter exists.

The existing repository contract tests from A12.2 remain mandatory for every repository adapter.

## 26. Technology Selection Requirements

A durable storage technology selected in A12.5 MUST support:

- aggregate-level atomic save;
- optimistic concurrency or an equivalent lost-update prevention mechanism;
- deterministic record serialization;
- explicit record versioning;
- rehydration from immutable scalar data;
- migration strategy;
- testable corrupt-record handling;
- package-local adapter implementation;
- no domain dependency on storage SDKs.

The selected technology MUST NOT require domain objects to contain ORM decorators, database IDs, lazy loaders, transaction handles, or persistence annotations.

## 27. Package Boundary

The Portfolio Workspace domain package MUST remain persistence-free.

The Portfolio Workspace application package owns the repository port.

Durable infrastructure belongs in an infrastructure package, not in the domain or application package.

Mapper code, record shapes, versioning, and storage-specific errors MUST remain internal to the durable infrastructure package unless a future architecture document defines public infrastructure contracts.

The in-memory adapter remains test/development infrastructure and MUST NOT become the durable mapping authority.

## 28. Relationship to In-Memory Adapter

The current in-memory adapter is a useful reference implementation for boundary behavior:

- it stores one aggregate snapshot by ExecutionId;
- it clones serialized aggregate state;
- it rehydrates through public domain constructors;
- it does not replay facts;
- it does not persist projections or policies;
- it does not expose supporting-entity repositories.

It is not a durable persistence design.

A durable adapter MUST add explicit record versioning, corrupt-state classification, and optimistic concurrency.

## 29. Required Decisions Before Durable Adapter

Before implementing a durable adapter, the architecture MUST decide:

- durable storage technology;
- physical record shape;
- record version value and versioning policy;
- migration ownership and execution mechanism;
- optimistic concurrency token strategy;
- infrastructure error contract exposed to application services;
- package location for durable adapter;
- test-fixture strategy for corrupt records and concurrency conflicts;
- operational data classification and retention expectations.

## 30. Deferred Topics

Deferred:

- database selection;
- ORM or query-builder selection;
- schema files;
- migrations;
- repository adapter implementation;
- transaction manager implementation;
- unit-of-work abstraction;
- projection persistence;
- audit/fact persistence;
- read repositories;
- query services;
- caching;
- observability implementation;
- deployment configuration;
- backups and retention tooling.

## 31. Recommended Sequence

1. Complete A12.5 Durable Persistence Technology Decision.
2. Define durable record shape, versioning, concurrency, and mapping errors.
3. Implement mapper tests against the selected record shape.
4. Implement the durable PortfolioExecution repository adapter.
5. Run A12.2 repository contract tests against both in-memory and durable adapters.
6. Add application/infrastructure composition only after adapter contracts pass.
