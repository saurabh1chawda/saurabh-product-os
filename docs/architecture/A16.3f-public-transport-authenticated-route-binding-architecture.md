## Executive Summary

A16.3f defines the first public transport authentication boundary for Portfolio Workspace. The current implementation has an internal, framework-neutral API host whose handlers receive an already-trusted `PortfolioWorkspacePresentationPrincipal`. A16.3d and A16.3e added the provider-neutral OIDC/JWT authentication adapter, redacted bearer credential contract, JOSE/JWKS verifier, and host composition boundary, but they intentionally do not parse public transport headers or bind public routes.

The chosen architecture adds a future API-local public route boundary under `apps/api/src/portfolio-workspace/public/`. That boundary will extract credentials from transport headers, authenticate through the existing A16.3d/e adapter, map failures to safe public responses, then hand only a trusted presentation principal to the existing host/internal handler flow.

No production route, middleware, HTTP framework, provider deployment, Domain behavior, Application behavior, Infrastructure behavior, authorization rule, idempotency behavior, or persistence behavior is implemented in this slice.

## Existing Authentication Baseline

The API package now contains a Portfolio Workspace authentication boundary:

- `PortfolioWorkspaceAuthenticationAdapter` authenticates external credentials into credential-free authenticated identity.
- `authenticatePortfolioWorkspacePrincipal(...)` maps authenticated identity into the trusted `PortfolioWorkspacePresentationPrincipal`.
- `PortfolioWorkspaceBearerTokenCredential` redacts token material in JSON and inspection.
- `PortfolioWorkspaceOidcJwtAuthenticationAdapter` validates issuer, audience, algorithm, subject, expiry, not-before, principal type, and display-name claims after verifier success.
- `PortfolioWorkspaceJoseJwtVerifier` verifies JWTs through configured HTTPS JWKS.
- `createPortfolioWorkspaceOidcJwtAuthenticationAdapter(...)` composes the generic adapter and JOSE verifier.

This baseline does not extract `Authorization` headers and does not bind a public route.

## Existing Public Transport Baseline

There is no public Portfolio Workspace HTTP transport implementation yet. `apps/api` contains:

- transport-neutral presentation contracts;
- framework-neutral internal request/response contracts;
- internal initialize and get-by-ID handlers;
- an API host that composes runtime, authorization, command context factory, and internal handlers;
- no Express, Fastify, Next route handler, middleware, server startup, OpenAPI, or public controller.

The current host boundary is intentionally internal: callers must supply a trusted principal.

## Transport Ownership Decision

Public transport owns:

- HTTP method and route matching;
- path parameter extraction;
- request body availability and content-type handling;
- header normalization;
- `Authorization` bearer parsing;
- public status codes;
- safe public response headers;
- `WWW-Authenticate` decisions;
- incoming correlation hint extraction.

Authentication owns:

- credential verification;
- claim validation;
- trusted principal construction.

Authorization owns:

- operation/resource permission decisions after authentication.

Domain, Application, Infrastructure, repositories, runtime composition, and durable mappers own none of the public transport parsing rules.

## Package / Placement Decision

Future implementation should live in:

```text
apps/api/src/portfolio-workspace/public/
```

Expected files:

- `credential-extraction.ts`
- `public-transport.ts`

- `get-portfolio-execution-route.ts`
- `index.ts`

This keeps public transport in the API package, outside Domain/Application/Infrastructure, and separate from the existing internal handler contracts.

## Credential Extraction Contract

The public boundary should introduce a narrow extractor that accepts only host-local transport headers. It should return:

```text
Result<PortfolioWorkspaceBearerTokenCredential, PortfolioWorkspaceAuthenticationError>
```

or an equivalent API-local public authentication failure if an extra transport reason is required.

The extractor must:

- read only the `Authorization` header;
- reject missing credentials as `authentication-required`;
- reject malformed bearer values as `credential-malformed`;
- reject duplicate or ambiguous authorization values;
- reject control characters;
- enforce a bounded raw header length before constructing a bearer credential;
- never serialize or log token material;
- never accept credentials from query parameters, path parameters, body fields, cookies, correlation headers, idempotency keys, or command IDs.

## Bearer Parsing Rules

Recommended bearer parsing rules:

- header name comparison is case-insensitive;
- exactly one `Authorization` header value is accepted;
- the scheme is case-insensitive and must be `Bearer`;
- the value must contain `Bearer` plus one or more spaces followed by a token;
- empty tokens are rejected;
- comma-joined or multi-value credentials are rejected;
- values containing unsafe control characters are rejected;
- oversized header values are rejected before token creation;
- the normalized token must still satisfy `PortfolioWorkspaceBearerTokenCredential` validation.

The existing bearer credential currently tolerates a raw token string or a `Bearer ` prefix. Public transport should be stricter than that low-level credential convenience so accidental non-bearer public schemes do not authenticate.

## Authentication Pipeline

For a matched public Portfolio Workspace route, the required pipeline is:

```text
public transport request
  -> correlation hint normalization
  -> credential extraction
  -> authenticatePortfolioWorkspacePrincipal(...)
  -> trusted PortfolioWorkspacePresentationPrincipal
  -> route/request validation as appropriate
  -> authorization
  -> command-context creation for mutations
  -> existing host/internal handler or equivalent presentation flow
  -> safe public response
```

Public route existence and method matching may happen before authentication. For a matched Portfolio Workspace route, authentication should run before detailed resource or body validation unless a framework requires shallow path parsing first.

## Trusted Principal Handoff

Only `PortfolioWorkspacePresentationPrincipal` may cross from public authentication into the existing handler flow. Raw JWTs, bearer credentials, verified claim sets, JOSE payloads, provider SDK objects, session objects, cookies, request objects, and authorization headers must not be passed to internal handlers, Application Services, Domain objects, command contexts, idempotency scopes, or persistence.

The existing internal handlers already have the correct trust shape: each receives `{ request, principal }`.

## Public Request Context Decision

No broad public request context object should be introduced yet. If a future route needs request metadata, it should use a narrow API-local value that contains only safe, non-secret fields:

- route identifier;
- method;
- normalized correlation ID;
- optional client-facing request ID if later approved.

It must not contain raw headers, credentials, tokens, sessions, database objects, runtime internals, repositories, or provider SDK values.

## Authentication Error Mapping

Authentication failures should map at the public transport layer:

| Authentication reason | Public status | Presentation category |
| --- | ---: | --- |
| `authentication-required` | 401 | unauthenticated |
| `credential-malformed` | 401 | unauthenticated |
| `authentication-invalid` | 401 | unauthenticated |
| `verification-failed` | 401 | unauthenticated |
| `issuer-mismatch` | 401 | unauthenticated |
| `audience-mismatch` | 401 | unauthenticated |
| `algorithm-rejected` | 401 | unauthenticated |
| `subject-missing-or-invalid` | 401 | unauthenticated |
| `credential-expired` | 401 | unauthenticated |
| `credential-not-yet-valid` | 401 | unauthenticated |
| `invalid-authenticated-identity` | 401 | unauthenticated |
| `trusted-principal-mapping-failed` | 401 | unauthenticated |
| `authentication-unavailable` | 503 | unavailable |
| `verifier-unavailable` | 503 | unavailable |
| `invalid-authentication-configuration` | 500 | internal |

The response body should reuse safe presentation error JSON and must not include raw authentication errors, tokens, claim payloads, provider stack traces, JWKS URLs, SQL, or runtime internals.

## WWW-Authenticate Decision

Public `401` authentication failures should include a minimal challenge:

```text
WWW-Authenticate: Bearer
```

Do not include `error`, `error_description`, issuer, audience, provider names, realm, or claim-level details until a specific public API disclosure policy approves them.

Do not emit `WWW-Authenticate` for authorization denials, not-found results, invalid request bodies, persistence unavailability, or internal failures.

## Correlation Flow

Correlation is not authentication and not idempotency. It remains an untrusted transport hint.

The public route should normalize or generate the correlation ID before authentication so authentication failures still return correlated safe errors. The response should include the existing `x-correlation-id` header and body correlation field where the presentation contract already includes it.

## Authentication / Authorization Ordering

The approved order is:

```text
match public route
  -> normalize correlation
  -> extract credential
  -> authenticate
  -> create trusted principal
  -> validate route/request data
  -> authorize
  -> create command context for mutations
  -> apply durable idempotency for public mutations
  -> invoke internal handler/application flow
```

Authorization must never run from raw credential claims. It must receive a trusted `PortfolioWorkspacePresentationPrincipal`.

## First Public Route Recommendation

The first public Portfolio Workspace route should be authenticated get-by-ID:

```text
GET /v1/portfolio-workspace/executions/{executionId}
```

Reason:

- the query path already exists through `runtime.getPortfolioExecution`;
- it does not mutate state;
- it does not require durable idempotency;
- authorization can reuse the existing resource resolver and production authorization boundary;
- it exercises the public authentication and trusted-principal handoff without introducing public retry semantics.

## Initialize Public Exposure Decision

Initialize Portfolio Execution must remain internal-only for now.

Public initialization should wait until:

- public route authentication is implemented and validated;
- production authorization is bound to public callers;
- public durable idempotency is bound to the mutation route;
- public retry and abuse-control policy is approved;
- operational logging/metrics/redaction policy is approved;
- live route validation proves duplicate/replay behavior.

## Route Versioning Decision

Public transport routes should use a transport version prefix such as `/v1`. The route version is separate from presentation response `version: "v1"` and separate from durable record versions, migration versions, command IDs, correlation IDs, and idempotency keys.

Do not infer future list/search/version behavior from the first get-by-ID route.

## Host Composition Design

The host should construct:

- one `PortfolioWorkspaceApiHost`;
- one configured `PortfolioWorkspaceOidcJwtAuthenticationAdapter`;
- one public credential extractor;
- one public route handler per public route.

Handlers may hold references to the API host and authentication adapter. They must not construct runtimes, repositories, database pools, Drizzle clients, Domain aggregates, command facts, or Application Services directly.

## Authentication Component Lifetime

The authentication adapter and JOSE verifier should be host-scoped and reused across requests. They are stateless except for the verifier's bounded JWKS cache. Do not create a verifier per request.

The API host owns runtime disposal. Public route handlers must not dispose the runtime or authentication adapter per request.

## JWKS Cache / Network Lifetime

The JOSE verifier owns process-local JWKS cache behavior through its approved configuration. JWKS retrieval failure should produce a safe `verifier-unavailable` authentication failure for the request.

Do not add active JWKS health checks, background refresh loops, distributed key caches, or startup network validation in the first public transport binding unless a later deployment architecture explicitly requires them.

## Public Response Contract

Success responses should use the existing presentation response body. For the first public get-by-ID route:

- status `200`;
- safe presentation get response;
- `x-correlation-id` header;
- no facts;
- no command context;
- no repository revision;
- no aggregate or entity object;
- no principal echo by default.

Error responses should use existing safe presentation error JSON plus the host-local status mapping.

## Security / Privacy Assessment

The architecture preserves current privacy boundaries:

- raw bearer tokens are never serialized;
- verified claims are not persisted;
- trusted principals contain only approved identity fields;
- authorization resource references remain separate from authentication credentials;
- command context actor references are audit provenance, not credential storage;
- public errors do not disclose provider internals;
- database and repository internals remain hidden from the API route.

The public route boundary must be covered by source-scan tests proving no token, claim, Pool, Drizzle, repository, Domain aggregate, or provider SDK leaks through responses or handler contracts.

## Rate-Limit Boundary

Rate limiting is not implemented in this slice. The first public route implementation should leave a clear host-local seam for later rate limiting.

Recommended future order:

- cheap generic pre-auth abuse controls before JWT verification;
- authenticated principal/resource-aware controls after authentication;
- mutation idempotency after authorization for public mutations.

Do not place rate limiting in Domain, Application, Infrastructure, repository adapters, or presentation mappers.

## Observability Boundary

Observability is deferred, but the route design should permit safe signals:

- correlation ID;
- route ID;
- method;
- outcome category;
- public status;
- authentication failure reason category;
- latency;
- authenticated principal type after successful authentication if approved.

Never log authorization headers, bearer tokens, raw claims, JWKS responses, database URLs, SQL, command contexts, idempotency payloads, or application result facts by default.

## Framework Decision

Stay framework-neutral for the next implementation slice. The repository currently has no Portfolio Workspace Express, Fastify, Next route, or server startup convention. Introducing a framework during credential extraction would widen the change unnecessarily.

The first implementation should define a small API-local public transport contract that can later be adapted to a concrete framework.

## Test Strategy

Future tests should cover:

- missing authorization header;
- malformed bearer header;
- duplicate authorization headers;
- control-character and oversized header rejection;
- successful authentication into trusted principal;
- expired/invalid/audience/issuer/algorithm failures;
- verifier-unavailable failure;
- minimal `WWW-Authenticate` on `401`;
- no challenge on `403`, `404`, `500`, or `503`;
- correlation preservation on success and failure;
- get-by-ID route calls the existing host/internal flow with only trusted principal;
- no public initialize route;
- no token, raw claims, Pool, Drizzle, repository, aggregate, service locator, command bus, Express, Fastify, or Next coupling in the public boundary.

Live provider/JWKS validation remains a later step once deployment-specific configuration exists.

## Recommended Implementation Sequence

1. Implement API-local public credential extraction and authentication response mapping.
2. Add a framework-neutral authenticated public get-by-ID route wrapper.
3. Route the wrapper into `PortfolioWorkspaceApiHost.getPortfolioExecutionHandler`.
4. Add database-free tests for credential parsing, authentication ordering, authorization ordering, and response mapping.
5. Add a concrete host/framework adapter only when the repository chooses a public server boundary.
6. Run live public-route validation against PostgreSQL and a controlled test JWKS/provider configuration.
7. Consider public initialize only after durable idempotency, authorization, rate/abuse controls, and retry semantics are publicly bound and validated.

## Implementation Reconciliation

A16.3g implements step one of this sequence: strict framework-neutral public
bearer extraction, correlation establishment before authentication,
authentication through the existing adapter boundary, safe 401/503/500 public
authentication failure mapping, minimal `WWW-Authenticate: Bearer` behavior for
401 failures, and trusted-principal handoff. It intentionally does not implement
the public get-by-ID route wrapper, public initialize, authorization,
idempotency, runtime service invocation, or concrete framework binding.

A16.3h implements the framework-neutral public get-by-ID binding. It composes
the A16.3g public authentication boundary with the existing internal get handler,
passes only the trusted principal into the authorization/get flow, and returns
the existing safe versioned Get presentation response. It still does not add a
concrete HTTP route/framework binding, public initialize, public mutation
idempotency route binding, or provider deployment.
