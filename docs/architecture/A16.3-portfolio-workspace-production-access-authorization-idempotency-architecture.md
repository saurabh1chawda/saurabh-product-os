## 2. Scope

A16.3 defines the production-access boundary for Portfolio Workspace public read access through the concrete API host.

This document distinguishes:

- authentication from authorization;
- trusted-principal resolution from raw credentials;
- public GET from internal mutation paths;
- committed durable idempotency infrastructure from unimplemented public mutation exposure;
- concrete HTTP-host capability from deployment/bootstrap concerns;
- verified behavior from deferred hardening.

## 3. Architecture Decision

Portfolio Workspace keeps security and transport concerns outside Domain and Application.

The approved shape is:

1. Public transport extracts bearer credentials.
2. The API authentication adapter validates credentials.
3. The adapter resolves a trusted `PortfolioWorkspacePresentationPrincipal`.
4. The API host performs operation/resource authorization.
5. Application services receive only trusted command/query inputs.
6. Domain objects remain unaware of tokens, sessions, providers, transport headers, and HTTP concerns.

## 4. Authentication Boundary

Authentication answers who the caller is.

Committed capability includes:

- provider-neutral authentication contracts;
- generic OIDC/JWT handling;
- bearer credential handling;
- JOSE/JWKS verifier support;
- safe authentication error categories;
- trusted-principal mapping.

Authentication remains host/provider-adapter owned. Domain, Application, Infrastructure repositories, and facts do not parse JWTs, cookies, OAuth sessions, provider SDK objects, passwords, or raw claim bags.

No specific deployed identity provider is claimed by this release. Provider URL, issuer, audience, JWKS, key-rotation, and operational credential configuration remain deployment concerns.

## 5. Trusted Principal Resolution

The trusted principal is the only identity object allowed past the authentication boundary.

It carries normalized, provider-neutral identity needed by the API host, including principal identity, principal type, and authentication-provider context. It intentionally excludes raw credentials and provider-specific claim payloads.

Command context derives actor identity from the trusted principal, not from caller-supplied request bodies.

## 6. Authorization Boundary

Authorization answers whether the authenticated caller can perform an operation on a resource.

Committed capability includes:

- authorization-resource ownership through `PortfolioWorkspaceAuthorizationResourceReference`;
- persisted execution ownership;
- authorization-resource resolution through Application;
- host-local ownership/capability policy;
- deny-by-default behavior for unauthorized access;
- privacy-safe forbidden/not-found mapping decisions at the presentation boundary.

Authorization is separate from lifecycle validation. The aggregate still owns lifecycle rules, work-item/candidate rules, duplicate accepted-artifact rules, and completion eligibility.

## 7. Public GET Path

The public-read path is implemented for bearer-authenticated get-by-ID access.

Verified capability includes:

- public authentication boundary;
- public get-by-ID request handling;
- trusted-principal handoff into the existing host flow;
- object-level authorization before returning execution data;
- concrete HTTP route binding;
- safe response and error mapping;
- correlation preservation.

This is the public-read/API-host capability closed by A16.3.

## 8. Internal Mutation and Idempotency Path

Durable idempotency infrastructure is committed for the internal mutation path.

Committed capability includes:

- idempotency contracts in Application;
- PostgreSQL idempotency table and mapper;
- reservation and duplicate classification;
- request fingerprinting;
- replay payload persistence;
- atomic coordination with aggregate mutation through Infrastructure;
- hosted PostgreSQL validation.

Idempotency identity remains separate from `commandId` and `correlationId`:

- `Idempotency-Key` identifies caller retry intent;
- `commandId` identifies command/audit intent;
- `correlationId` identifies request tracing.

Successful replay must not rerun the Domain mutation or create a new Domain fact.

## 9. Public Mutation Exclusion

Public mutation exposure is not included in A16.3.

Before public mutation routes are exposed, separate work must bind and validate:

- public mutation handlers;
- public-route idempotency semantics;
- provider-authenticated mutation access;
- operation/resource authorization for every mutation;
- retry behavior;
- rate limiting and abuse controls;
- audit and operational policy;
- production observability.

## 10. Concrete HTTP Host

A16.3 includes the concrete Node HTTP server and executable host capability required for the public-read/API-host release.

Verified behavior includes:

- route binding;
- request parsing;
- health/readiness behavior;
- lifecycle/disposal behavior;
- executable HTTP-host PostgreSQL integration;
- privacy-safe error behavior.

Deployment bootstrap, hosting topology, production secrets, identity-provider environment configuration, and operations runbooks remain separate concerns.
