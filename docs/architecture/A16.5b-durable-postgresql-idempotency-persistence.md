## Purpose

A16.5b implements the first durable PostgreSQL persistence slice for Portfolio Workspace mutation idempotency. It proves durable reservation, duplicate classification, replay payload persistence, release semantics, and PostgreSQL-backed concurrency behavior without wiring idempotency into mutation handlers.

Domain and Application remain unaware of idempotency keys, replay records, retries, HTTP semantics, or durable idempotency storage.

## Ownership Decision

A16.5a keeps semantic idempotency contracts in `apps/api` because idempotency is presentation/public-transport-adjacent.

A16.5b adds Infrastructure-owned durable persistence under `packages/infrastructure/src/portfolio-workspace/idempotency/`. The Infrastructure module accepts primitive operation, scope, fingerprint, and replay-payload data so it does not import the API package and does not create a circular dependency.

The intended direction for A16.5c remains:

```text

```

## Table Design

The new table is:

```text
portfolio_workspace_idempotency_records
```

Persisted fields:

- `scope_hash`: SHA-256 digest of operation, authorization resource, resource identity, and idempotency key digest.
- `record_version`: persistence-record compatibility version, currently `1`.
- `operation`: one of the nine Portfolio Workspace mutation operations.
- `authorization_resource_reference`: pseudonymous resource ownership scope.
- `resource_identity`: primary execution/resource identity for the mutation.
- `idempotency_key_hash`: SHA-256 digest of the raw idempotency key.
- `request_fingerprint_algorithm`: currently `sha256`.
- `request_fingerprint_value`: deterministic request fingerprint digest.
- `status`: `reserved` or `succeeded`.
- replay metadata: `replay_presentation_version`, `replay_outcome`, `original_correlation_id`, `replay_status`, `replay_body`, `replay_headers`.
- timestamps: `created_at`, `updated_at`, `completed_at`, `expires_at`.

The raw idempotency key is not persisted.

## Uniqueness Boundary

The database enforces the durable idempotency scope through:

```text
operation
+ authorization_resource_reference
+ resource_identity
+ idempotency_key_hash
```

`scope_hash` is the primary key. A unique index also covers the explicit scoped fields so the database, not an application pre-check, protects duplicate reservation correctness.

Fingerprint is intentionally not part of the uniqueness boundary. Same key plus different fingerprint is misuse and maps to fingerprint mismatch.

## State Machine

Implemented durable states:

- `reserved`: first request has acquired execution ownership.
- `succeeded`: successful replay payload has been persisted.

Implemented transitions:

- absent -> `reserved`
- `reserved` -> `succeeded`
- `reserved` -> deleted by release after mutation failure
- `succeeded` -> replay

`failed-final`, `expired`, stale-reservation recovery, and TTL cleanup remain deferred.

## Reservation Algorithm

Reservation uses PostgreSQL atomic insertion:

```text
INSERT idempotency row
ON CONFLICT(scope_hash) DO NOTHING
RETURNING scope_hash
```

If insert succeeds, the caller owns the first execution. If insert conflicts, the existing record is read and classified:

- same fingerprint + `reserved`: in progress;
- same fingerprint + `succeeded`: replay stored success;
- different fingerprint: conflict.

This avoids an unprotected `SELECT` then `INSERT` race.

## Replay Semantics

Success completion persists a presentation-safe replay payload: presentation version, outcome, original correlation ID, success status, safe JSON body, and safe JSON headers.

The store does not persist Domain facts, aggregate JSON, repository rows, command context, actor reference, credentials, raw headers, SQL details, or framework objects for replay.

## Release Semantics

Release after simulated mutation failure deletes a matching `reserved` row. A later request with the same scope and fingerprint may reserve again.

Release is intentionally limited to matching scope, fingerprint, and `reserved` state.

## Transaction Boundary

A16.5b proves atomic idempotency reservation and durable success completion at the idempotency table boundary.

It does not yet prove atomic coupling between:

- PortfolioExecution mutation save; and
- idempotency success replay persistence.

A16.5c must introduce the handler/coordinator transaction boundary before public mutation idempotency can be considered production-complete.

## Privacy Posture

Persisted idempotency data excludes:

- authentication tokens;
- cookies;
- raw credentials;
- provider principal objects;
- actor reference;
- command context;
- stack traces;
- SQL/SQLSTATE;
- Pool/Drizzle objects;
- raw idempotency key.

The durable scope uses the pseudonymous authorization resource reference.
