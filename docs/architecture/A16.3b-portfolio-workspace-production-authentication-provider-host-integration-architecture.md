# A16.3b - Portfolio Workspace Production Authentication Provider and Host Integration Architecture

## 1. Executive Summary

A16.3b selects the production authentication strategy for Portfolio Workspace public host integration.

Decision: approve a generic OIDC/JWT provider adapter strategy for the first production authentication implementation. No commercial provider is selected in this slice because repository evidence does not prove Auth0, Clerk, Okta, Cognito, Auth.js, Supabase, Firebase, Microsoft Entra, Google Identity, or another provider as the product/deployment standard.

The future implementation should verify standards-based bearer JWTs against configured issuer, audience, algorithm, and JWKS rules, then map the verified identity into the A16.3a provider-neutral contract:

```text
transport credential
  -> provider-specific OIDC/JWT adapter
  -> PortfolioWorkspaceAuthenticatedIdentity
  -> PortfolioWorkspacePresentationPrincipal
  -> authorization
  -> internal handler / Application Service
```

No SDK, token verifier, HTTP route, dependency, Domain change, Application change, Infrastructure change, or public API is introduced by this architecture slice.

## 2. Current A16.3a Baseline

A16.3a implemented:

- `PortfolioWorkspaceExternalAuthenticationContext`;
- `PortfolioWorkspaceAuthenticationAdapter`;
- `PortfolioWorkspaceAuthenticatedIdentity`;
- safe `PortfolioWorkspaceAuthenticationError`;
- trusted principal mapping into `PortfolioWorkspacePresentationPrincipal`;
- database-free tests proving privacy and boundary separation.

The API host remains framework-neutral and internal-handler based. Existing handlers receive a trusted `PortfolioWorkspacePresentationPrincipal`; they do not accept raw credentials.

## 4. Authentication Requirements

Human authentication requires:

- stable provider subject;
- stable issuer/provider identity;
- no email-as-primary-ID assumption;
- signature verification;
- issuer and audience validation;
- expiry validation;
- algorithm allow-list;
- key rotation handling;
- safe unavailable behavior for provider/JWKS outages;
- optional display name only after verification.

Service authentication requires:

- stable service subject;
- explicit provider distinction;
- no implicit authorization bypass;
- credential rotation support;
- compatibility with future worker/internal-service callers.

Security requirements:

- reject forged, expired, malformed, wrong-issuer, wrong-audience, wrong-algorithm, and missing-subject credentials;
- do not log or serialize raw bearer tokens, cookies, JWT claims, session secrets, signing keys, or provider SDK objects;
- map failures into A16.3a safe categories.

Operational requirements:

- deterministic unit tests without provider network calls;
- explicit configuration;
- no permissive production fallback;
- provider outage classification as authentication unavailable;
- future live auth validation before public route exposure.

## 5. Provider Options Considered

### Managed OIDC Provider

Examples: Auth0, Okta, Clerk, or similar.

Strengths: mature user management, hosted login, JWKS, revocation/disable behavior, operational support.

Limitations: provider lock-in and SDK/config coupling. Repository evidence does not select one.

Disposition: compatible but deferred until product/deployment choice is explicit.

### Cloud-Native Identity Provider

Examples: AWS Cognito, Microsoft Entra, Google Identity.

Strengths: strong in matching cloud ecosystems, mature OIDC/JWKS support, service identity options.

Limitations: no repository evidence selects a cloud provider for Portfolio Workspace.

Disposition: compatible but deferred.

### Auth.js / Application-Owned Authentication Facade

Strengths: web-framework friendly and can normalize sessions.

Limitations: current API host is framework-neutral; adopting Auth.js would imply route/framework integration not yet approved.

Disposition: deferred until a concrete Next.js/API route host is selected.

### Deployment Platform-Native Identity

Strengths: may reduce custom auth if the host platform supplies verified identity context.

Limitations: current repository only proves Vercel deployment references for the web surface, not an approved Portfolio Workspace identity platform.

Disposition: not selected.

### Generic OIDC/JWT Verifier

Strengths: standards-based, provider-portable, aligns with A16.3a, supports user and service principals, keeps provider details at the host boundary.

Limitations: implementation must correctly own JWKS caching, key rotation, clock tolerance, algorithm allow-list, and error privacy.

Disposition: selected for first implementation.

## 6. Provider Selection Decision

Selected: generic OIDC/JWT provider adapter approved.

Rationale:

- no specific commercial provider is evidenced;
- JWT/OIDC verification is a realistic standards-based production baseline;
- A16.3a already provides the provider-neutral output contract;
- user and service identities can share the same verified-token path initially;
- provider-specific code remains host-local and replaceable.

This does not prevent a future hosted provider such as Auth0, Clerk, Okta, Cognito, Entra, or Google Identity from being configured as the OIDC issuer.

## 7. Provider Coupling Boundary

Provider-specific code may live under a host-local path such as:

```text
apps/api/src/portfolio-workspace/authentication/providers/oidc-jwt/
```

Allowed dependencies for a future implementation are limited to the API host package unless separately approved.

Provider SDK or verifier types must not enter:

- Domain;
- Application;
- Infrastructure persistence/runtime;
- Portfolio Workspace presentation contracts;
- trusted principal JSON;
- command context;
- Domain facts;
- idempotency records.

## 8. Credential Input Decision

Initial credential input should be transport-owned bearer token extraction.

Future sequence:

```text
HTTP/framework request
  -> extract Authorization: Bearer <token>
  -> pass token only to OIDC/JWT authentication adapter
  -> discard raw token after verification
  -> emit credential-free authenticated identity
```

The A16.3a provider-neutral identity must never expose the raw token or claims object.

If a future framework supplies an already verified session, it should use a separate host-verified-session adapter implementing the same A16.3a contract.

## 9. Authenticated Identity Mapping

Verified JWT/OIDC claims map conceptually as:

- configured issuer/provider -> `provider`;
- stable subject claim (`sub`) -> `subject`;
- configured principal-kind rule -> `principalType`;
- optional safe display claim -> `displayName`.

Do not use email as `subject`.

Do not allow a request body, arbitrary header, or client-provided display name to become trusted identity.

## 10. Principal Stability

Current identity semantics remain:

```text
actorReference = principalType:authenticationProvider:principalId
authorizationResourceReference = portfolio-workspace:principal:<principalType>:<sha256(provider + subject)>
```

Provider migration may change `authenticationProvider` and therefore actor/resource identity. That is a future identity migration concern, not a reason to redesign current persisted semantics.

Tenant or organization context remains deferred because no current Portfolio Workspace requirement proves it.

## 11. Human Authentication Strategy

Human users should authenticate through an OIDC-compatible provider.

Required token properties:

- valid signature from issuer JWKS;
- expected issuer;
- expected audience;
- allowed algorithm;
- unexpired token;
- valid not-before when present;
- stable `sub`;
- no reliance on mutable email.

Display name is optional and non-authoritative.

## 12. Service Authentication Strategy

Service principals should authenticate through provider-verifiable credentials, preferably:

- OAuth client credentials producing JWT access tokens; or
- workload-identity issued JWTs from an approved issuer.

Static API keys are deferred and should be avoided for the first production path unless deployment evidence proves they are required.

Service principals use `principalType: "service"` and still require explicit authorization.

## 13. Authentication / Authorization Ordering

Selected request order:

```text
parse minimal transport envelope
  -> normalize correlation hint
  -> extract credential
  -> authenticate credential
  -> map to trusted principal
  -> check runtime readiness
  -> parse/validate request body/path
  -> authorize operation/resource
  -> create command context where needed
  -> invoke Application path
  -> map safe response
```

Authentication happens before authorization. Authorization happens before mutation, read response, and idempotency replay.

## 14. Runtime Readiness Ordering

Authentication should occur before runtime readiness checks for protected routes.

Reasoning:

- unauthenticated callers should receive authentication failures without learning runtime state;
- expensive body parsing or database readiness work should not occur for missing/invalid credentials;
- a valid authenticated caller may then receive safe unavailable if the runtime is not ready.

Credential extraction must remain cheap and bounded.

## 15. Error Mapping

Future provider adapter failure mapping:

| Provider condition | A16.3a reason | Presentation mapping |
| --- | --- | --- |
| missing bearer/session | `authentication-required` | unauthenticated |
| malformed token/session | `authentication-invalid` | unauthenticated |
| bad signature | `authentication-invalid` | unauthenticated |
| expired token | `authentication-invalid` | unauthenticated |
| wrong issuer | `authentication-invalid` | unauthenticated |
| wrong audience | `authentication-invalid` | unauthenticated |
| disallowed algorithm | `authentication-invalid` | unauthenticated |
| missing stable subject | `invalid-authenticated-identity` | unauthenticated |
| provider/JWKS outage | `authentication-unavailable` | unavailable |
| adapter mapping failure | `trusted-principal-mapping-failed` | unauthenticated |

Retryability:

- required/invalid/identity/mapping failures are not retryable without caller credential changes;
- provider/JWKS outage is retryable.

## 16. Credential Privacy

Do not expose:

- raw bearer token;
- cookie/session secret;
- JWT header/payload;
- claims object;
- signing keys;
- JWKS response body;
- provider response body;
- provider stack trace;
- SDK object;
- client secret.

Safe errors may contain only stable category/reason, safe cause name/code where already supported, and correlation ID at presentation level.

## 17. JWKS / Key Rotation Strategy

The OIDC/JWT adapter should own:

- issuer configuration;
- audience configuration;
- algorithm allow-list;
- JWKS retrieval;
- bounded JWKS cache;
- unknown `kid` refresh behavior;
- key rotation handling;
- verification timeout;
- provider outage classification.

Unknown key ID should trigger one bounded refresh, then fail invalid or unavailable according to whether the JWKS endpoint is reachable.

No JWKS cache, verifier, or network code is implemented in A16.3b.

## 18. Clock Strategy

Token expiry and not-before validation require authentication-time clock ownership.

Do not reuse command-context `occurredAt` as authentication time.

Future adapter tests should use an adapter-local clock seam or a verifier-supported deterministic clock. A15.2 command clock remains command-context-only.

## 19. Local Development Strategy

Local development should use either:

- a local/test OIDC issuer; or
- an explicit development-only fake authentication adapter.

No silent bypass is allowed.

Any development adapter must be:

- environment-gated;
- impossible in staging/production;
- credential-free beyond deterministic test identity;
- still subject to authorization.

## 20. Test Strategy

Unit tests:

- fake A16.3a adapter;
- deterministic valid/invalid/unavailable cases;
- no network.

Provider adapter tests:

- signed test JWTs;
- issuer/audience/expiry/algorithm/key-rotation cases;
- malformed tokens;
- safe error serialization.

API integration tests:

- credential extraction;
- successful trusted principal creation;
- authentication failure before authorization;
- authorization still required after authentication.

Live auth integration:

- deferred until a concrete issuer/provider is configured.

## 21. Configuration Contract

Future configuration should include:

- `PORTFOLIO_WORKSPACE_AUTH_PROVIDER=oidc-jwt`;
- `PORTFOLIO_WORKSPACE_AUTH_OIDC_ISSUER`;
- `PORTFOLIO_WORKSPACE_AUTH_OIDC_AUDIENCE`;
- `PORTFOLIO_WORKSPACE_AUTH_OIDC_JWKS_URI` only if issuer discovery is not used;
- `PORTFOLIO_WORKSPACE_AUTH_OIDC_ALLOWED_ALGORITHMS`;
- optional clock skew/timeout values with conservative defaults.

Issuer, audience, JWKS URI, and allowed algorithms are configuration, not secrets.

Client secrets are not required for bearer JWT verification and should not be introduced unless a future flow proves the need.

## 22. Public Route Gate

No public Portfolio Workspace route may invoke protected use cases until:

1. authentication verification exists;
2. trusted principal mapping succeeds;
3. production authorization executes;
4. public mutations use durable idempotency where required;
5. safe error/status mapping is tested;
6. public route integration is validated.

Authentication alone is insufficient for public mutation exposure.

## 23. Security Threat Review

| Threat | Mitigation | Status |
| --- | --- | --- |
| Forged token | signature verification via configured issuer JWKS | future implementation |
| Wrong issuer | exact issuer validation | future implementation |
| Wrong audience | exact audience validation | future implementation |
| Algorithm confusion | allow-list algorithms | future implementation |
| Expired token | expiry validation with auth clock | future implementation |
| Unknown/rotated key | bounded JWKS refresh | future implementation |
| Replay | authorization plus durable idempotency for mutations | auth implementation plus existing idempotency path |
| Credential leakage | A16.3a privacy contract and safe errors | partially implemented |
| Identity spoofing via body/header | credentials only through transport-owned extractor; body never trusted | future route work |
| Email-as-ID instability | use `sub`, not email | architecture decision |
| Service principal bypass | no bypass from `principalType: service` | already enforced by policy/tests |
| Provider outage | map to unavailable | architecture decision |
| Malformed claims | invalid identity | future implementation |
| Client display-name trust | optional, non-authoritative, post-verification only | architecture decision |
| Auth/authz confusion | authentication before authorization; authorization before use case/replay | architecture decision |
