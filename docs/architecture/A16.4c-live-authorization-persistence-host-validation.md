# A16.4c - Live Authorization Persistence and Current Host Authorization Validation

## Document Control

- Status: Ready
- Date: 2026-08-11
- Scope: Portfolio Workspace current internal API host authorization flows
- Non-goals: provider authentication, public routes, future mutation handlers, durable idempotency, version-1 backfill, public enumeration policy

## Purpose

A16.4c validates the current production authorization path for the two API-host operations that exist today:

- Initialize Portfolio Execution
- Get Portfolio Execution by ID

The validation target is the approved host path:

API Host -> Authorization -> Runtime -> Application -> PostgreSQL Repository -> PostgreSQL 17

## Authorization Resource Persistence Design

The API host receives a trusted `PortfolioWorkspacePresentationPrincipal` from the host boundary. Provider authentication remains external to this package.

`PortfolioWorkspaceProductionAuthorization` derives a `PortfolioWorkspaceAuthorizationResourceReference` from:

- principal type
- authentication provider
- principal ID

The provider and principal ID are hashed before storage. The durable resource string has the form:

`portfolio-workspace:principal:<principal-type>:<sha256>`

The raw provider token and session data are not stored in the PortfolioExecution aggregate payload. The authorization resource itself does not store raw principal ID or authentication provider values. The separate initialization command context still stores `actorReference` for internal audit provenance according to the existing A15.2 command-context contract.

## Owner Initialize/Get Flow

Initialization uses `authorizeInitialize(...)` before command-context construction and application service invocation.

The initialization handler passes the trusted authorization resource into `InitializePortfolioExecutionInput`. The application service passes it to `PortfolioExecution.initialize(...)`. The aggregate stores it and returns an initialization fact carrying the same resource.

Get-by-ID parses the execution ID, maps it to application input, resolves the stored authorization resource through the runtime-exposed resolver, and invokes the protected get application service only after authorization succeeds.

## Different Principal Denial

Different principals are denied when any trusted identity component differs:

- principal ID
- authentication provider
- principal type

The current internal response is forbidden. Public forbidden-versus-not-found privacy behavior remains deferred.

## Host Recreation Proof

The live API host suite initializes an execution through one host, disposes that host, creates a second host/runtime against the same PostgreSQL schema, and verifies:

- the same principal can get the execution;
- a different principal is denied;
- no revision or infrastructure metadata is exposed.

## Record Version 2 Behavior

`PORTFOLIO_EXECUTION_RECORD_VERSION` is `2`.

Version 2 records include `authorizationResourceReference` in `aggregate_payload`. The mapper writes and reads the field as aggregate state. Corrupt or missing authorization resources fail as mapping errors.

Version 1 records remain unsupported because they cannot prove trusted persisted ownership. No implicit fallback owner or runtime backfill is introduced.

## Spoofing Assessment

The live host suite attempts initialization with request-owned spoof fields including:

- owner
- ownerId
- actor
- principal
- principalId
- authorizationResource
- authorizationResourceReference
- commandId
- occurredAt

The stored authorization resource is still derived from the trusted host principal. The spoofed values do not appear in the stored aggregate row.

## Fail-Closed Assessment

Current fail-closed cases are covered by database-free and live tests:

- runtime not ready returns unavailable before authorization or service invocation;
- malformed initialization input returns invalid-input before authorization or service invocation;
- authorization denial returns forbidden and does not invoke the protected get service;
- missing execution maps safely through the authorization resolver;
- unsupported or corrupt durable records fail through mapper/repository errors.

## Optimistic Concurrency Regression

Existing live PostgreSQL repository tests continue to cover revision behavior:

- duplicate creation fails explicitly;
- compare-and-swap update succeeds only with the loaded revision;
- stale save fails without overwriting the stored state;
- authorization resource remains part of the persisted aggregate payload.

## Privacy Assessment

Representative live and database-free assertions verify safe serialization does not leak:

- raw provider tokens or session data;
- raw principal object;
- principal ID or authentication provider through the authorization resource or public response/error surfaces;
- database URL, password, SQL, SQLSTATE, Pool, Drizzle, repository row, revision, stack, or cause.

The persisted aggregate initialization command context is intentionally separate from authorization ownership. Its `actorReference` may contain the trusted principal-derived audit reference until a future approved actor pseudonymization contract replaces it.

A16.2m closed the live persisted-principal privacy contract regression. The corrected API host live assertion now scopes raw principal/provider checks to `aggregate_payload.authorizationResourceReference`, and final PostgreSQL 17 evidence reports the API host suite passed 9/9 with no failed or skipped live tests.
