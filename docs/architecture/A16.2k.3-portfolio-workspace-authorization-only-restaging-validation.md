## Authorization Flow

The intended runtime flow is:

trusted principal -> production authorization boundary -> pseudonymous authorization resource -> initialize application input -> PortfolioExecution aggregate -> serialized aggregate payload -> PostgreSQL JSONB -> rehydration -> authorization-resource resolver -> get-by-ID authorization check -> safe response or forbidden error.

Request bodies cannot provide or override ownership. Persisted command context actor references remain audit provenance, while `authorizationResourceReference` is the authorization ownership key.

## Record-Version Decision

PortfolioExecution record version advances to `2` because trusted ownership is mandatory in the durable aggregate payload. Version `1` records do not contain an approved authorization resource and are intentionally rejected by mapper compatibility checks rather than inferred, backfilled, or silently treated as public.

No SQL migration is required for this authorization change because the existing PostgreSQL schema stores the aggregate payload as JSONB and mapper validation owns payload compatibility.
