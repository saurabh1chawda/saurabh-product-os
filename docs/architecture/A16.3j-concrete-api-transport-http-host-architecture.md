# A16.3j - Concrete API Transport and HTTP Host Architecture

## Document Control

- Status: Ready for implementation
- Date: 2026-08-16
- Repository: `C:\Users\saura\saurabh-product-os`
- Branch: `release/portfolio-workspace-a16-rc`
- Scope: Concrete HTTP transport and host architecture decision for Portfolio Workspace public API routes

## Purpose

A16.3i correctly stopped because `apps/api` had no concrete HTTP route or server
convention. A16.3j decides the concrete host model so public Portfolio Workspace
routes can be implemented without inventing transport behavior inside a route
slice.

The decision is architecture-only. No route, server, dependency, Domain,
Application, Infrastructure, runtime, persistence, authorization, idempotency,
or CI behavior is implemented here.

## Existing Transport Baseline

Repository inspection found the following current state:

- `apps/api` is a TypeScript workspace package.
- `apps/api` contains Portfolio Workspace presentation contracts, internal
  handlers, provider-neutral authentication contracts, public bearer
  authentication, framework-neutral public Get binding, and
  `PortfolioWorkspaceApiHost`.
- `PortfolioWorkspaceApiHost` composes the Portfolio Workspace runtime,
  production authorization, command-context factory, and internal handlers.
- `PortfolioWorkspaceApiHost` exposes lifecycle, readiness, liveness, and
  deterministic disposal.
- `apps/api` does not contain Express, Fastify, Hono, Next route handlers, Node
  HTTP server startup, OpenAPI route registration, or concrete request/response
  adapters.

The current public API path is therefore:

```text
framework-neutral public request
  -> public bearer authentication boundary
  -> trusted principal
  -> public Get binding
  -> internal Get handler
  -> PortfolioWorkspaceApiHost/runtime
  -> safe framework-neutral response
```

The missing layer is:

```text
HTTP request/response
  -> framework-neutral public request/response
```

## Repository HTTP Convention Findings

Searches across the repository found no existing production API route convention
for Portfolio Workspace or another backend bounded context.

The root repository is a Next.js App Router Product OS web application. Its
documented responsibility is the public narrative/product web experience, not
the Career Companion API service.

`apps/web` exists only as a reserved future migration location for the root
Next.js application. It has no package manifest, route handlers, server runtime,
or API responsibility.

`apps/worker` is reserved for future background execution. It has no HTTP
server, route convention, or Portfolio Workspace role.

## apps/web Assessment

`apps/web` should not own Portfolio Workspace public API routes in this slice.

Findings:

- `apps/web` is reserved for future migration of the existing root Next.js app.
- The current Next.js app lives at the repository root and is documented as the
  Product OS web experience.
- No route handler convention exists in `apps/web`.
- Binding Portfolio Workspace API routes to the web app would couple an
  operational API surface to the public content/UI deployment.
- The API package already owns Portfolio Workspace presentation/authentication
  host boundaries.

Next.js route handlers remain a possible future outer adapter, but they should
not be selected now without a broader web/API deployment decision.

## apps/api Assessment

`apps/api` is the correct bounded package for the Portfolio Workspace public API
host.

Evidence:

- It already owns Presentation/API contracts.
- It already owns authentication and public binding code.
- It already owns `PortfolioWorkspaceApiHost`.
- It already depends on Infrastructure and Portfolio Workspace packages needed
  for runtime composition.
- Its README describes concrete HTTP route binding as deferred, not assigned to
  another package.

The missing concern is an executable HTTP transport shell, not a relocation of
API responsibilities.

## Options Considered

### Model A - apps/api Standalone Node Built-In HTTP Host

Use Node's built-in `node:http` module for a small explicit HTTP server under
`apps/api`.

Benefits:

- no new runtime dependency;
- concrete and testable HTTP semantics;
- keeps Portfolio Workspace API routes in `apps/api`;
- preserves existing API host lifecycle ownership;
- allows graceful shutdown and readiness/liveness endpoints later;
- avoids coupling to the root Product OS Next.js deployment;
- deployable as a long-running Node service or container.

Limitations:

- route matching, JSON serialization, method rejection, and body handling must
  be implemented carefully;
- future observability, CORS, compression, and middleware ergonomics are manual;
- framework migration may be needed if route count grows substantially.

### Model B - apps/api Standalone Framework-Based HTTP Host

Adopt a lightweight framework such as Fastify or Hono.

Benefits:

- mature routing and request/response ergonomics;
- easier future middleware integration;
- better ecosystem support for OpenAPI and testing.

Limitations:

- adds a new production dependency and framework convention;
- no repository evidence currently points to a preferred framework;
- wider review surface than needed for a single public read route.

### Model C - Fetch-Standard Adapter With Separate Outer Host

Implement fetch-style `Request`/`Response` handlers in `apps/api` and leave the
outer runtime for a future deployment host.

Benefits:

- portable to many runtimes;
- clean testing model;
- can be adapted to Next.js, workers, or serverless hosts later.

Limitations:

- still does not decide the concrete executable host;
- may defer A16.3i's concrete route problem rather than solve it;
- lifecycle/disposal ownership is less explicit without an outer host.

### Model D - Next.js Route Handlers in Root App or apps/web

Use Next.js App Router route handlers.

Benefits:

- existing root app already uses Next.js;
- route handlers provide concrete HTTP semantics;
- deployment could piggyback on existing web deployment.

Limitations:

- couples the Portfolio Workspace API to the Product OS web experience;
- `apps/web` is currently only reserved and not executable;
- root Next.js app is not documented as the Career Companion API host;
- pulling API runtime dependencies into the web app would blur package
  boundaries.

### Model E - Another Repository-Supported Model

No other concrete HTTP transport convention was found.

## Selected Model

Selected:

```text
MODEL A - apps/api standalone Node built-in HTTP host
```

This selection provides a concrete HTTP runtime without a new framework
dependency, preserves the purpose of `apps/api`, and gives A16.3i a real host
route target.

## Selection Rationale

Model A best satisfies the current release criteria:

- preserves A15/A16 dependency boundaries;
- keeps API responsibilities in `apps/api`;
- avoids coupling Portfolio Workspace to the root Product OS Next.js app;
- requires no dependency additions;
- supports deterministic request/response tests through actual HTTP semantics;
- keeps `PortfolioWorkspaceApiHost` as the owner of runtime readiness and
  disposal;
- is sufficient for one public read-only route;
- remains portable to containers or long-running Node deployment.

The architecture should be revisited before introducing broad route families,
complex middleware, streaming, multipart requests, or public mutation traffic at
scale.

## Dependency Decision

Do not add Express, Fastify, Hono, OpenAPI tooling, middleware frameworks, or
deployment SDKs for the first concrete route.

Use Node built-ins only:

- `node:http`;
- `node:url`, if needed;
- existing API package contracts.

## Proposed HTTP Route

The first public route should be:

```text
GET /v1/portfolio-workspace/executions/:executionId
```

Route version `/v1` is transport versioning. It is distinct from presentation
response version, persistence record version, migration version, correlation ID,
command ID, and idempotency key.

No public mutation route should be introduced with this host slice.

## Request Flow

```text
HTTP request
  -> method/path match
  -> bounded header/path extraction
  -> GetPortfolioExecutionPublicRequest
  -> GetPortfolioExecutionPublicBinding.handle(...)
  -> internal Get handler
  -> PortfolioWorkspaceApiHost/runtime
  -> public response
  -> HTTP response
```

## Request Adapter

The route adapter maps only:

- `Authorization` header;
- `x-correlation-id` header;
- `executionId` path segment.

It must not map client-provided actor, principal, command context, command ID,
authorization resource, repository revision, aggregate state, runtime object,
or arbitrary body/query fields.

For `GET`, request body content must not override path identity, principal,
correlation, command context, or authorization data.

## Authentication Flow

The route must not parse or verify JWTs directly.

Required flow:

```text
Authorization header
  -> PortfolioWorkspacePublicAuthenticationBoundary
  -> existing authentication adapter
  -> trusted PortfolioWorkspacePresentationPrincipal
  -> public Get binding
```

The public authentication boundary owns bearer extraction, credential
validation, correlation establishment before authentication, trusted principal
creation, and safe 401/503/500 authentication failure mapping.

## Trusted Principal Handoff

Only `PortfolioWorkspacePresentationPrincipal` may cross into the internal Get
flow. Raw bearer tokens, authorization headers, verified claim payloads, JOSE
headers, provider SDK objects, sessions, cookies, and authentication errors must
not cross the boundary.

## Authorization Flow

Authorization remains inside the existing internal Get handler path:

```text
public binding
  -> internal Get handler
  -> PortfolioWorkspaceInternalAuthorization.authorizeGet(...)
  -> runtime.getPortfolioExecution
```

The concrete route must not perform business authorization independently and
must not invoke `runtime.getPortfolioExecution` directly.

## Correlation Flow

Use the existing public correlation header:

```text
x-correlation-id
```

Flow:

```text
incoming x-correlation-id
  -> public authentication boundary normalization/generation
  -> public Get binding
  -> internal handler
  -> presentation result/error
  -> response x-correlation-id
```

Unsafe incoming values are replaced and must not be echoed.

## Response Adapter

The HTTP response adapter maps `GetPortfolioExecutionPublicResponse` into:

- numeric HTTP status;
- JSON response body;
- `content-type: application/json`;
- safe `x-correlation-id`;
- `WWW-Authenticate: Bearer` only when the public authentication failure
  includes it.

The adapter must not serialize raw `Error`, Application `Result`, Domain fact,
aggregate, repository error, runtime status, stack, cause, SQL, token, claims,
principal object, command context, or revision.

## Status Mapping

Use existing public/internal status semantics:

| Condition | Status |
| --- | ---: |
| Get success | 200 |
| invalid execution ID/request | 400 |
| unauthenticated | 401 |
| forbidden | 403 |
| execution not found | 404 |
| unavailable | 503 |
| internal failure | 500 |

`409` remains available for mutation conflicts but is not expected for the
public Get route.

## Runtime / Host Access

The HTTP host should construct or receive:

- one `PortfolioWorkspaceApiHost`;
- one public authentication boundary;
- one `GetPortfolioExecutionPublicBinding`;
- one route adapter for public Get.

The HTTP route must not construct:

- `PortfolioWorkspaceRuntime`;
- repositories;
- Drizzle database;
- PostgreSQL Pool;
- Application Services;
- Domain aggregates;
- Domain facts.

`PortfolioWorkspaceApiHost` remains the runtime/lifecycle owner.

## Startup Lifecycle

Future startup sequence:

```text
read host environment
  -> create authentication adapter/boundary
  -> create PortfolioWorkspaceApiHost
  -> verify host is ready
  -> create public Get binding
  -> start Node HTTP server
  -> listen
```

Environment parsing belongs at the host executable boundary. Domain,
Application, Infrastructure runtime composition, repositories, and presentation
mappers must not parse process environment.

## Shutdown Lifecycle

Future shutdown sequence:

```text
stop accepting HTTP requests
  -> optional bounded in-flight drain policy
  -> close HTTP server
  -> PortfolioWorkspaceApiHost.dispose()
  -> process termination by executable
```

Signal handling belongs in the executable server/bootstrap layer, not
`PortfolioWorkspaceApiHost`, Domain, Application, Infrastructure, or route
handlers.

In-flight drain policy remains deferred.

## Readiness / Liveness

Readiness/liveness endpoints are not required for the first public Get route.

Future health endpoints may be added under a separate slice:

```text
GET /health/live
GET /health/ready
```

They should map only safe `PortfolioWorkspaceApiHost.status()` information and
must not expose database URL, SQL, migration internals, repository state, Pool,
Drizzle client, credentials, or provider configuration.

## Security / Privacy

Minimum route-security requirements:

- accept only `GET` for the first public route;
- reject or ignore body fields for GET so they cannot override path identity;
- bound path/header sizes;
- handle malformed percent-encoding safely;
- parse Authorization only through the public authentication boundary;
- never trust forwarded identity headers without an approved proxy contract;
- never accept identity from query/body;
- return JSON only;
- return safe errors only;
- do not log credentials, raw claims, SQL, database URLs, or stack traces by
  default;
- do not expose public Initialize.

CORS, rate limiting, request logging, audit logging, and abuse controls remain
separate production-readiness concerns.

## Deployment Implications

The selected host model supports:

- local Node process execution;
- containerized API deployment;
- platform-managed long-running Node services;
- later adaptation behind a reverse proxy or gateway.

It avoids unnecessary lock-in to the root Next.js/Vercel web deployment. If a
future deployment decision requires serverless or Next route handlers, the
framework-neutral public binding can be adapted without changing Domain,
Application, runtime, repository, or persistence contracts.

## Test Strategy

Next implementation should add:

1. Request-adapter unit tests for method, path, headers, correlation, malformed
   path, and body non-override behavior.
2. HTTP integration tests using actual Node HTTP request/response semantics and
   controlled fake public binding/host dependencies.
3. Authentication handoff tests proving auth failure short-circuits before Get.
4. Authorization preservation tests proving the route only calls the public
   binding and does not duplicate authorization.
5. Response/status/privacy tests for 200, 400, 401, 403, 404, 503, and 500.
6. Runtime-not-ready mapping through the existing public/internal path.
7. Source-boundary tests proving no repository, Pool, Drizzle, aggregate,
   public Initialize, idempotency store, retry loop, service locator, command
   bus, Express, Fastify, Hono, or Next route coupling.
8. Later live PostgreSQL concrete-host validation once the HTTP server exists.

Tests for the concrete route should enter through HTTP semantics, not only by
calling handler functions directly.

## OpenAPI Decision

Defer OpenAPI until route conventions stabilize.

No existing OpenAPI convention was found. Introducing OpenAPI with the first
transport decision would add a second new convention without evidence that it is
needed for A16.3i.

## Public Initialize Verification

Public Initialize remains forbidden.

Public mutation exposure remains blocked by:

- durable idempotency route binding;
- public mutation authorization/readiness contract;
- retry/replay semantics;
- abuse/rate controls;
- operational logging and redaction policy;
- live public mutation validation.

## Recommended Implementation Sequence

1. A16.3k - Node HTTP host primitives and transport contracts for `apps/api`.
2. A16.3l - Public Get HTTP route adapter using A16.3h binding.
3. A16.3m - Database-free Node HTTP route integration tests.
4. A16.3n - Live PostgreSQL concrete-host validation for public Get.
5. A16.3o - Health/readiness route architecture and implementation, if still
   required before deployment.

A16.3i should not be resumed as originally written until the Node HTTP host
primitive exists. Its intended public Get route work becomes A16.3l after A16.3k
establishes the concrete transport shell.

## Final Decision

READY FOR IMPLEMENTATION.

Portfolio Workspace public HTTP routes should be hosted by `apps/api` as a
standalone Node built-in HTTP service. This provides the missing concrete
transport model while preserving existing A15/A16 boundaries and avoiding a new
framework dependency.

## A16.3k Implementation Reconciliation

A16.3k implements the first concrete Node built-in HTTP host primitives under
`apps/api/src/http`. It adds generic transport contracts, request normalization,
safe JSON response serialization, handler error containment, and deterministic
server start/stop lifecycle. It intentionally does not bind the Portfolio
Workspace public Get route, add executable process startup, or implement health,
OpenAPI, signal handling, body parsing, authentication, authorization, or
idempotency behavior.

## A16.3l Implementation Reconciliation

A16.3l implements the first concrete Portfolio Workspace public HTTP route under
`apps/api/src/portfolio-workspace/http`:

```text
GET /v1/portfolio-workspace/executions/:executionId
```

The route uses the A16.3k Node HTTP primitive, decodes only the path execution
ID, resolves a trusted principal through an injected host boundary, invokes the
existing internal Get handler, and returns safe JSON responses. It does not add
public mutation, executable startup, provider authentication parsing, repository
access, runtime construction, health endpoints, OpenAPI, idempotency, or a web
framework.

## A16.3m Implementation Reconciliation

A16.3m adds the concrete executable Portfolio Workspace HTTP host shell. It
creates one existing `PortfolioWorkspaceApiHost`, one `NodeHttpApiServer`,
registers `/health/live`, `/health/ready`, and the A16.3l public GET route, then
listens on explicit validated host/port configuration. It preserves the Node
built-in HTTP decision and still does not add Express, Fastify, Next route
handlers, public mutation, provider-specific authentication parsing, OpenAPI, or
deployment bootstrap.
