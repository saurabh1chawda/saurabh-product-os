## Purpose

Portfolio Workspace internal handlers are live validated, authorization ownership is persisted, PostgreSQL persistence is durable, and durable idempotency storage/orchestration is implemented and live validated. Public mutation exposure remains blocked until provider authentication, public route integration, operational controls, and public retry/abuse validation are complete.

This document defines the minimum durable idempotency architecture required before Portfolio Workspace mutation handlers can become public. It does not implement idempotency, schema, migrations, repositories, transaction management, handlers, retries, telemetry, or public routes.

A16.5a implements the first contract slice under the API Portfolio Workspace boundary. It adds immutable idempotency key, mutation operation, scope, fingerprint, replay payload, outcome, and safe error contracts. A16.5b adds Infrastructure-owned PostgreSQL idempotency persistence, schema, migration, durable record mapping, atomic reservation semantics, replay payload persistence, release semantics, and database-free validation. It intentionally does not wire storage into handlers, require public idempotency keys, coordinate PortfolioExecution saves and idempotency success in one transaction, add retries, or expose public routes.

## Current Baseline

Current mutation Application Services are:

- `InitializePortfolioExecutionApplicationService`
- `BeginExecutionApplicationService`
- `ActivateWorkItemApplicationService`
- `CompleteWorkItemApplicationService`
- `CancelWorkItemApplicationService`
- `AcceptCandidateApplicationService`
- `RejectCandidateApplicationService`
- `CompleteExecutionApplicationService`
- `CancelExecutionApplicationService`

Each service performs one Application use case over `PortfolioExecutionRepository`. Initialization creates and saves a new aggregate. Behavioral services load one aggregate, call one aggregate operation, save with the loaded revision, and return an Application Result.

Current API host exposure is internal and limited to initialize plus get-by-ID. The host receives a trusted principal, runs authorization, creates command context, maps request to Application input, invokes runtime services, and maps safe presentation responses.

No idempotency primitive currently exists. `packages/portfolio-workspace-application` has architecture coverage preventing accidental idempotency concepts in the Application layer.

## Existing Controls Are Not Idempotency

| Control | Provides | Does not provide |
| --- | --- | --- |
| `commandId` | Audit identity for one command attempt. | Durable duplicate detection or replay. A retry currently receives a new command ID. |
| `correlationId` | Request tracing and safe response/error correlation. | Request identity. Clients may reuse or change it without changing mutation intent. |
| Optimistic concurrency revision | Lost-update prevention on one aggregate save. | Safe retry after unknown outcome. Duplicate retries may still run a second Domain decision or return a conflict instead of replaying success. |
| Domain lifecycle guards | Business validity. | Transport retry semantics. A duplicate after success may fail because state already moved. |
| Unique aggregate identifiers | Duplicate create conflict. | Response replay for a successful but lost initialization response. |
| Authorization | Access decision. | Duplicate request detection. Authorization must still run before replay. |
| Database transaction | Atomic write boundary. | Request identity, replay payload, key scoping, or fingerprint conflict semantics by itself. |

## Mutation Operation Assessment

All current mutations require durable idempotency before public transport exposure.

| Operation | Classification | Reason |
| --- | --- | --- |
| Initialize Portfolio Execution | Required for public transport | Duplicate create can currently become conflict instead of replaying the original success. Timeout after create is ambiguous. |
| Begin Execution | Required for public transport | Duplicate begin after success may become lifecycle conflict. |
| Activate Work Item | Required for public transport | Duplicate activation may conflict or observe changed lifecycle. |
| Complete Work Item | Required for public transport | Duplicate completion may conflict and cannot safely prove whether the first response was lost. |
| Cancel Work Item | Required for public transport | Duplicate cancellation needs replay semantics. |
| Accept Candidate | Required for public transport | Creates accepted artifact state and has duplicate-artifact conflict risk. |
| Reject Candidate | Required for public transport | Duplicate rejection may conflict after candidate state changes. |
| Complete Execution | Required for public transport | Terminal transition must not run twice or report misleading conflict on retry. |
| Cancel Execution | Required for public transport | Terminal transition must replay success for duplicate retry. |

Get-by-ID is a query and does not require durable mutation idempotency.

## Idempotency Key Contract

The public mutation contract should use a presentation/transport-owned idempotency key, preferably an HTTP header when public HTTP routes are added.

Recommended conceptual name:

```text
Idempotency-Key
```

Rules:

- Client generated.
- Required for public mutation requests.
- Opaque to Portfolio Workspace.
- Trimmed only for surrounding whitespace rejection, not semantic normalization.
- Allowed characters: printable safe ASCII without controls; recommended pattern `[A-Za-z0-9._:-]`.
- Minimum length: non-empty.
- Maximum length: 128 characters unless an operations/security review chooses a lower cap.
- Reuse is allowed only for the same scoped operation and same request fingerprint.
- The key is not trusted as authentication, authorization, command ID, correlation ID, or aggregate identity.

The key must remain outside Domain entities, facts, and Application command context.

## Idempotency Scope

The same raw key must not collide across actors, operations, or resources.

Canonical scope:

```text
operation
+ authorizationResourceReference
+ normalized primary resource identity
+ raw idempotency key
```

For initialize, the primary resource is `executionId` from the request. For behavioral mutations, it is the persisted `PortfolioExecution` resource after authorization confirms access. Work-item, candidate, and accepted-artifact identifiers belong in the request fingerprint, not the broad scope, because they are part of the operation-specific intent.

`authorizationResourceReference` is preferred over raw principal identity because A16.2m/A16.4 established it as the pseudonymous durable ownership reference. `actorReference` is not required for idempotency scope; it remains audit provenance in command context.

## Request Fingerprint Design

An idempotency record must include a deterministic fingerprint to distinguish:

- same key + same request: replay or in-progress duplicate behavior;
- same key + different request: conflict, not replay.

Fingerprint inputs should include:

- idempotency contract version;
- operation/use-case name;
- normalized execution ID;
- normalized child IDs where applicable (`workItemId`, `candidateId`, `acceptedArtifactId`);
- normalized initialization references (`portfolioPlanReference`, `planSnapshotReference`, `approvalReference`);
- normalized initial work item IDs and candidate IDs in canonical order;
- pseudonymous `authorizationResourceReference`;
- presentation contract version where it affects intent.

Fingerprint inputs should exclude:

- `correlationId`;
- generated `commandId`;
- generated `occurredAt`;
- `actorReference`;
- unrelated transport headers;
- raw request body text;
- authentication tokens, sessions, cookies, provider claims, email addresses, or display names.

The fingerprint should be stored as a deterministic digest plus the digest algorithm/version. The digest is not a security secret; its purpose is compact equality checking and privacy-preserving storage.

## Trusted Principal and Authorization Relationship

Authorization must occur before replay.

Reason: a previously completed idempotency record must not let a caller bypass current access control. Every duplicate request still arrives with a current trusted principal, and the host must verify that principal against the operation/resource before returning any replayed success or in-progress status.

For initialize:

```text
parse request
-> trusted principal supplied by host
-> authorize initialize and derive authorizationResourceReference
-> normalize idempotency key and fingerprint
-> reserve/check idempotency
-> create command context only for first execution
-> invoke Application Service
-> atomically persist aggregate and idempotency success
-> return presentation response
```

For existing execution mutations:

```text
parse request
-> trusted principal supplied by host
-> resolve/authorize stored authorizationResourceReference
-> normalize idempotency key and fingerprint
-> reserve/check idempotency
-> create command context only for first execution
-> invoke Application Service
-> atomically persist aggregate and idempotency success
-> return presentation response
```

Authorization denial must not reveal or replay a prior result.

## Command Context Relationship

A duplicate request after success should reuse the originally completed result, not generate a second command context and not invoke a second Domain operation.

For the first execution, command context remains generated by the existing A15.2 factory after authorization and idempotency reservation. The Domain fact and Application Result keep their existing command/correlation semantics.

For replay, the transport response should come from the persisted idempotency replay data. The replay payload preserves the original successful response correlation because it identifies the original mutation outcome. A retry may have a separate host-local request correlation for logs and diagnostics, but retries must not rewrite the stored replay result.

The idempotency record should store enough safe metadata to support audit and replay:

- original command ID if a command was executed;
- original correlation ID included in the successful response;
- completed timestamp;
- operation and resource identifiers;
- safe replay payload.

It does not need to store `actorReference`; actor provenance remains inside persisted command context and facts.

## State Model

Minimum durable states:

| State | Meaning | Behavior |
| --- | --- | --- |
| `reserved` | First request has claimed the scoped key and is executing. | Concurrent duplicate with same fingerprint does not execute mutation. |
| `succeeded` | Mutation and replay payload were durably committed. | Duplicate with same fingerprint replays stored success. |
| `failed-released` | No mutation was committed and key can be reused. | Future same key may attempt again. |
| `failed-final` | A deterministic client/domain failure was recorded for a limited replay window, if policy chooses to persist failures. | Duplicate replays same safe failure or returns same category. |
| `expired` | Record is past retention and unavailable for replay. | Future use behaves as first request only after cleanup/expiry policy permits. |

`reserved` records require stale recovery rules. A record stuck in `reserved` after process crash is an unknown outcome unless the transaction design can prove no aggregate mutation committed. Unknown outcome must not be silently retried as a new mutation.

## Concurrent Duplicate Semantics

PostgreSQL implementation should use:

- unique constraint on scoped idempotency identity;
- insert-if-absent reservation;
- row-level lock or compare-and-swap for state transition;
- transaction isolation sufficient to ensure only one first executor runs;
- deterministic conflict for same key + different fingerprint.

Concurrent duplicate with the same fingerprint while the first request is `reserved` should return a safe in-progress/conflict response such as HTTP 409 or 425-equivalent at the host layer. It must not execute the mutation.

Concurrent duplicate after `succeeded` should replay the stored success.

## Atomicity Assessment

The hardest requirement is atomicity between:

- idempotency reservation/state update;
- aggregate repository save;
- replay result persistence.

The system must not allow:

- aggregate mutation committed but idempotency success lost;
- idempotency success committed while aggregate mutation failed;
- duplicate executor entering after stale reservation when outcome is unknown.

Correct durable implementation requires a PostgreSQL transaction spanning idempotency row work and `portfolio_executions` save, or an equivalent single-storage atomic design. The current `PortfolioExecutionRepository` exposes no transaction-aware API and `PostgresPortfolioExecutionRepository` performs direct Drizzle operations without an external transaction boundary.

Implementation prerequisite: introduce a narrow Infrastructure-owned PostgreSQL transaction composition boundary or a transaction-aware repository/idempotency coordinator without leaking Drizzle/Pool/SQL into Domain or Application.

## Storage Model

Recommended separate PostgreSQL table:

```text
portfolio_workspace_idempotency_records
```

Essential fields:

- record ID or scoped key digest primary identity;
- raw idempotency key or key digest;
- operation name;
- authorization resource reference;
- primary execution ID;
- request fingerprint digest;
- fingerprint algorithm/version;
- status;
- created at;
- updated at;
- completed at;
- expires at;
- original command ID when command executed;
- original correlation ID for replay;
- safe replay payload;
- safe error payload if final failure replay is supported;
- version column for record format.

Optional fields:

- in-progress owner token for debugging/recovery;
- attempt count;
- stale reservation deadline;
- completed aggregate revision for diagnostics.

Do not store:

- raw authentication tokens;
- sessions/cookies/JWT claims;
- raw provider user objects;
- emails/display names;
- full request body;
- database errors, SQL, SQLSTATE, stack traces, Pool/Drizzle objects;
- Domain aggregate JSON unless needed as the actual business persistence.

The existing `portfolio_executions` table should remain unchanged for idempotency.

## Result Replay Contract

Recommended replay model: persist a safe presentation replay payload, not a Domain aggregate, repository row, or raw HTTP framework object.

Rationale:

- Public clients need the same transport-level result shape on duplicate success.
- Application Results may contain facts and Application-only types that are not public API contracts.
- Infrastructure persistence should not depend on framework request/response objects.
- Presentation-owned replay payload can be versioned and privacy-reviewed.

The replay payload should include:

- presentation version;
- safe response body;
- success status code;
- public headers required for replay, especially correlation handling;
- operation/outcome code.

If future multiple hosts need shared replay, extract a transport-neutral `PortfolioWorkspaceMutationReplayPayload` in the API/presentation boundary, not in Domain.

## Failure and Retry Semantics

| Failure point | Idempotency behavior |
| --- | --- |
| Malformed request before key validation | Do not reserve key. Return invalid input. |
| Missing/invalid idempotency key for public mutation | Do not invoke Application. Return invalid input. |
| Unauthenticated | Do not reserve or replay. |
| Unauthorized | Do not reserve or replay. |
| Same key + different fingerprint | Return conflict. Do not invoke Application. |
| Domain rejection before save | May release key or persist final failure. Prefer release initially unless replaying failures is explicitly required. |
| Optimistic concurrency conflict | Do not auto-retry. Prefer final conflict or release depending transaction certainty. |
| Persistence unavailable before mutation | Release if no durable mutation occurred; otherwise unknown/in-progress. |
| Failure after aggregate save but before response delivery | Must be covered by transaction/replay persistence; duplicate should replay success if committed. |
| Process crash during execution | Recover through transaction state; unresolved `reserved` is not safe to replay or re-execute without proof. |

A15.1's conservative `retryable: false` posture should remain until idempotency is implemented and live validated.

## TTL and Retention

Idempotency records require bounded retention to control storage growth and reduce replay risk. The exact TTL is an operations/product decision and should not be hard-coded in architecture without evidence.

Recommended policy:

- Require a configurable retention window.
- Keep records long enough for realistic client retry windows.
- Expire successful and final-failure replay records after retention.
- Keep stale/unknown records long enough for investigation.
- Implement cleanup as a later operational slice, not as implicit handler behavior.

## Security and Privacy Assessment

Threats and mitigations:

| Threat | Mitigation |
| --- | --- |
| Key guessing | Scope by authorization resource and operation; do not reveal records before authorization. |
| Cross-user collision | Include pseudonymous `authorizationResourceReference` in scope. |
| Replay across operation | Include operation in scope and fingerprint. |
| Replay after authorization change | Authorize current request before replay. |
| Oversized/log-injection keys | Strict length and safe-character validation; redact or digest in logs. |
| Storage amplification | Required key length cap, TTL, cleanup, and rate limiting at public host. |
| Fingerprint oracle | Return generic conflict for mismatch; do not expose canonical fingerprint inputs. |
| Privileged old replay | Authorization-before-replay plus bounded retention. |
| Secret leakage | Store no tokens, sessions, raw provider objects, SQL, stack, or full request bodies. |

## Port Ownership

Do not place idempotency in the Domain package.

Recommended ownership:

- Presentation/API owns external key parsing, normalization, public error/status mapping, and replay payload shape.
- Application may own a narrow technology-neutral mutation idempotency port only if the orchestration is use-case-level and must be testable without PostgreSQL.
- Infrastructure owns PostgreSQL implementation, table records, locking, transactions, and storage errors.

Because correct behavior must coordinate presentation replay, authorization, command context, Application invocation, and repository save, the first implementation should be an API-host/Infrastructure coordinator with a narrow port. Avoid generic middleware, decorators, command buses, service locators, or Domain annotations.

Potential future packages:

- API-local contract for `PortfolioWorkspaceMutationIdempotencyKey` and replay payload.
- Infrastructure module under `packages/infrastructure/src/portfolio-workspace/idempotency/` for PostgreSQL storage.
- Runtime composition may expose an idempotency coordinator only to API host construction, not to Domain/Application.

A16.5a placement decision: contracts live under `apps/api/src/portfolio-workspace/idempotency/` because the key and replay payload are presentation/public-transport-adjacent. Domain and Application remain unaware of idempotency.

## Handler Integration Model

Future mutation handler flow:

```text
parse transport input
-> obtain trusted principal
-> validate/normalize idempotency key
-> authorize current principal and resource
-> build request fingerprint from authorized intent
-> reserve/check idempotency
-> if succeeded duplicate: replay stored safe response
-> if reserved duplicate: return in-progress/conflict
-> if mismatch: return idempotency conflict
-> generate command context for first execution
-> map request to Application input
-> invoke exactly one Application Service inside atomic transaction boundary
-> persist aggregate save and replay payload atomically
-> return response
```

Existing internal initialize/get handlers should remain unchanged until a dedicated implementation slice adds public mutation idempotency.

## Public Mutation Release Gate

Public mutation routes remain NO-GO until all are true:

- idempotency key contract implemented and documented;
- durable PostgreSQL idempotency storage migrated;
- transaction boundary atomically coordinates idempotency and aggregate persistence;
- authorization runs before reservation/replay;
- same-key same-request replay is live validated;
- same-key different-request conflict is live validated;
- concurrent duplicates execute mutation at most once;
- successful duplicate replay returns safe presentation response;
- failure semantics are deterministic and safe;
- no secrets or raw provider identity leak through records, logs, or responses;
- live PostgreSQL repository/runtime/API host tests pass in CI;
- public route policy explicitly requires idempotency keys for mutations.
