# A16.4 - Production Authentication and Authorization Boundary Readiness

## Executive Summary

Portfolio Workspace has a correct internal trust boundary, but it is not ready for public API exposure.

Current handlers receive an already-authenticated `PortfolioWorkspacePresentationPrincipal`, invoke a host-local authorization boundary, and keep provider/session/token details outside Domain and Application. That shape should be retained.

The original production blocker was not the handler sequence. It was that `PortfolioExecution` persisted state did not contain a tenant, workspace, owner, or authorization-resource reference. Existing `PortfolioPlanReference`, `PlanSnapshotReference`, and `ApprovalReference` are business provenance references, not security ownership concepts.

A16.4a resolved the durable ownership-model gap by introducing `PortfolioWorkspaceAuthorizationResourceReference`, requiring it during initialization, persisting it with `PortfolioExecution`, carrying it in the initialization fact, and keeping it out of public projections/responses.

Decision: authentication remains host/provider-owned; Portfolio Workspace consumes only a normalized trusted principal. Authorization remains outer-layer/host-owned through explicit use-case/resource methods. Before public exposure, Portfolio Workspace still needs production authorization policy and resource resolution.

## Current Trust Model

The current model is intentionally split:

1. Raw credentials are outside Portfolio Workspace.
2. Provider authentication is outside Portfolio Workspace.
3. `PortfolioWorkspacePresentationPrincipal` is the normalized trusted principal consumed by handlers.
4. `PortfolioWorkspaceInternalAuthorization` makes authorization decisions before Application Service invocation.
5. `PortfolioWorkspaceCommandContextFactory` maps the trusted principal into Domain `actorReference` for command facts.

Handlers do not accept principal identity, role, permission, actor reference, command ID, or occurrence time from request body/path/query data.

## Authentication Boundary

Authentication is the host/provider mechanism that proves a caller identity before Portfolio Workspace handler invocation.

Portfolio Workspace should not parse or validate:

- JWTs;
- OAuth tokens;
- cookies;
- sessions;
- provider SDK objects;
- framework auth objects;
- raw claims.

The future production host adapter should transform provider-specific authentication output into a normalized trusted principal before calling any Portfolio Workspace handler.

## Principal Contract

Current fields:

- `principalId`
- `principalType`: `user` or `service`
- `authenticationProvider`
- optional `displayName`

This is sufficient for command-context actor attribution and internal testing.

It is not sufficient for production authorization because it contains no tenant, account, organization, workspace, ownership, role, capability, or resource-access data.

Recommendation: keep this principal contract as the authentication output. Do not add authorization decisions to it. If production authorization requires tenant/workspace membership, model that as authorization subject/resource input, not as client-controlled request fields.

## Authentication Facts vs Authorization Decisions

Authentication facts answer:

- who the caller is;
- how identity was verified;
- whether the subject is a user or service;
- which provider asserted the identity.

Authorization decisions answer:

- whether this principal may perform this operation;
- on this execution or initialization resource;
- within this tenant/workspace/ownership boundary;
- with this capability.

These must remain separate. A trusted identity is not automatically authorized.

## Principal Trust Model

The trusted data path should be:

```text
HTTP/framework request
-> provider credential extraction
-> provider verification
-> normalized trusted principal
-> authorization subject/resource construction
-> authorization decision
-> command context or query input
-> Application Service
```

The request body/path/query may carry business identifiers such as execution ID, work item ID, candidate ID, plan reference, or correlation hint. It must not assert:

- principal identity;
- role or capability;
- actor reference;
- command ID;
- occurredAt;
- tenant/workspace ownership;
- provider claims.

## Actor Reference Assessment

Current default actor reference:

```text
principalType:authenticationProvider:principalId
```

Benefits:

- deterministic;
- provider-neutral enough for current internal audit facts;
- does not include tokens or raw claims;
- supports user and service identities.

Risks:

- provider migration could change actor reference values;
- provider subject IDs may be opaque but still sensitive;
- tenant ambiguity remains if the same principal can access multiple workspaces;
- account linking is not represented.

Decision: retain the current mapping for internal facts. Before public rollout, evaluate whether a stable internal `ActorId` or actor directory is required. Do not change Domain command context in A16.4.

## Current Authorization Boundary

Current interface:

```ts
authorizeInitialize({ principal, request })
authorizeGet({ principal, executionId })
```

Current invocation:

- initialization parses the request, then authorizes, then creates command context, maps input, and calls runtime initialization;
- get validates/parses execution ID, maps to input, authorizes, then calls runtime query service;
- runtime-not-ready returns before authorization;
- authorization failures map through safe presentation errors.

This boundary is correctly outside Domain and Application.

## Authorization Model Decision

Use an explicit resource/capability policy model, not generic string permissions or Domain lifecycle rules.

Recommended vocabulary:

- authorization subject: trusted user or service principal;
- authorization resource: execution, initialization source, portfolio workspace/tenant, or approved plan context;
- capability: initialize, read, begin, activate-work-item, complete-work-item, cancel-work-item, accept-candidate, reject-candidate, complete-execution, cancel-execution;
- decision: allow or deny with safe denial category.

Do not select RBAC by default. Roles may be an input to a future policy, but the Portfolio Workspace boundary should ask explicit use-case authorization questions.

## Portfolio Execution Ownership Assessment

`PortfolioExecution` currently stores:

- `ExecutionId`;
- `PortfolioPlanReference`;
- `PlanSnapshotReference`;
- `ApprovalReference`;
- initialization `PortfolioExecutionCommandContext`;
- lifecycle;
- owned work items, candidates, and accepted artifacts.

None of these fields identify the user, tenant, organization, account, or workspace that owns the execution.

`PortfolioPlanReference`, `PlanSnapshotReference`, and `ApprovalReference` are provenance/business references. They may help resolve authorization through Planning/Approval systems, but they are not themselves ownership/security concepts.

Classification after A16.4a: OWNERSHIP MODEL IMPLEMENTED; production policy and resolver remain BLOCKING BEFORE PUBLIC EXPOSURE.

## Tenancy and Workspace Scope Decision

Portfolio Workspace should become explicitly scoped to an authorization resource before public API exposure.

Implemented A16.4a model:

- introduce an execution-level `PortfolioWorkspaceAuthorizationResourceReference`;
- persist it with `PortfolioExecution`;
- keep provider-specific identity outside Domain/Application;
- avoid overloading plan or approval references;
- source it from the trusted authorization boundary during initialization, not from arbitrary request JSON.

Production policy evaluation and efficient execution-to-resource lookup remain future work.

## Pre-Load vs Post-Load Authorization

Initialize:

- can authorize before aggregate creation if the request includes an approved plan/workspace/authorization resource reference;
- current initialization request lacks a dedicated ownership/security reference;
- production initialization therefore requires a pre-load authorization resource decision against Planning/Approval context or a new workspace scope.

Get and mutations:

- current handler can authorize by `ExecutionId` before loading only if an external authorization lookup maps execution ID to an owner/tenant;
- without that lookup, the handler would need to load execution first, but the loaded aggregate lacks enough ownership metadata;
- public endpoints should avoid returning different details that leak cross-tenant existence.

Decision: production authorization needs either pre-load execution-to-scope lookup or persisted execution authorization scope. Current model is not enough.

## User Principal Policy

User principals should receive only capabilities granted by ownership, tenant/workspace membership, or approved collaboration role.

Minimum user policy:

- owner/member may read executions in their scope;
- only authorized operators may mutate executions;
- candidate acceptance should require a stronger review/approval capability than generic read;
- cross-tenant execution IDs must be denied without revealing sensitive details.

## Service Principal Policy

Service principals must not have blanket access by default.

Minimum service policy:

- each service identity has explicit capabilities;
- service access is tenant/workspace scoped when possible;
- initialization by service principal is allowed only for approved orchestration sources;
- read/mutation/admin privileges must be distinct;
- service-principal operations require audit.

## Authentication Provider Boundary

Provider selection remains outside Portfolio Workspace.

Provider-neutral production requirements:

- stable subject identifier;
- provider identifier;
- verified subject type;
- issuer/audience/session validity when token-based;
- optional trusted organization/workspace claims only if independently verified;
- no raw credential or provider object crosses into Domain/Application.

No Auth0, Clerk, Firebase, Cognito, Google Identity, custom JWT, session, cookie, or OAuth implementation is selected in A16.4.

## Authentication Failure Contract

Unauthenticated means no trusted principal can be established.

Safe public response:

- category: unauthenticated;
- status: 401;
- message: authentication required;
- include correlation ID;
- no token/provider details.

Forbidden means a trusted principal exists but policy denies the operation.

Safe response:

- category: forbidden or intentionally not-found depending on public privacy policy;
- include correlation ID;
- no policy internals, role list, scope list, tenant identifiers, or provider claims.

## Forbidden vs Not-Found Privacy Decision

Decision for internal handlers: keep current explicit 403 for authorization denial and 404 for Application not-found.

Decision for future public execution-specific endpoints: prefer enumeration-resistant 404 for a principal that is authenticated but not authorized to access an execution ID, unless a support/debug-only internal route is explicitly marked internal.

Tradeoff:

- 404 reduces cross-tenant resource enumeration;
- 403 is clearer for internal diagnostics;
- public clients do not need to know whether another tenant's execution exists.

This is a future implementation policy and does not change A15 internal handler behavior.

## Authorization Failure Contract

Authorization failures must not expose:

- whether a protected execution exists;
- another tenant's identifiers;
- policy internals;
- role/scope details;
- provider token details;
- repository or persistence metadata.

They should be represented as safe presentation errors and mapped to host-local statuses at the outer boundary only.

## Command Context Interaction

Command context is created after a trusted principal exists and after authorization allows the mutation.

Rules:

- request body cannot set command ID, actor reference, or occurredAt;
- actor reference is derived from the trusted principal or future trusted actor mapper;
- correlation may accept a safe incoming hint or use a generated fallback;
- command context remains operation-specific;
- command context is not idempotency storage.

## Idempotency Interaction

Public mutation idempotency remains a separate blocker.

Future idempotency rules:

- key scope must include trusted principal and tenant/workspace/resource;
- one principal cannot replay another principal's key;
- authorization must still be enforced on replay;
- cached responses must not cross tenant/principal boundaries;
- command ID and correlation ID must not be treated as durable idempotency keys.

## Audit Requirements

Minimum future audit requirements:

- authentication failure count/context without credentials;
- authorization denial with safe principal/resource references;
- successful privileged mutations;
- service-principal operations;
- idempotency replay decisions once implemented;
- production policy configuration changes.

Do not log tokens, cookies, raw claims, secrets, full database URLs, or sensitive provider errors.

## Rate Limit and Abuse Boundary

Rate limiting remains outside Domain/Application.

Recommended scopes:

- unauthenticated traffic by IP/client fingerprint at the transport edge;
- authenticated traffic by principal;
- tenant/workspace scoped limits for shared resources;
- stricter limits for public mutation endpoints;
- separate service-principal quotas.

## Host Integration Impact

Future production host composition needs:

- authentication adapter/provider integration;
- trusted principal normalizer;
- production authorization policy;
- authorization resource resolver;
- Portfolio Workspace runtime;
- command-context dependencies;
- optional audit sink;
- public transport/router binding;
- rate limiting and operational guards outside Portfolio Workspace core.

A15.7's explicit authorization dependency remains valid.

## Blocking Security Gaps

- No production authentication provider adapter.
- No production authorization policy.
- No production authorization resource resolver or policy enforcement.
- No public forbidden-vs-not-found implementation.
- No durable idempotency for public mutation.
- No security audit/logging strategy.
- No public rate-limit/abuse policy.

## Required Future Data Model Changes

Minimum future correction must introduce one of:

1. persisted execution authorization scope on `PortfolioExecution`;
2. external execution-to-authorization-resource lookup owned by an approved security/application boundary;
3. Planning/Approval-owned authorization resource that can safely resolve execution access before aggregate load.

Affected layers will depend on the selected option:

- Domain: affected if authorization scope is part of execution identity/invariants.
- Application: affected if inputs/results or repository lookup need scope.
- Persistence: affected if scope is stored with execution records.
- Presentation/API: affected in all options because handlers need production policy/resource resolution.

## Security Test Strategy

Future tests should cover:

Authentication:

- missing credential;
- invalid credential;
- expired credential;
- wrong issuer/audience when token-based;
- service identity.

Authorization:

- owner allowed;
- non-owner denied;
- cross-tenant access denied;
- service capability allowed and denied;
- read vs mutation permission;
- candidate acceptance as privileged mutation;
- enumeration-resistant public errors.

Trust:

- body principal ignored;
- actorReference cannot be client-controlled;
- role/scope claims cannot be body-controlled;
- command context remains trusted.

Privacy:

- tokens never serialized;
- provider errors not leaked;
- authorization internals not leaked;
- protected-resource existence not leaked publicly.

## Readiness Decision

READY FOR IMPLEMENTATION.

A16.4 defines the authentication and authorization boundary architecture. Production public exposure remains blocked until the ownership/resource model, provider authentication, production authorization policy, and security tests are implemented.
