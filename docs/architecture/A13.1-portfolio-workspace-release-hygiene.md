## 8. Structural API Decision

The approved correction is Option A/B from the A13.1 prompt:

- Make structural collection registration private.
- Keep constructor collection inputs as the explicit reconstruction path.
- Do not introduce a generic rehydration framework.
- Do not replay business operations during persistence load.
- Do not preserve accidental public mutation API for compatibility because the bounded context is not yet broadly composed.

## 9. Rehydration Impact

Rehydration remains safe because both durable and in-memory mappers construct supporting entities directly and pass collection snapshots into the `PortfolioExecution` constructor.

No rehydration path requires:

- private-field mutation;
- reflection;
- `Object.assign()`;
- unsafe casts;
- behavior replay;
- fact production.

Live PostgreSQL rerun is not required solely for this change because serialization, constructors, mapper, repository port, schema, revision semantics, and PostgreSQL adapter code were not changed. Package, mapper, adapter, and root tests remain required.

## 10. Public API Impact

The TypeScript public class surface of `PortfolioExecution` is narrowed:

- Removed from public contract: `registerWorkItem()`.
- Removed from public contract: `registerCandidate()`.
- Removed from public contract: `recordAcceptedArtifact()`.

Replacement:

- Use the constructor with validated collection inputs for construction or rehydration.
- Use behavioral operations for business decisions.
- Use `acceptCandidate(candidateId, acceptedArtifactId, commandContext)` for candidate acceptance and accepted-artifact creation.

No package root exports were removed.

## 15. CI Live PostgreSQL Gate

Policy:

- Database-free tests MUST run on every normal CI validation.
- Live PostgreSQL integration MUST run before merge when a pull request changes:
  - Portfolio Workspace domain constructors or serialization;
  - supporting entity serialization;
  - identifiers, references, or command context serialization;
  - application repository contracts;
  - durable mapper;
  - record version;
  - schema or migration files;
  - PostgreSQL adapter;
  - repository revision semantics;
  - live test harness.
- Deployment MUST require the latest successful live PostgreSQL suite for the release candidate being deployed.
- Live tests MUST use an isolated disposable test database.
- The database name MUST contain `test` and MUST NOT contain `prod` or `production`.
- CI MUST NOT use production credentials.
- The committed migration MUST be applied during the live suite.
