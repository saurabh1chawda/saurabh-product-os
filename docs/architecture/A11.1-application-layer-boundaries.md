# A11.1 - Application Layer Boundaries

## 1. Purpose

This document defines the canonical Application Layer boundary for Portfolio Workspace before application service implementation begins.

It applies after completion of the Portfolio Workspace Domain Model:

- Canonical vocabulary.
- Value objects and planning references.
- Supporting entities.
- `PortfolioExecution` behavioral aggregate.
- Immutable domain facts.
- Pure domain policies.
- Pure domain projections.
- Domain service justification.

The Application Layer coordinates use cases around the Domain Model. It does not redefine domain behavior.

This document does not define TypeScript interfaces, classes, dependency injection, frameworks, controllers, routes, storage, or implementation code.

## 2. Definition

An Application Service coordinates one business use case by invoking domain behavior and returning domain results.

An Application Service is not:

- Domain logic.
- Aggregate.
- Entity.
- Value object.
- Policy.
- Projection.
- Repository implementation.
- Infrastructure adapter.
- Controller.
- UI model.
- Workflow engine.
- AI provider boundary.

Application Services belong above the Domain Model. They translate application intent into valid domain operations without owning the rules that make those operations valid.

## 3. Responsibilities

Application Services may:

- Load aggregates through repository ports.
- Invoke aggregate behavior.
- Receive immutable domain facts from aggregate operations.
- Evaluate domain policies where required.
- Build or return domain projections.
- Coordinate transaction boundaries.
- Invoke infrastructure through ports.
- Enforce idempotency at the application boundary when commands may be retried.
- Coordinate authorization checks before domain operations are invoked.
- Return use-case results containing domain facts, projections, and domain errors.

Application Services MUST NOT:

- Implement business rules.
- Duplicate aggregate invariants.
- Mutate projections.
- Mutate domain facts.
- Bypass aggregates to change domain state.
- Directly access databases.
- Call external SDKs directly.
- Own lifecycle transition policy.
- Own approval policy.
- Place infrastructure concerns inside domain models.
- Treat projections as the source of truth.

Business rules remain inside the Domain Model. Application Services coordinate when domain behavior is invoked and how results are returned.

## 4. Dependency Rules

Allowed dependencies:

- Portfolio Workspace Domain Model.
- Repository ports.
- Infrastructure ports.
- Transaction abstractions.
- Application-level command or result contracts.

Forbidden dependencies:

- Database drivers.
- HTTP frameworks.
- UI frameworks.
- Messaging SDKs.
- AI SDKs.
- ORM entities.
- Browser automation libraries.
- Rendering libraries.
- External integration SDKs.

Application Services may depend on ports. Infrastructure adapters implement those ports outside the Application Layer.

No dependency cycle is permitted.

## 5. Transaction Boundaries

Transactions are owned by the Application Layer, not the Domain Layer.

The Domain Model validates and mutates aggregate state in memory. It does not begin, commit, roll back, retry, or recover transactions.

An Application Service may coordinate a transaction around:

- Loading the current aggregate through a repository port.
- Invoking one domain operation.
- Capturing produced domain facts.
- Persisting the updated aggregate through a repository port.
- Persisting or exposing facts according to the future persistence boundary.
- Returning a projection or result.

Infrastructure provides transaction implementation. The Application Layer decides the unit of work. The Domain Model remains persistence-free.

## 6. Typical Flow

Canonical application service flow:

```text
Repository Port
    ↓
Aggregate
    ↓
Facts
    ↓
Policies
    ↓
Projections
    ↓
Return Result
```

This flow is not a universal execution pipeline. It is a use-case coordination pattern for application services.

Application Services may skip optional steps when they are not required by the use case. For example, a command may invoke aggregate behavior and return facts without policy evaluation.

Application Services MUST NOT skip the aggregate when changing domain state.

For fact-producing Portfolio Workspace operations, the Application Service supplies the operation-specific `PortfolioExecutionCommandContext` to the aggregate operation. The fact returned by the aggregate is the authoritative source of command context for the completed operation. Application Services MUST derive returned correlation identifiers from the fact rather than independently from input metadata.

## 7. Future Use Cases

Conceptual examples only:

| Use case | Application responsibility | Domain responsibility |
| --- | --- | --- |
| Begin Execution | Load or create the execution boundary, coordinate idempotency, invoke domain operation, persist result. | Validate execution lifecycle and update aggregate state. |
| Activate Work Item | Load execution, authorize request, invoke aggregate behavior, return fact and projection. | Validate work-item existence and lifecycle rule. |
| Complete Work Item | Load execution, invoke completion behavior, capture fact, return updated projection. | Enforce work-item completion invariant. |
| Accept Candidate | Load execution, verify explicit human approval exists at the application boundary, invoke aggregate behavior. | Validate candidate state and record accepted candidate fact. |
| Complete Execution | Load execution, optionally evaluate completion policy, invoke aggregate completion behavior, return projection. | Enforce aggregate completion invariant. |

These examples do not authorize implementation, command schemas, repositories, controllers, routes, background jobs, or infrastructure adapters.

## 8. Deferred Topics

The following remain explicitly deferred:

- REST.
- GraphQL.
- CLI.
- Scheduling.
- Background jobs.
- Messaging.
- Infrastructure adapters.
- Repository implementations.
- Database schemas.
- ORM mappings.
- API DTOs.
- UI models.
- AI integration.
- Workflow engines.
- Dependency injection.
- Cross-workspace orchestration.

These are not Application Layer gaps. They require future implementation evidence and architecture review.

## 9. Final Decision

Portfolio Workspace Application Services may be implemented to coordinate one use case at a time.

They may load aggregates through ports, invoke domain behavior, receive facts, evaluate policies where required, return projections, and coordinate transactions.

They must not own business rules, bypass aggregates, mutate projections, directly access infrastructure, call external SDKs, or weaken the Domain Model boundary.
