## 14. A16.1a Defect and Correction

A16.1a identified a migration metadata concurrency defect exposed by root live-test execution:

- Runtime and API live harnesses create isolated application schemas.
- Migration readiness originally used one fixed Drizzle migration metadata location.
- Concurrent root Vitest execution could make live suites collide on migration metadata even though package-level live suites passed in isolation.

Correction:

- Infrastructure migration readiness now derives a deterministic migration metadata table from the active PostgreSQL schema.
- Production readiness uses the installed Drizzle PostgreSQL migrator contract.
- Apply and verify-only inspect the same metadata relation.

Exact production change:

- `packages/infrastructure/src/portfolio-workspace/runtime/PortfolioWorkspaceMigrationReadiness.ts` now derives schema-scoped migration metadata table names and verifies the same relation used by Drizzle apply mode.

Domain and Application behavior did not change.

## 15. A16.1b Defect and Correction

A16.1b identified the remaining root live-test failure as a harness identifier defect:

- Drizzle 0.45.2 supports `migrationsSchema` and `migrationsTable`.
- Drizzle creates metadata at the exact configured `migrationsSchema.migrationsTable` relation.
- PostgreSQL truncates identifiers longer than 63 bytes.
- The live harnesses generated schema names long enough to be truncated by PostgreSQL.
- Production readiness hashed `current_schema()`, which reported the truncated schema name.
- Harness count helpers hashed the original untruncated string.
- The hashes differed, so harness assertions queried a non-existent metadata table even though production readiness had applied and verified migrations.

Correction:

- Runtime and API live harnesses now generate PostgreSQL test schema names below the 63-byte identifier limit.
- Harness metadata counting and cleanup hash the same active schema identifier that production readiness reads from PostgreSQL.
- Database-free regression coverage confirms the deterministic metadata table identifier is PostgreSQL-safe.

Exact test-harness correction:

- `packages/infrastructure/tests/portfolio-workspace-runtime-live.test.ts` uses short runtime live schema names.
- `apps/api/tests/portfolio-workspace-api-host-live.test.ts` uses short API host live schema names.
- `packages/infrastructure/tests/portfolio-workspace-migration-readiness.test.ts` covers metadata table identifier length.

No production Domain, Application, Infrastructure runtime, persistence, API host, repository, mapper, schema, or migration behavior was changed in A16.1b.

## 16. Migration Metadata Final Design

Final stable metadata design:

- Metadata schema: `drizzle`
- Metadata table: `__portfolio_workspace_migrations_<hash>`
- Physical relation: `drizzle.__portfolio_workspace_migrations_<hash>`

The hash is derived from the active PostgreSQL schema reported by `current_schema()`.

This preserves:

- Infrastructure-owned migration metadata
- Active-schema isolation for concurrent live tests
- Strict verify-only behavior
- Shared apply/verify metadata semantics
- Runtime cwd independence
- No caller exposure of migration internals
