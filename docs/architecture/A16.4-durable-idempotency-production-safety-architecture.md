# A16.4 - Portfolio Workspace Durable Mutation Idempotency Production Safety Architecture

## Document Control

- Slice: A16.4
- Scope: Architecture and production-safety review for durable mutation idempotency
- Repository: saurabh-product-os
- Published baseline reviewed: `origin/main`
- Status: READY - superseded by A16.4c/A16.5b implementation and live validation

## Executive Summary

Portfolio Workspace is not ready for public mutation exposure until durable idempotency is integrated with public routes and public retry/abuse policy is validated. The current release candidate has production authorization for the current internal initialize/get host surface and adds the durable idempotency table, port, transaction boundary, replay contract, and PostgreSQL 17 live validation.

The canonical architecture is:

Presentation + Application port + Infrastructure adapter.

Presentation owns transport extraction and safe response mapping. Application owns the idempotency contract and mutation orchestration boundary. Infrastructure owns PostgreSQL persistence. Domain remains unaware of idempotency.

The most important implementation requirement is atomicity: idempotency reservation, aggregate mutation/save, and idempotency completion must be coordinated as one PostgreSQL transaction for public mutation safety. The current `PortfolioExecutionRepository` port is revision-aware, but not transaction-scoped, so implementation must add the smallest Portfolio Workspace-specific atomic mutation capability rather than relying on separate reserve/save/complete calls.

## Current Command Context Assessment

`PortfolioExecutionCommandContext` contains:

- `commandId`;
- `correlationId`;
- `actorReference`;
- `occurredAt`.

The command context is operation-specific. It is supplied by the trusted host/presentation command-context factory and is carried into aggregate-produced facts. The Application Result correlation is derived from the returned fact.

`commandId` is a trusted operation audit identifier, not a client-controlled retry key. `correlationId` is observational tracing metadata, not a durable idempotency key. `actorReference` is audit provenance, not authorization proof. `occurredAt` is operation time, not retry identity.

Decision:

`commandId != durable idempotency key`.

## Threat Model

Durable idempotency must handle:

- client retry after timeout;
- duplicate browser/mobile submission;
- network or load-balancer replay;
- server commit followed by lost response;
- concurrent identical requests with the same key;
- same key with different payload;
- same key from different principals;
- same key across different operations;
- process restart between write and response;
- database transaction failure;
- optimistic-concurrency conflicts;
- replay after aggregate state has advanced;
- malicious key guessing or collision attempts;
- retention/expiry;
- abandoned in-progress reservations.

Required behavior:

- execute the intended mutation at most once per approved idempotency identity;
- replay a stored successful response for an identical completed request;
- reject same-key/different-request collisions safely;
- never use process memory for correctness;
- never bypass authorization during replay;
- never treat `commandId` or `correlationId` as retry identity.

## Ownership Decision

Selected model:

Presentation + Application port + Infrastructure adapter.

Responsibilities:

- Presentation normalizes the external idempotency input and maps idempotency outcomes to safe transport responses.
- Application owns the Portfolio Workspace idempotency contract, mutation orchestration, and technology-neutral failures.
- Infrastructure implements durable PostgreSQL storage and transaction coordination.
- Domain owns business invariants only and remains idempotency-unaware.

Rejected:

- Presentation-only: cannot survive process restart or multi-instance concurrency.
- Infrastructure-only: would hide business operation scope and replay semantics from Application.
- Domain-owned: would leak retry/transport/persistence concerns into aggregate behavior.
- Generic framework: unnecessary and outside Portfolio Workspace scope.

## External Key Contract

Future public mutations must require a caller-supplied external idempotency key. Presentation may extract it from a transport header such as `Idempotency-Key`, but Application and Domain must not know the header name.

Contract:

- client-generated for public mutations;
- required for public mutations;
- optional only for controlled internal non-public handlers that make no retry guarantee;
- normalized by trimming and rejecting empty values;
- bounded length;
- restricted to a safe printable token format;
- expected to have high entropy;
- raw key must not be persisted or logged;
- persistence stores a cryptographic hash of the key.

Exact length and character limits may be finalized in the implementation contract, but they must be deterministic and test-covered.

## Idempotency Identity / Scope

The durable identity is scoped, not global.

Canonical scope:

- pseudonymous authorization resource reference;
- operation name;
- operation resource identity;
- external idempotency key hash.

This allows the same raw key to be safely reused by different principals, different operations, or unrelated resources without cross-user leakage. It also prevents one principal from probing another principal's idempotency records.

The operation resource identity should include the execution ID for execution-scoped mutations. Initialization should use the requested execution ID because the aggregate does not exist before creation.

## Request Fingerprinting Decision

A deterministic request fingerprint is required to detect:

same idempotency identity + different semantic request.

Fingerprint inputs:

- operation name;
- presentation contract version;
- pseudonymous authorization resource reference;
- operation resource identity;
- normalized semantic request payload.

Fingerprint exclusions:

- `correlationId`;
- host-generated `commandId`;
- `occurredAt`;
- transient transport headers;
- request object ordering;
- raw external idempotency key.

Canonical serialization must be stable and key-ordered. Hashing should use a standard algorithm such as SHA-256. The stored fingerprint should be a hash, not raw request contents.

## Durable Record Design

Minimum conceptual record:

- record identity or scope hash;
- record version;
- operation;
- authorization resource reference;
- resource identity;
- idempotency key hash;
- request fingerprint algorithm and value;
- state;
- original command ID for audit linkage;
- original correlation ID for replayed response semantics;
- presentation response/replay payload;
- created timestamp;
- completed timestamp;
- updated timestamp;
- expiry timestamp.

Initial states:

- `pending` or `reserved`;
- `completed` or `succeeded`.

A permanent `failed` state is not required initially. Failures should be released or allowed to expire unless a later product requirement proves failure replay is needed.

Raw idempotency keys must not be stored.

## Replay Semantics

A completed matching request must not rerun the Application Service or reconstruct the response from current aggregate state.

Decision:

Return the stored presentation-safe response payload for the original successful mutation.

Rationale:

- prevents a second Domain mutation/fact;
- handles lost-response retries after a committed mutation;
- remains correct even if the aggregate has since advanced;
- avoids exposing repository revision or database internals.

The replay payload is a versioned presentation artifact, not a Domain Fact and not a database row. If the presentation response version changes, compatibility must be handled explicitly.

## Concurrent Duplicate Semantics

PostgreSQL must enforce uniqueness for the scoped idempotency identity.

Behavior:

- first request creates the reservation and owns execution;
- second concurrent request with the same identity and same fingerprint observes in-progress state;
- second request must not execute the mutation;
- if the first completes, later identical retries replay the stored successful response;
- if the same identity has a different fingerprint, return a safe conflict.

No correctness may depend on an in-memory mutex or single API instance.

## Atomicity / Transaction Requirement

Production-safe public mutation idempotency cannot be achieved with independent non-transactional steps:

1. reserve idempotency;
2. save aggregate;
3. complete idempotency.

If the process dies after aggregate save but before idempotency completion, a retry cannot reliably know whether to replay, retry, or reject without risking duplicate mutation or stuck reservations.

Required architecture extension:

Add the smallest Portfolio Workspace-specific atomic mutation capability so idempotency reservation, aggregate load/save, and idempotency completion can commit or roll back together in one PostgreSQL transaction.

This must not become a generic transaction framework. It should be a bounded Application/Infrastructure contract for Portfolio Workspace mutation orchestration, with Infrastructure providing the PostgreSQL transaction implementation.

## Optimistic Concurrency Relationship

Idempotency and optimistic concurrency solve different problems.

Idempotency:

- same intended client mutation should execute at most once.

Optimistic concurrency:

- stale aggregate revisions must not overwrite newer state.

Both remain required. Idempotency must not suppress legitimate concurrency conflicts from distinct idempotency keys. A stale-save conflict should not be cached as a successful replay unless a future contract deliberately and safely defines failure replay.

## Command ID Relationship

One durable idempotency identity should bind to the original trusted command ID created for the first execution attempt.

Rules:

- clients do not control `commandId`;
- replay should not create a new Domain Fact;
- stored replay payload may preserve the original correlation/result semantics;
- observability may separately record the current retry's correlation, but response replay should remain deterministic.

`commandId` remains audit/correlation metadata, not the external idempotency key.

## Authorization Interaction

Authorization must occur before idempotency replay or mutation execution.

Rules:

- unauthorized callers must not learn whether another principal has used a key;
- the scoped idempotency identity includes the pseudonymous authorization resource;
- request bodies cannot assert authorization ownership;
- replay must not bypass current authorization checks;
- authorization-resource changes over time must be handled explicitly before replaying a protected response.

For initialization, authorization produces the trusted resource reference. For existing executions, authorization must first resolve the persisted resource and authorize the principal before idempotency replay is allowed.

## Error Taxonomy

Future technology-neutral categories:

- missing required idempotency key;
- malformed idempotency key;
- fingerprint mismatch;
- request already in progress;
- idempotency storage unavailable;
- unsupported idempotency record version;
- corrupt idempotency record;
- idempotency state transition conflict;
- internal idempotency contract failure.

Presentation may map these to transport statuses such as bad request, conflict, in-progress, unavailable, or internal error. Domain and Application must not contain HTTP status codes.

## Failure Caching Policy

Initial policy:

- cache/replay successful committed mutation responses;
- do not cache input validation failures;
- do not cache authentication failures;
- do not cache authorization failures;
- do not cache persistence unavailable failures;
- do not cache internal errors;
- do not cache optimistic-concurrency conflicts as successes;
- do not cache Domain rejections unless a later use-case-specific decision proves replaying a failure is required and safe.

If a mutation fails before commit, the reservation should roll back or be released. Abandoned reservations require expiry/recovery handling.

## Retention / Expiry Decision

Retention must be product/configuration policy, not hard-coded architecture.

Requirements:

- completed records must remain at least for the supported client retry window;
- pending records must expire or be recoverable;
- cleanup must not delete records still needed for replay;
- raw keys and sensitive payloads must not be retained unnecessarily;
- audit retention is separate from idempotency replay retention.

After expiry and cleanup, key reuse may be allowed only according to documented policy.

## Database Schema Impact

Durable idempotency requires a new PostgreSQL table.

Conceptual table:

`portfolio_workspace_idempotency_records`

Required characteristics:

- scoped primary key or scope hash;
- unique constraint over authorization resource, operation, resource identity, and key hash, or an equivalent deterministic scope hash;
- record version;
- request fingerprint columns;
- state;
- versioned replay payload;
- safe timestamps;
- expiry index.

No migration, Drizzle schema, or mapper is created in A16.4.

## Application Port Design

Application needs a narrow Portfolio Workspace idempotency contract. It should not be a generic key-value store.

Conceptual operations:

- reserve or observe an idempotency identity;
- complete a successful mutation with replay payload;
- release or abandon a failed reservation where safe;
- report replay, fingerprint conflict, in-progress, storage unavailable, and corrupt/unsupported record failures.

Because atomicity is mandatory, the final design also needs a bounded transaction-capable mutation orchestration contract. That contract should let the idempotency store and repository participate in the same PostgreSQL transaction without exposing Pool, Drizzle, SQL, or transaction handles to Domain.

## Presentation / Handler Sequence

Future public mutation sequence:

1. parse transport request;
2. verify/authenticate principal outside Portfolio Workspace;
3. authorize principal for the operation/resource;
4. normalize and validate external idempotency key;
5. create deterministic request fingerprint;
6. reserve or observe durable idempotency identity;
7. if completed and matching, replay stored response;
8. if in progress, return safe in-progress/conflict response;
9. if fingerprint mismatch, return safe conflict;
10. create trusted command context for first execution;
11. execute Application mutation and aggregate save inside the atomic persistence boundary;
12. complete idempotency record with versioned replay payload inside the same transaction;
13. return the presentation response.

Current internal initialize/get handlers do not change in A16.4.

## Multi-Instance / Restart Safety

The design is safe only if PostgreSQL is authoritative for:

- reservation uniqueness;
- in-progress state;
- completed replay payload;
- transaction commit/rollback;
- expiry/recovery state.

Multiple API instances, restarts, lost responses, and horizontal scaling must not depend on process memory.

## Security / Privacy Assessment

Requirements:

- do not store raw idempotency keys;
- hash key material before persistence;
- store pseudonymous authorization resource references, not provider tokens;
- store request fingerprints rather than raw request payload when possible;
- version and minimize replay payloads;
- avoid logging raw keys, request bodies, credentials, or provider identifiers;
- include authorization resource in scope to prevent cross-user probing;
- require future rate limiting or quota controls outside this slice to limit high-cardinality key abuse.

## Observability Boundary

A16.4 does not implement observability.

Future safe signals:

- reservation created;
- replay served;
- fingerprint conflict;
- duplicate in progress;
- completion recorded;
- stale pending record observed;
- storage unavailable;
- unsupported/corrupt record.

Signals must omit raw keys, raw request payloads, credentials, and provider IDs.

## Local Future Idempotency Work Assessment

The dirty worktree contains uncommitted idempotency drafts under `apps/api` and `packages/infrastructure`, plus uncommitted schema/migration/test changes.

Assessment:

- API idempotency contracts: partially aligned with scoped keys, fingerprints, operation vocabulary, and replay payloads, but premature until the atomic Application/Infrastructure boundary is approved.
- Infrastructure persistence contracts/store/mapper: partially aligned with PostgreSQL reservation and replay concepts, but premature because independent reserve/complete calls do not by themselves satisfy the required aggregate-save atomicity.
- Schema/migration changes: premature/unsupported for this review slice and must not be treated as committed baseline.
- Tests: useful future evidence candidates, but not authoritative for A16.4 because they are uncommitted and may encode incomplete semantics.

No local idempotency work is approved, staged, or modified by this document.

## Recommended Implementation Sequence

1. Define Application idempotency contracts, error taxonomy, scope, fingerprinting, replay payload, and tests.
2. Add PostgreSQL idempotency schema/migration/mapper/store with reservation, replay, fingerprint conflict, expiry, and corruption tests.
3. Add the bounded atomic Portfolio Workspace mutation orchestration capability so idempotency and aggregate persistence share one transaction.
4. Integrate idempotency into public mutation presentation handlers.
5. Add database-free handler and boundary tests for replay/conflict/in-progress behavior.
6. Add PostgreSQL live tests for duplicate retry, concurrent duplicate, lost-response replay, restart safety, and fingerprint mismatch.
7. Add hosted CI coverage for the live idempotency paths before public mutation exposure.

Public mutation remains NO-GO until durable idempotency is implemented and live validated.
