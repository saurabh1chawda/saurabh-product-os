# A16.4a - Durable Idempotency Application Contracts

## Document Control

- Slice: A16.4a
- Scope: Portfolio Workspace durable idempotency Application contracts
- Repository: saurabh-product-os
- Status: READY FOR A16.4b

## Executive Summary

A16.4a introduces only transport-neutral Application contracts for future durable mutation idempotency. It does not implement persistence, PostgreSQL schema, atomic transaction orchestration, handler integration, retries, public routes, or cleanup workers.

The contracts live under `packages/portfolio-workspace-application/src/idempotency` because the Application layer owns technology-neutral ports and error vocabulary while Infrastructure implements durable storage later.

## Package Placement

The idempotency boundary is Application-owned:

```text
Presentation
  -> Portfolio Workspace Application idempotency contracts
  -> Infrastructure implementation
  -> PostgreSQL
```

Domain remains unaware of idempotency. API/Presentation remains responsible for transport extraction and future request canonicalization.

## Operation Vocabulary

The stable operation vocabulary covers exactly the nine mutations:

- `initialize-execution`
- `begin-execution`
- `activate-work-item`
- `complete-work-item`
- `cancel-work-item`
- `accept-candidate`
- `reject-candidate`
- `complete-execution`
- `cancel-execution`

Get-by-ID is a query and is intentionally excluded.

## Identity and Key Hash Boundary

`PortfolioWorkspaceIdempotencyIdentity` contains:

- pseudonymous authorization resource reference;
- mutation operation;
- operation resource identity;
- SHA-256 idempotency key hash.

The Application contract never accepts a raw external idempotency key. Presentation must normalize and hash the external key before constructing the Application identity.

## Request Fingerprint

`PortfolioWorkspaceIdempotencyRequestFingerprint` is an opaque SHA-256 fingerprint. It represents already-normalized semantic request identity.

It must not include:

- command ID;
- correlation ID;
- occurredAt;
- authorization tokens;
- sessions;
- raw principal claims;
- transient headers.

Request canonicalization remains deferred to Presentation integration.

## Durable State and Observation Semantics

The durable state vocabulary is intentionally minimal:

- `reserved`
- `completed`

Reservation/observation outcomes are explicit:

- acquired for first execution;
- replay available;
- in progress;
- fingerprint mismatch.

Fingerprint mismatch and in-progress duplicate are typed observations, not generic infrastructure failures.

## Replay Payload

`PortfolioWorkspaceIdempotencyReplayPayload` stores a versioned, presentation-safe response payload. It does not expose aggregates, repositories, command context, raw facts, database rows, or HTTP framework objects.

The replay payload is designed for exact response replay after a successful committed mutation. It is not a persistence DTO for Application Result classes.

## Error Taxonomy

The Application-owned port failure taxonomy includes:

- persistence unavailable;
- corrupt durable record;
- unsupported idempotency record version;
- invalid state transition;
- orchestration contract failure.

Constructor/contract validation failures use `PortfolioWorkspaceIdempotencyContractError`.

No error exposes SQL, PostgreSQL codes, table names, connection strings, raw keys, or provider identity details.

## Original Command and Correlation Binding

`PortfolioWorkspaceIdempotencyCommandBinding` stores only:

- original trusted command ID;
- original correlation ID.

It intentionally does not persist the whole `PortfolioExecutionCommandContext`. Actor audit provenance remains part of command-context/fact behavior; idempotency only needs the minimum binding required for replay and audit linkage.

## Expiry Metadata

`PortfolioWorkspaceIdempotencyExpiryMetadata` stores:

- createdAt;
- expiresAt;
- optional completedAt.

Retention duration remains product/configuration policy. Cleanup, polling, and recovery are deferred.

## Durable Port

`PortfolioWorkspaceIdempotencyPort` defines:

- reserve-or-observe identity;
- complete successful mutation with replay payload.

This is a contract only. It is not safe to use as three independent commits around current mutation services.

## Atomicity Warning

Public mutation safety still requires A16.4c atomic orchestration:

```text
reserve idempotency
  + aggregate load/mutation/save
  + complete idempotency
  = one PostgreSQL transaction
```

Current mutation services must not be modified to call reserve, save, and complete independently.

## Public API

The production package root now exports only stable idempotency contract values, errors, outcomes, and the port interface. It does not export PostgreSQL schema, Drizzle, Pool, transaction handles, raw keys, transport requests, or test doubles.

## Deferred Scope

Deferred to later slices:

- PostgreSQL schema and migration;
- Infrastructure adapter;
- transaction-aware mutation orchestration;
- handler integration;
- public routes;
- retry behavior;
- retention cleanup;
- observability;
- live PostgreSQL validation.
