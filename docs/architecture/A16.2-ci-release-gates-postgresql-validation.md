## 2. Purpose

A16.2 converts the Node 22 and PostgreSQL release validation proven manually in A16.1 into a deterministic GitHub Actions release gate.

It originally did not implement authentication, authorization policy, idempotency, public HTTP routes, observability, deployment infrastructure, Domain behavior, Application behavior, repository redesign, migration redesign, dependency upgrades, or release commits. Later A16 slices implemented production authorization for the internal Portfolio Workspace API boundary and durable mutation idempotency persistence/orchestration; this document now records the current CI gate set for those implemented capabilities.

## 3. Existing CI Baseline

Repository inspection found:

- `.github` existed only for issue and pull-request templates.
- No GitHub Actions workflow existed.
- No CI job ran build, lint, typecheck, tests, or live PostgreSQL validation.
- No PostgreSQL integration service was represented in repository CI configuration.

Because there was no existing workflow to extend, A16.2 adds one narrow workflow:

`.github/workflows/portfolio-workspace-release-validation.yml`

## 4. CI Architecture Decision

The workflow uses two jobs:

1. `Release Validation`
2. `Portfolio Workspace PostgreSQL Integration`

This preserves the conceptual separation from A16.1:

- database-free repository validation proves normal build/lint/typecheck/test behavior without requiring PostgreSQL;
- the live PostgreSQL job proves the explicit repository, durable idempotency, runtime, and API host integration gates against PostgreSQL 17.

The workflow does not rerun the full monorepo in the live job. The live job uses the package-owned integration commands that A16.1 proved manually.

## 5. Toolchain Pinning

Both jobs use:

- `actions/setup-node@v4`
- `node-version-file: .nvmrc`
- Corepack activation
- `corepack prepare pnpm@11.9.0 --activate`

Both jobs verify:

- `node --version`
- `pnpm --version`
- pnpm version equals `11.9.0`

The workflow does not change the repository Node engine, pnpm version, or dependency versions.

## 6. Frozen Lockfile Gate

Both jobs run:

`pnpm install --frozen-lockfile`

CI must fail if the lockfile is stale or dependency resolution would mutate workspace metadata.

The existing `expect-type` override remains unchanged.

## 7. Static Release Validation Gate

The database-free job runs:

- `pnpm build`
- `pnpm lint`
- `pnpm typecheck`
- `pnpm test`

It does not set `PORTFOLIO_WORKSPACE_TEST_DATABASE_URL`.

This keeps root tests deterministic without PostgreSQL. Existing live tests remain present, but default package tests skip live PostgreSQL paths when the live database URL is absent.

## 8. PostgreSQL 17 Live Gate

The live job uses a GitHub Actions service container:

- image: `postgres:17`
- database: `portfolio_workspace_test`
- user: `portfolio_workspace_ci`
- password: CI-local test password

The job sets:

`PORTFOLIO_WORKSPACE_TEST_DATABASE_URL`

The database name contains `test` and does not contain `prod` or `production`, satisfying the live harness safety checks.

The job does not require production credentials or external secrets.

The live job runs:

```powershell
pnpm --filter @career-companion/infrastructure test:integration:portfolio-workspace-idempotency

```

Expected current A16.2l-proven coverage:

- repository live suite: 17 tests

These counts are recorded here for release evidence but are not hard-coded into the workflow.

## 10. Migration Metadata Isolation

A16.1a and A16.1b remain compatible with CI:

- live suites create isolated temporary application schemas;
- migration metadata physical relation is `drizzle.__portfolio_workspace_migrations_<hash>`;
- the hash derives from PostgreSQL `current_schema()`;
- live harness schema names are below PostgreSQL's 63-byte identifier limit;
- cleanup is per temporary schema and per schema-derived metadata table;
- one live suite must not drop another live suite's migration metadata.

The CI workflow does not serialize tests merely to avoid concurrency.

## 11. Trigger Policy

The workflow runs on:

- pull requests;
- pushes to `main`;
- manual `workflow_dispatch`.

This is conservative and avoids inventing release branches. It also avoids `pull_request_target`.

## 12. Path Filter Decision

No path filtering is used.

Reasoning:

- A13/A16 live-gate policy covers several cross-cutting changes, including Domain serialization, repository contracts, mapper, schema/migration, adapter, revision semantics, runtime persistence behavior, API host integration, and migration metadata logic.
- The current repository is still in release-candidate formation with broad uncommitted changes.
- Running the live gate on every PR is simpler and safer than premature path optimization.

Path filtering may be reconsidered only after CI has produced stable green history.

## 13. Cache Decision

The workflow uses `actions/setup-node` pnpm dependency caching.

It does not cache PostgreSQL state, generated database schemas, or migration metadata.

Frozen install remains authoritative and must fail on lockfile drift.

## 14. Security and Permissions

Workflow security posture:

- `permissions: contents: read`
- no `pull_request_target`
- no write token permissions
- no production secrets
- PostgreSQL credentials are CI-local and disposable
- no external secret manager introduced
- no `continue-on-error` on release-critical gates

The workflow does not echo a production database URL. The CI test database URL contains only disposable service credentials.
