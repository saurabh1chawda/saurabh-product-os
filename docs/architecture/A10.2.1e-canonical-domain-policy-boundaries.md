# A10.2.1e - Canonical Domain Policy Boundaries

## 1. Purpose

This document defines the canonical Portfolio Workspace domain policy boundary before policy implementation begins.

It applies to the Portfolio Workspace bounded context after completion of:

- Canonical domain vocabulary.
- Supporting entities.
- `PortfolioExecution` behavioral aggregate.
- Immutable Portfolio Workspace domain facts.

This document does not define TypeScript interfaces, classes, repositories, handlers, events, commands, or implementation code.

## 2. Definition

A Domain Policy represents reusable business decision logic derived from established domain facts and observable domain state.

A Portfolio Workspace policy may answer questions such as:

- Whether a work item is eligible for completion.
- Whether an artifact candidate is eligible for acceptance.
- Whether aggregate state is internally consistent.
- Whether no further domain action is recommended.

A Domain Policy is not:

- Orchestration.
- Workflow.
- Infrastructure.
- Persistence.
- Messaging.
- Projection.
- Integration.
- Application service behavior.

Policies MUST remain bounded-context-specific unless future architecture review authorizes a shared abstraction.

## 3. Responsibilities

Policies may:

- Evaluate immutable domain facts.
- Evaluate read-only aggregate state.
- Evaluate supporting entity state through the aggregate boundary.
- Return business recommendations.
- Return immutable policy decisions.
- Explain why a domain action is recommended, blocked, or unnecessary.

Policies MUST NOT:

- Modify aggregates.
- Mutate entities.
- Produce or publish facts.
- Publish events.
- Load repositories.
- Call APIs.
- Coordinate workflows.
- Perform retries.
- Schedule work.
- Trigger side effects.
- Own application authorization.
- Own UI behavior.
- Invoke AI providers.

Policy evaluation is advisory or validating. Domain state changes remain owned by `PortfolioExecution` operations.

## 4. Dependencies

Allowed dependencies:

- Portfolio Workspace value objects.
- Portfolio Workspace domain facts.
- `PortfolioExecution` read-only state.
- Supporting entity read-only state.
- Portfolio Workspace domain errors where policy rejection must be represented.

Forbidden dependencies:

- Repositories.
- Ports.
- Messaging.
- Persistence.
- HTTP.
- UI.
- AI.
- External services.
- Browser automation.
- Workflow engines.
- Application services.
- Infrastructure adapters.

Policies must not introduce reverse dependencies into Planning packages.

## 5. Outputs

The canonical policy output is an immutable policy decision.

Policy output may represent:

- `PolicyDecision`: a deterministic business decision.
- `Recommendation`: a suggested next domain action.
- `NoAction`: an explicit statement that no domain action is recommended.

Policy output may include:

- Decision name.
- Decision result.
- Reason.
- Relevant aggregate reference.
- Relevant work-item, candidate, or artifact reference.
- Relevant fact references or fact types.

Policy output MUST NOT define executable commands.

Policy output MUST NOT:

- Execute aggregate methods.
- Schedule work.
- Publish messages.
- Persist records.
- Trigger integrations.
- Contain UI display metadata.

## 6. Policy Lifetime

Domain policies are:

- Stateless.
- Immutable.
- Deterministic.
- Pure.
- Dependency-free except for approved domain model imports.

Identical policy inputs MUST produce identical policy outputs.

Policies must not retain execution history, cache repository data, store pending decisions, or accumulate mutable state.

## 7. Policy Taxonomy

Portfolio Workspace may define the following policy categories when implementation evidence justifies them.

| Category | Purpose | Inputs | Must not own |
| --- | --- | --- | --- |
| Completion policies | Evaluate whether work-item or execution completion is recommended or valid. | Aggregate read-only state; work-item state; relevant facts. | Completion mutation, terminal outcome derivation, scheduling. |
| Acceptance policies | Evaluate whether an artifact candidate is ready for human acceptance. | Candidate state; accepted-artifact state; relevant facts; approval reference where available. | Approval workflow, artifact creation, AI validation. |
| Consistency policies | Evaluate whether aggregate-owned collections and lifecycle state remain coherent. | Aggregate read-only state; entity identities; relevant facts. | Duplicate registration behavior, repository checks, repair workflows. |
| Validation policies | Evaluate deterministic domain preconditions that may be reused across aggregate operations. | Value objects; aggregate read-only state; entity state. | Transport validation, authorization, persistence schema validation. |

Policies for initialization, blocking, unblocking, progress, terminal outcome, or feedback remain deferred until the corresponding behavior is implemented or canonicalized.

## 8. Relationship Matrix

| Component | Relationship to policies | Boundary |
| --- | --- | --- |
| `PortfolioExecution` aggregate | Owns mutable state and domain operations. May call policies for deterministic decisions. | Policies must not mutate the aggregate. |
| Supporting entities | Provide read-only state for policy evaluation through aggregate ownership. | Policies must not coordinate entities independently. |
| Domain facts | Provide immutable evidence of completed domain decisions. | Policies may evaluate facts but must not publish or retain them. |
| Application layer | May invoke policies and decide whether to call aggregate operations. | Authorization, orchestration, retries, and idempotency remain application concerns. |
| Projections | May later consume aggregate state and facts to derive read models. | Policies are not projections and must not own presentation shape. |
| Integrations | May later consume accepted artifacts or outcomes through application orchestration. | Policies must not call external services or produce integration events. |

## 9. Examples

Conceptual examples only:

- A completion policy evaluates a work item and returns a decision that completion is blocked because the work item is not active.
- An acceptance policy evaluates a candidate and returns a recommendation that human review is required before acceptance.
- A consistency policy evaluates aggregate-owned identities and returns no action when no duplicate identity is present.
- A validation policy evaluates whether a candidate acceptance request references a known candidate.

These examples do not authorize command schemas, policy registries, handlers, or executable workflows.

## 10. Deferred Work

The following remain explicitly deferred:

- Policy execution framework.
- Policy registry.
- Policy engine.
- Shared policy abstractions.
- Scheduling.
- Integration.
- Projection implementation.
- Repository-backed policy evaluation.
- Application orchestration.
- Workflow automation.
- AI-assisted policy evaluation.

These are not gaps in A10.2.2 policy implementation. They require future implementation evidence and architecture review.

## 11. Final Decision

Portfolio Workspace domain policies may be implemented as deterministic, immutable, package-local business decision logic.

They may evaluate aggregate state and immutable domain facts.

They must not own mutation, orchestration, persistence, messaging, UI, AI, or external side effects.
