## Application Contracts

The Application package owns transport-neutral durable idempotency contracts:

- mutation operation vocabulary for the nine mutations;
- SHA-256 key hash value object;
- request fingerprint value object;
- scoped identity using authorization resource reference, operation, resource identity, and key hash;
- original command/correlation binding;
- expiry metadata;
- replay payload;
- reservation observations;
- completion result;
- idempotency port and safe errors.

The Application contract does not expose:

- raw idempotency keys;
- HTTP header names;
- PostgreSQL, Drizzle, SQL, Pool, or transaction types;
- Domain aggregates/facts as replay payloads;
- sessions, JWTs, provider claims, or credentials.

## API Key and Fingerprint Semantics

The API/presentation idempotency contract accepts the raw client key because that value is presentation-adjacent. The key is:

- string-only;
- trimmed before validation;
- nonblank;
- maximum 128 characters;
- limited to safe token characters: letters, digits, `.`, `_`, `:`, `-`;
- case-sensitive.

The API contract calculates SHA-256 fingerprints over canonical mutation intent. Fingerprints exclude volatile command context and tracing values:

- `commandId`;
- `correlationId`;
- `occurredAt`;
- actor/session/provider data;
- unrelated transport metadata.

The current helper covers initialization intent. Later handler integration must add explicit fingerprint intent builders for the remaining eight mutations rather than hashing arbitrary request bodies.

## Scope Identity

Durable uniqueness is:

```text
authorization resource reference
+ operation
+ resource identity
+ idempotency key hash
```

The Infrastructure mapper derives a deterministic `scope_hash` from that identity and stores the key hash separately for audit/debugging without storing the raw key.

This prevents replay across:

- different authorization resources;
- different operations;
- different execution identities;
- different work-item/candidate/artifact resource identities;
- different client idempotency keys.

`commandId` and `correlationId` are intentionally excluded from scope.

## Constraints and Indexes

The schema enforces:

- primary key on `scope_hash`;
- uniqueness of operation + authorization resource + resource identity + key hash;
- positive record version;
- valid status values;
- SHA-256 fingerprint algorithm;
- 64-character lowercase hex fingerprint value;
- 64-character lowercase hex key hash;
- complete replay payload fields when status is `succeeded`.

No JSONB indexes, projection tables, fact tables, audit tables, or child aggregate tables are added.

## Store Semantics

`PostgresPortfolioWorkspaceIdempotencyStore.reserve()` atomically inserts a reserved record with `onConflictDoNothing`.

Observable outcomes:

- new key/scope/fingerprint: `first-execution-reserved`;
- existing same fingerprint and `reserved`: `in-progress`;
- existing same fingerprint and `succeeded`: replay payload returned;
- existing different fingerprint: deterministic mismatch;
- storage or corrupt mapping failure: safe persistence error.

`completeSuccess()` updates only the matching scope, fingerprint, and `reserved` status to `succeeded`.

`release()` deletes only the matching scope, fingerprint, and `reserved` status, supporting retry after a failed mutation where no success committed.

## Transaction Architecture

`PostgresPortfolioWorkspaceIdempotentMutationOrchestrator` establishes the foundation for atomic mutation idempotency. It runs reservation, transaction-bound `PostgresPortfolioExecutionRepository` mutation work, and replay completion inside one Drizzle transaction.

If the mutation fails, it rolls back the reservation. If replay completion fails, it rolls back aggregate persistence. Replay, in-progress, and mismatch observations do not execute Domain behavior.

This preserves the repository port boundary because transaction objects remain Infrastructure-owned and do not enter Domain or Application contracts.

## Replay Payload

Application replay payloads are versioned and JSON-safe. They are intended to contain the successful presentation result needed for replay.

Replay does not:

- create a new command context;
- produce a new Domain fact;
- save the aggregate;
- expose repository revision;
- expose Domain aggregate objects.

The original success correlation remains part of the replay data.

## Privacy and Security

The implementation uses SHA-256 hashes for key identity and scope identity. Raw idempotency keys are limited to the API/presentation boundary and are not persisted.

Durable records store pseudonymous authorization resource references but not actor references, sessions, JWT claims, cookies, credentials, SQLSTATE, SQL text, or stack traces.

Authorization remains a prerequisite for future handler integration. Unauthorized requests must not reserve idempotency keys and must not receive replay payloads.
