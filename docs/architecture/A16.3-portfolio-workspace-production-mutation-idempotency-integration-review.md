# A16.3 - Portfolio Workspace Production Mutation Idempotency Integration Review

## Document Control

- Status: Architecture reviewed; superseded by A16.3a/A16.4c/A16.5b implementation and live validation
- Scope: Portfolio Workspace mutation idempotency architecture and release readiness
- Repository state reviewed: uncommitted A16 idempotency work is present
- Production code changes in this slice: none
- Public mutation readiness: NO-GO

## Executive Summary

Durable idempotency is required before any public Portfolio Workspace mutation endpoint is exposed. The current Domain, Application, repository revision, runtime, and internal handler architecture do not by themselves provide durable client retry protection.

The correct architecture is a client-supplied opaque idempotency key scoped by trusted server-owned metadata: authorization resource reference, mutation operation, resource identity, and key hash. The raw key must be accepted only at the presentation boundary, validated, hashed, and excluded from durable persistence.

Request fingerprinting is required. A retry with the same key and same mutation intent may replay the original successful result. A retry with the same key and different mutation intent must return a deterministic idempotency conflict.

Correct public mutation idempotency requires the idempotency reservation, aggregate mutation, aggregate save, and replay-result completion to commit atomically in one PostgreSQL transaction. Optimistic concurrency remains necessary but solves a different problem.

Current release-candidate work now contains architecture-aligned contracts and Infrastructure pieces for durable idempotency, including Application-facing hashed identity contracts, an Infrastructure PostgreSQL idempotency table/store, and a transaction-bound orchestrator. A16.2l accepts dedicated PostgreSQL 17 live idempotency validation at 13/13. Public mutation exposure remains blocked until provider authentication, public route integration, operational controls, and public retry/abuse validation are complete.

## Existing Command Identity Semantics

`commandId` is part of `PortfolioExecutionCommandContext`. A15.2 creates it from a trusted presentation command-context factory for each accepted command. It identifies the domain command context carried by the produced fact. It is operation-specific provenance, not a durable transport retry key.

## Existing Correlation Semantics

`correlationId` is also part of command context and appears in Application Results. It exists for request tracing and response correlation. It may be supplied as a hint by transport and normalized by presentation code. It must not be used as an idempotency key because clients and intermediaries may reuse, omit, or regenerate correlation values for diagnostics.

## Existing Optimistic Concurrency Semantics

The Application-owned repository returns `LoadedPortfolioExecution` with a persistence revision. Mutating services pass the loaded revision into `save`. PostgreSQL save uses compare-and-swap semantics to avoid lost updates. Revision is Infrastructure/Application persistence metadata, not Domain state.

## Why Current Semantics Are Not Durable Idempotency

Command IDs are generated per command attempt. Correlation IDs trace attempts. Repository revision detects stale writes. None of those persists a client retry intent and none can replay a lost success response. Without a durable idempotency record, a retry after success can produce a lifecycle or duplicate error even though the user's original mutation succeeded.

## Idempotency Ownership Decision

The external idempotency key is client-supplied and opaque. The server owns validation, normalization, hashing, scoping, authorization, request fingerprinting, storage, replay, and conflict semantics.

Server-generated keys do not protect retries after the client loses the response. Fully derived keys are too sensitive to payload drift and can accidentally collapse independent user intent. The selected model is hybrid: client key plus trusted server-owned scope metadata.

## Idempotency Key Contract

The presentation/API boundary should accept an opaque key, conceptually equivalent to `Idempotency-Key`.

Required contract:

- string only;
- trim leading/trailing whitespace before validation;
- reject blank values;
- maximum length: 128 characters;
- allowed characters: ASCII letters, digits, `.`, `_`, `:`, `-`;
- case-sensitive;
- reject control characters;
- do not embed business meaning;
- do not place the key in request bodies when transport metadata is available;
- hash before crossing into durable Application/Infrastructure contracts.

The current API idempotency contract follows this shape.

## Idempotency Scope Decision

Uniqueness is:

```text
authorization resource reference
+ operation
+ resource identity
+ idempotency key hash
```

The same raw key may be reused safely by different users/authorization resources. It may also be reused for different operations or different resource identities without collision. It must not be scoped only by actor string or only by execution ID. Initialization uses the target execution ID as resource identity. Execution mutations use the execution ID plus operation-specific primitive identity where needed.

After expiry, reuse may create a new reservation and the system no longer guarantees replay of the expired result. Retention duration remains a product/operations decision.

## Request Fingerprint Decision

Request fingerprinting is required. The fingerprint must cover canonical mutation intent, not volatile request metadata.

Include:

- idempotency scope;
- presentation contract version;
- operation name;
- execution ID;
- work item ID, candidate ID, accepted artifact ID where applicable;
- initialization references and initial work/candidate definitions;
- other mutation-specific primitive inputs.

Exclude:

- `commandId`;
- `correlationId`;
- `occurredAt`;
- raw headers unrelated to mutation intent;
- sessions, tokens, provider claims;
- unordered raw JSON.

Canonicalization must sort object keys and preserve array order where the array is semantically ordered.

## Durable Record Design

Minimum durable record:

- stable scope hash;
- record version;
- operation;
- pseudonymous authorization resource reference;
- resource identity;
- idempotency key hash;
- request fingerprint algorithm and value;
- status;
- original command ID;
- original correlation ID;
- replay contract version;
- replay response payload;
- created timestamp;
- updated timestamp;
- completed timestamp;
- expiry timestamp.

Do not persist raw idempotency keys, request bodies, Domain aggregates, Domain facts, actor objects, JWT/session/provider objects, SQL errors, stacks, or credentials.

## Application Boundary Decision

Application may own narrow technology-neutral idempotency contracts for hashed key identity, request fingerprint, replay payload, outcomes, and a port. Domain must not depend on idempotency. Existing mutation Application Services should not become individually idempotency-aware unless a later slice proves that is the only viable option.

## Infrastructure Boundary Decision

Infrastructure owns PostgreSQL storage, Drizzle rows, record mapping, unique constraints, durable reservation, replay lookup, and transaction-bound orchestration. Infrastructure must not expose PostgreSQL, Drizzle, rows, or SQL metadata to Domain or Presentation.

## PostgreSQL Schema Decision

A dedicated PostgreSQL table is required. It should be added via a new forward migration, never by rewriting the existing initial PortfolioExecution migration history.

The current uncommitted schema uses `portfolio_workspace_idempotency_records`, a primary scope hash, an operation/resource/key uniqueness constraint, fingerprint constraints, status constraints, replay-payload checks, and an expiry index. That matches the architecture.

## Transaction / Atomicity Assessment

Durable public idempotency cannot be correct without atomic persistence. The unsafe crash window is:

1. reserve idempotency key;
2. mutate and save aggregate;
3. crash before idempotency completion.

That leaves a durable mutation with no replay result. The reverse window, completed idempotency with rolled-back aggregate, can replay a success that never committed.

The correct strategy is one PostgreSQL transaction containing reservation observation, aggregate load/save through a transaction-bound repository, and idempotency completion. A generic transaction manager is not required; a narrow Portfolio Workspace Infrastructure orchestrator is sufficient.

## Concurrent Duplicate Request Semantics

Concurrent same-key/same-fingerprint requests must be deterministic:

- one request wins reservation and executes;
- another sees in-progress while the first is not completed;
- after completion, retry with the same fingerprint replays the stored success;
- no Application Service is invoked for replay;
- no polling loop is required in Application code.

## Same-Key Different-Request Semantics

Same scope/key with a different fingerprint is an idempotency conflict. The system must not replay the previous result and must not execute the new mutation. Presentation should map this to a safe conflict response without exposing stored fingerprints or payloads.

## Replay Result Design

Do not re-execute the Application Service. Do not fabricate a new Domain fact. Persist a dedicated replay payload with a replay contract version and presentation-safe response payload. This is safer than persisting raw Application Result or Domain fact objects and avoids coupling replay storage to HTTP framework internals.

## Failure Persistence / Replay Policy

Authentication failures, invalid request parsing, missing idempotency keys, and authorization denials happen before reservation and should not be stored.

Domain and persistence failures during first execution should normally rollback the reservation so the client can retry with the same key if no durable mutation was committed. Terminal failure replay may be added only for explicitly safe deterministic categories, but the current minimum architecture should persist successful replay payloads first.

## Authentication Ordering

Authentication must happen before idempotency. The handler must receive a trusted principal from the host boundary. No unauthenticated caller should reserve or probe an idempotency key.

## Authorization Ordering

Authorization must happen before reservation and before replay. A caller who is no longer authorized must not receive a stored replay payload. Authorization must use trusted principal and server-resolved resource ownership, not actorReference alone.

## Command Context Interaction

The first execution creates command context exactly once. Its command ID, correlation ID, actor reference, and occurredAt flow to the Domain fact and Application Result. Replay must not create a new command context and must not produce a new fact.

## Correlation-on-Replay Decision

The persisted replay payload should preserve the original successful result correlation. The current retry may also have host-local correlation for diagnostics and response headers if a later presentation slice chooses that, but it must not mutate the persisted replay result.

## Domain Fact Interaction

Facts remain aggregate-produced evidence of real state transitions. On replay:

- no aggregate method is called;
- no new Domain fact is produced;
- no repository save occurs;
- no fact is reconstructed as if new.

Replay is presentation-safe result replay, not Domain event replay.

## Optimistic Concurrency Interaction

Same key/same fingerprint should not cause repeated CAS attempts after success. Different keys targeting the same aggregate revision still rely on repository optimistic concurrency. Idempotency protects duplicate client intent; revision protects competing state transitions.

## Initialization Idempotency Semantics

Initialization is mandatory for idempotency because the response-lost retry case otherwise becomes `already exists` instead of replaying success.

Expected behavior:

- same key/same initialization intent: replay original created response;
- same key/different initialization intent: idempotency conflict;
- different key after first success: normal duplicate execution identity failure;
- concurrent same key: one creates; other sees in-progress or later replay.

## Begin Execution Idempotency Semantics

- same key/same request: replay original started response;
- same key/different execution: idempotency conflict;
- different key after success: normal lifecycle rejection;
- concurrent same key: one executes, one observes in-progress/replay.

## Activate Work Item Idempotency Semantics

- same key/same execution/work item: replay original activation;
- same key/different work item or execution: idempotency conflict;
- different key after success: normal lifecycle rejection;
- concurrent same key: one activates, one observes in-progress/replay.

## Complete Work Item Idempotency Semantics

- same key/same execution/work item: replay original completion;
- same key/different work item or execution: idempotency conflict;
- different key after success: normal lifecycle rejection;
- concurrent same key: one completes, one observes in-progress/replay.

## Cancel Work Item Idempotency Semantics

- same key/same execution/work item: replay original cancellation;
- same key/different work item or execution: idempotency conflict;
- different key after success: normal lifecycle rejection;
- concurrent same key: one cancels, one observes in-progress/replay.

## Accept Candidate Idempotency Semantics

- same key/same execution/candidate/accepted artifact: replay original acceptance;
- same key/different candidate or accepted artifact: idempotency conflict;
- different key after success: normal candidate lifecycle or duplicate artifact rejection;
- concurrent same key: one accepts, one observes in-progress/replay.

## Reject Candidate Idempotency Semantics

- same key/same execution/candidate: replay original rejection;
- same key/different candidate or execution: idempotency conflict;
- different key after success: normal lifecycle rejection;
- concurrent same key: one rejects, one observes in-progress/replay.

## Complete Execution Idempotency Semantics

- same key/same execution: replay original completion;
- same key/different execution: idempotency conflict;
- different key after success: normal lifecycle rejection;
- concurrent same key: one completes, one observes in-progress/replay.

## Cancel Execution Idempotency Semantics

- same key/same execution: replay original cancellation;
- same key/different execution: idempotency conflict;
- different key after success: normal lifecycle rejection;
- concurrent same key: one cancels, one observes in-progress/replay.

## Query-Side Decision

Get Portfolio Execution does not require mutation idempotency. It is read-only, produces no fact, and saves no aggregate. It may still use correlation for tracing.

## Retention / Expiry Decision

Records should be TTL-retained rather than permanent by default, but the exact retention period is a product and operations decision. The architecture must define behavior after expiry: the same key may reserve again, and replay is no longer guaranteed. Cleanup workers are deferred.

## Security / Privacy Assessment

Controls required:

- hash raw keys before persistence;
- scope by pseudonymous authorization resource reference;
- authorize before reservation and replay;
- reject malformed keys;
- avoid logging raw keys by default;
- store only presentation-safe replay payloads;
- exclude tokens, sessions, claims, stacks, SQL, SQLSTATE, raw request bodies, and Domain aggregate JSON;
- avoid exposing fingerprints in public errors.

## Presentation Contract Impact

Future public mutation contracts must require idempotency metadata, expose safe conflict/in-progress/unavailable outcomes, and define replay behavior. They must not add HTTP status semantics to Domain or Application.

Clients may benefit from a replay marker, but replay can also be transparent. If exposed, it should be presentation metadata only.

## Internal Handler Impact

Current internal initialize/get handlers are not idempotency-aware. Public mutation handlers should coordinate idempotency after authentication, request validation, and authorization. Avoid nine copy-pasted implementations; use a narrow explicit coordinator per Portfolio Workspace mutation family, not a generic command bus or service locator.

## Runtime Composition Impact

Runtime composition should remain explicit. Future composition may add a PostgreSQL idempotent mutation orchestrator for API host use. The runtime must not expose Pool, Drizzle, repository internals, idempotency rows, or generic service lookup.

## Repository / Persistence Impact

PortfolioExecutionRepository should remain the aggregate persistence boundary. Do not add idempotency methods to it. Transaction-bound repository construction is acceptable inside Infrastructure orchestration when the orchestrator owns the PostgreSQL transaction.

## Test Strategy

Mandatory future tests:

- key validation and hashing;
- scope canonicalization;
- fingerprint canonicalization;
- same key/same request replay;
- same key/different request conflict;
- concurrent same-key reservation;
- no replay before completion;
- no Application invocation on replay;
- authorization denial before reservation;
- initialization retry replay after lost response;
- aggregate save plus idempotency completion atomic commit;
- mutation failure rollback;
- optimistic concurrency interaction;
- raw-key privacy;
- safe replay/error payloads;
- public presentation mapping;
- CI live PostgreSQL gate coverage.

## Implementation Sequence

Current uncommitted state indicates several later slices have already been partially or fully implemented. The architecture sequence remains:

1. Idempotency key, fingerprint, replay payload, and outcome contracts.
2. Application-facing hashed idempotency identity/port contracts.
3. PostgreSQL idempotency table, mapper, store, constraints, and migration.
4. Transaction-bound Infrastructure idempotent mutation orchestrator.
5. Live PostgreSQL idempotency concurrency and privacy validation.
6. Runtime/API host composition of idempotent mutation orchestration.
7. Presentation/public mutation integration requiring idempotency keys.
8. Live public mutation retry/replay validation.
9. Release-readiness reassessment.

## Blocking Dependencies

- Dedicated live idempotency PostgreSQL evidence.

## Final Assessment

Durable idempotency is architecturally required for all nine Portfolio Workspace mutations and not required for Get Portfolio Execution. The correct design is now clear enough for implementation work, and current uncommitted code appears directionally aligned. Public mutation remains NO-GO until durable idempotency is wired into the presentation/API mutation path and live validated end to end.
