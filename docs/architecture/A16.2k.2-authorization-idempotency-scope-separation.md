## Authorization Behavior

The authorization path is complete for the currently exposed internal API surface:

1. The API host receives a trusted principal from the host boundary.
2. Production authorization derives a pseudonymous `PortfolioWorkspaceAuthorizationResourceReference` from principal type, provider, and principal ID.
3. Initialization receives that reference from the authorization boundary, not from request body/path/header data.
4. `PortfolioExecution` persists the reference as immutable aggregate state.
5. Durable record mapping writes and reads the reference from aggregate payload.
6. Runtime exposes a resource-resolution application service.
7. Get-by-ID resolves persisted ownership and denies mismatched principals before returning execution data.
8. Presentation errors remain safe and correlation-aware.

Only initialize and get-by-ID are currently presentation/host exposed. The other behavioral use cases remain Application services/runtime services and do not have public/internal API handlers in this scope.

## Persistence and Versioning

Record version `2` was introduced because durable aggregate payload compatibility changed: `authorizationResourceReference` became required aggregate state.

Version-1 records do not contain a trusted ownership reference. The current documented policy is to reject unsupported version-1 records rather than infer ownership from plan, approval, actor, or request principal. Because no approved production durable data set exists yet, this is acceptable for release-candidate validation but remains an explicit deployment/backfill consideration before any upgrade over real durable data.

No authorization table or migration is introduced. Ownership is embedded in the PortfolioExecution aggregate payload.
