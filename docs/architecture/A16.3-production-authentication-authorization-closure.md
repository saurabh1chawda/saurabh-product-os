## Executive Summary

Portfolio Workspace has the correct production authentication ownership shape:
authentication remains outer-host/provider-owned, and Portfolio Workspace
receives a normalized trusted presentation principal. Portfolio Workspace must
not verify provider credentials in Domain, Application, Infrastructure, or the
current framework-neutral internal handlers.

Portfolio Workspace also has a concrete production authorization policy for the
currently implemented internal handler surface:

- initialization receives a pseudonymous authorization resource derived from
  the trusted principal;
- get-by-ID resolves the persisted execution authorization resource through the
  runtime/application boundary and compares it with the requesting principal's
  derived resource;
- request bodies cannot override ownership;
- authorization denial occurs before the protected Application Service is
  invoked.

The remaining production gap is not a Domain/Application contract problem. It
is outer-host authentication integration: a future public transport/server must
verify provider credentials and pass only verified principals into
`PortfolioWorkspaceApiHost` handlers. Public mutation remains blocked by the
separate durable idempotency condition.

## Current Authentication Boundary

The committed presentation principal contract is
`PortfolioWorkspacePresentationPrincipal`.

It contains:

- `principalId`;
- `principalType` (`user` or `service`);
- `authenticationProvider`;
- optional `displayName`.

It validates field shape, length, and unsafe control characters. It does not
cryptographically verify tokens or sessions.

Current handlers require callers to provide an already-authenticated
`PortfolioWorkspacePresentationPrincipal`. This is intentional for the
framework-neutral internal API host. Authentication is expected to happen before
handler invocation.

## Current Trust Boundary

The current trusted flow is:

`outer host/auth provider`
-> `PortfolioWorkspacePresentationPrincipal`
-> `PortfolioWorkspaceApiHost`
-> `PortfolioWorkspaceInternalAuthorization`
-> `PortfolioWorkspaceRuntime`
-> `Application Service`
-> `PortfolioExecutionRepository`
-> `PortfolioExecution`

Portfolio Workspace trusts the host boundary to supply a verified principal.
The API host and handlers do not parse tokens, inspect sessions, call identity
providers, or read arbitrary identity from request bodies.

This means callers can fabricate principals if they can directly invoke the
internal handler API. That is acceptable for internal/test use but must not be
the public production boundary. A future public server adapter must obtain the
principal only from a verified authentication adapter.

## Authentication Ownership Decision

Decision: production authentication is owned by the outer public
transport/server and provider adapter.

Portfolio Workspace should not directly depend on Auth0, Clerk, Cognito,
Firebase Auth, Auth.js, JWT libraries, or OAuth SDKs inside Domain,
Application, Infrastructure, or the framework-neutral API host.

The correct production model is:

`Public Transport / Server`
-> `Authentication Adapter`
-> `Verified Principal`
-> `PortfolioWorkspaceApiHost`
-> `PortfolioWorkspaceProductionAuthorization`
-> `Application`

The authentication adapter must fail closed when provider identity is missing,
invalid, expired, revoked, or malformed.

## Principal Contract Review

The current principal contract is sufficient for provider-neutral handoff for
single-principal ownership:

- `principalId` is the stable provider subject;
- `authenticationProvider` scopes the subject to its issuer/provider;
- `principalType` distinguishes user and service actors;
- `displayName` is non-authoritative presentation metadata.

The principal intentionally does not carry arbitrary permissions. Authorization
decisions remain outside the principal.

No tenant/workspace identifier is represented. This is acceptable only for the
current principal-owned PortfolioExecution model. If future product behavior
requires organizations, teams, delegated access, shared executions, or workspace
membership, a separate authorization resource/model extension will be required.

## Current Authorization Boundary

`PortfolioWorkspaceInternalAuthorization` is presentation/host-local and exposes
explicit methods:

- `authorizeInitialize`;
- `authorizeGet`.

`PortfolioWorkspaceProductionAuthorization` is the committed production policy
for the current internal handler surface.

The API host composes production authorization by default with
`PortfolioWorkspaceRuntimeAuthorizationResourceResolver`. Tests may inject fake
authorization seams, but production host construction does not silently default
to a permissive policy.

## Authorization Ownership Decision

Authorization is owned by the presentation/host boundary using explicit
operation methods. It is not a Domain concern and is not encoded as transport
logic in Application.

The Domain stores `PortfolioWorkspaceAuthorizationResourceReference` as the
aggregate ownership/security resource. Application can initialize it and resolve
it through a narrow query service, but it does not decide whether a caller is
allowed.

Infrastructure persists and rehydrates the resource as part of the aggregate
payload. Infrastructure does not decide authorization policy.

## Initialize Authorization Assessment

Initialization authorization happens before command-context creation, before
Application input mapping, and before the initialization Application Service is
called.

The production policy derives a pseudonymous authorization resource from the
trusted principal:

`portfolio-workspace:principal:<type>:<sha256(provider + subject)>`

The initialization request body cannot supply or override the authorization
resource. The mapped Application input receives the trusted authorization
resource from the authorization result.

Status: structurally sound for internal initialization. Public mutation
exposure still requires provider authentication and durable idempotency.

## Get Authorization Assessment

Get-by-ID parses and validates the requested `ExecutionId`, then invokes
`authorizeGet` before calling `runtime.getPortfolioExecution`.

`PortfolioWorkspaceProductionAuthorization` resolves the persisted
authorization resource through
`ResolvePortfolioExecutionAuthorizationResourceApplicationService`, compares it
with the requesting principal's derived resource, and returns a safe forbidden
error if they differ.

Status: sound for current principal-owned read access.

## Resource and Ownership Authorization Assessment

The ownership model is now explicit:

- authorization resource is stored on `PortfolioExecution`;
- record mapping requires it;
- PostgreSQL JSONB payload persists it;
- live API host tests verify persisted privacy and cross-principal denial.

The model is intentionally pseudonymous and does not persist provider name or
raw principal ID in `authorizationResourceReference`.

Limitations:

- no tenant/workspace/team model;
- no delegated access;
- no role/capability policy;
- only initialize and get are handler-exposed today.

Those limitations are not defects for the current internal surface, but they
are product decisions before broader public access.

## Threat Assessment

| Threat | Current state | Classification |
| --- | --- | --- |
| Caller fabricates principal | Possible if caller reaches internal handler directly | Not prevented by Portfolio Workspace; outer host must prevent |
| Principal missing | Handler signature requires principal; future public transport must map absence to unauthenticated | Structurally prepared, provider integration pending |
| Malformed identity | Principal factory validates safe shape | Already partially prevented |
| Expired/revoked auth | No provider verification in Portfolio Workspace | Outside Portfolio Workspace ownership |
| Cross-user execution access | Get compares persisted resource with requester resource | Already prevented for principal-owned executions |
| Cross-tenant access | Tenant is not modeled | Product/authorization model deferred |
| Unauthorized initialize | Authorization runs before initialization side effects | Structurally prevented once principal is verified |
| Permissive production authorization | Production host composes `PortfolioWorkspaceProductionAuthorization` by default | Already prevented for current host |
| Authorization after side effect | Initialize/get authorize before Application Service call | Already prevented |
| Sensitive identity leakage | Authorization resource is hashed; errors are safe | Already partially prevented |

## Error and Privacy Assessment

The presentation error model distinguishes:

- unauthenticated;
- forbidden;
- invalid input;
- not found;
- conflict;
- unavailable;
- internal.

Errors do not expose provider tokens, database metadata, SQL, raw policy
internals, or raw principal identity.

The current internal handlers do not themselves create unauthenticated errors
because they receive a typed trusted principal. The future public adapter must
map missing/invalid provider authentication to the existing unauthenticated
presentation error.

## Public Mutation Exposure Decision

Public mutation exposure remains blocked.

Authentication plus authorization closure is not sufficient for public
initialize or other mutation endpoints because durable mutation idempotency is a
separate required A16 condition.

Allowed after A16.3:

- proceed to provider-auth adapter design;
- proceed to idempotency design/implementation;
- keep internal handlers and host-only surfaces.

Not allowed after A16.3:

- public retryable mutation exposure;
- client-supplied trusted principals;
- request-body ownership override.

## Implementation Model Selected

Selected model:

`MODEL A - Architecture already sufficient`

The provider-neutral principal handoff, production authorization policy, and
ownership resource path are sufficient for the current Portfolio Workspace
internal initialize/get surface.

No production code change is justified in A16.3. Provider authentication and
public transport integration should be handled in a future dedicated slice.
