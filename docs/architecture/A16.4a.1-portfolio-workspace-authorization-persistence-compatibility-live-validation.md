# A16.4a.1 - Portfolio Workspace Authorization Persistence Compatibility and Live Validation

## Executive Summary

A16.4a introduced durable Portfolio Workspace authorization ownership by adding `PortfolioWorkspaceAuthorizationResourceReference` to `PortfolioExecution`, initialization input, initialization fact, in-memory rehydration, and the durable aggregate payload.

This changed the durable PortfolioExecution record payload contract from record version `1` to record version `2`.

A16.4a.1 confirms the compatibility policy:

- record version `2` is the only supported durable PortfolioExecution record version;
- record version `1` is intentionally unsupported because it does not contain the trusted authorization resource;
- no mapper, repository, handler, or presentation path may fabricate a fallback authorization resource;
- version-2 records missing or corrupting the authorization resource fail safely as mapping failures;
- SQL schema migration is not required because the payload is stored in JSONB and `record_version` remains an existing relational column.

## Persistence Version Contract

`PORTFOLIO_EXECUTION_RECORD_VERSION` is `2`.

Record version `2` means the durable record contains:

- relational `execution_id`;
- relational `record_version`;
- relational optimistic-concurrency `revision`;
- JSONB aggregate payload including `authorizationResourceReference`.

`record_version` is persistence-shape compatibility metadata. It is distinct from:

- optimistic-concurrency `revision`;
- Drizzle migration metadata;
- Domain lifecycle;
- Application correlation.

## Version-1 Compatibility Classification

Classification: VERSION 1 INTENTIONALLY UNSUPPORTED.

The mapper validates record version before aggregate reconstruction. Any record whose `recordVersion` is not `2` fails with `UnsupportedPortfolioExecutionRecordVersionError`.

This includes record version `1`.

## Security Rationale

Version-1 PortfolioExecution payloads predate `PortfolioWorkspaceAuthorizationResourceReference`.

They do not contain enough trusted data to reconstruct the new ownership resource. Inferring ownership from `PortfolioPlanReference`, `PlanSnapshotReference`, `ApprovalReference`, current request principal, current user, `actorReference`, or a static fallback would violate the A16.4a ownership model.

Therefore, the safe behavior is explicit incompatibility until a future approved migration/backfill can assign trusted resources to any known historical records.

## Historical Production Data Assessment

Repository evidence shows Portfolio Workspace has been implemented through release-candidate slices with local and hosted validation. A16 and A16.4 documentation still classify provider authentication, production authorization policy, public routes, public mutation idempotency, observability, and database operations as remaining production blockers.

No repository evidence proves that public production Portfolio Workspace records exist.

If external deployment evidence later proves version-1 production records exist, A16.4a.1 is not sufficient by itself. A safe explicit migration or backfill decision will be required before deployment over that data.

## Mapper Behavior

The mapper:

- writes record version `2`;
- writes `authorizationResourceReference` inside `aggregatePayload`;
- rehydrates the aggregate through public Domain constructors and value objects;
- rejects unsupported versions with `UnsupportedPortfolioExecutionRecordVersionError`;
- rejects corrupt version-2 payloads with `PortfolioExecutionPersistenceMappingError`;
- does not create fallback ownership values.

Regression coverage proves:

- version `2` round-trips authorization ownership exactly;
- version `1` is rejected as unsupported;
- future unsupported versions are rejected;
- missing or invalid authorization resource in a version-2 record is a mapping failure.

## In-Memory Parity

The in-memory repository stores cloned aggregate JSON and rehydrates through the current `PortfolioExecution` constructor.

It preserves:

- authorization resource type/value;
- aggregate identity;
- lifecycle;
- work items;
- candidates;
- accepted artifacts;
- independent loaded object graphs.

The in-memory adapter does not model durable record versions and therefore does not hide the PostgreSQL mapper policy. Durable record-version behavior is tested in the Infrastructure mapper and PostgreSQL repository tests.

## Privacy and Presentation Boundary

Presentation request JSON cannot set authorization ownership.

The trusted ownership resource is returned by the host-local internal authorization boundary during initialization and then passed to the initialization mapper.

Presentation responses and Get output do not expose the authorization resource.

Mapper and repository errors remain technology-neutral and do not expose raw PostgreSQL, Drizzle, SQL, connection strings, table details, or credentials.
